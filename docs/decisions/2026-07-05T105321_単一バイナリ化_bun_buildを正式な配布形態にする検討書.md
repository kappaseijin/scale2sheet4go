# 単一バイナリ化（bun buildを正式な配布形態にする）についての検討書

## 背景

[Ph.11の検討書](./2026-07-05T102021_Bun_CLI化についての検討書.md)では、Bunを「追加のビルド専用ツール」として位置づけ、`node dist/index.js`を正式経路のまま維持し、`bun build --compile`は追加のオプションとする方針を採用した。

その後ユーザーから明確な方針転換の指示があった: 「このプロジェクトで作成するアプリを『bun build』からの単一バイナリアプリとする」。すなわち、`bun build --compile`で生成する単体実行バイナリを、追加のオプションではなく**正式な配布・運用形態そのもの**にする。

この指示を受けて、何を「正式」と「維持」の境界にするかを再定義する必要がある。

## 採用した案

**案A: 配布・運用（launchd自動実行、エンドユーザーへの成果物）はBunの単体バイナリを正式経路とする。ソースコードは引き続きNode.js API互換のTypeScriptとして書き、`npm test`/`tsc --noEmit`等の開発・CI検証にはNode.jsツールチェインを使い続ける。**

具体的な境界:

| 区分 | 方針 |
| --- | --- |
| ソースコード | 引き続きNode.js API互換のTypeScript（Bun固有API不使用）。「Node.jsアプリであることを保つ」という制約は、配布形態ではなくソースコードの互換性として維持する |
| 開発・型検査・ユニットテスト | 現状通り `npm run typecheck` / `npm test`（vitest, Node実行）を使う。Bunでも同等に通ることは受け入れ基準として維持するが、開発フローそのものをBunに置き換えない |
| ビルド成果物・配布形態 | `bun build --compile`による単体バイナリを正式な成果物とする。`npm run build && node dist/index.js`は開発・デバッグ用の経路として残すが、運用上の正式手順ではなくなる |
| launchd自動実行 | `scripts/run-pipeline.sh`が呼び出す実体を、Node実行からコンパイル済み単体バイナリへ切り替える |
| README | 「インストール」手順の主経路をBunバイナリのビルド・配置に更新する。Node実行手順は開発者向けとして残す |

採用理由:

- ユーザーの明示的な指示（「単一バイナリアプリとする」）に最も直接対応する
- Ph.11で判明した「ソースコードはNode.js互換のまま」という制約は、配布形態を変えても矛盾しない（バイナリの中身がNode.js互換コードのBunコンパイル結果であることと、配布形態が単体バイナリであることは両立する）
- 開発時の型検査・テストにNode.jsツールチェイン（tsc, vitest）を使い続けられるため、[Ph.11の検討書](./2026-07-05T102021_Bun_CLI化についての検討書.md)で発見された「`bunx --bun vitest run --run`でzodが壊れる」問題を、テスト実行方法の変更（Node実行のまま）で当面回避しつつ、実行時（コンパイル済みバイナリ）側の問題として独立に解決を進められる

**前提条件（ブロッカー）**: Ph.11で発見済みの「コンパイル済みバイナリ実行時、Bunランタイム上でzodが正しく動くか」は未検証（判明しているのは`vitest`経由の`--bun`実行時の問題であり、`bun build --compile`で生成した実際のバイナリでのzod動作は別途確認が必要）。実装フェーズの最優先事項として、コンパイル済みバイナリが実際にzodスキーマ検証（`config/settings.ts`, `config/env.ts`, `sources/scale-exporter/reader.ts`で使用）を含む一連の処理を問題なく実行できるかを最初に切り分ける。ここで解決不能な問題が見つかった場合は、本方針自体を見直す（zodの別バージョンへの切り替え、または代替のバリデーション手段への置き換えを検討する）。

## 却下した案

### 案B: Ph.11の方針（Node実行を正式、Bunは追加オプション）を維持する

却下した理由: ユーザーから明示的に「単一バイナリアプリとする」という上書き指示があったため、追加オプション止まりの位置づけは指示に反する。

### 案C: ソースコードもビルドツールチェインも含め、全面的にBun化する（`bun install`、Bun純正テストランナーへの移行、tscの廃止）

却下した理由: 「Node.jsアプリであることを保つ」という2026-07-04〜05にかけての一連のユーザー指示の一貫性（[Ph.11検討書](./2026-07-05T102021_Bun_CLI化についての検討書.md)参照）と矛盾する。また現時点でzod/Bunランタイムの相互運用性に既知の問題があり、開発・テストツールチェインまでBun化すると問題の切り分けが困難になる。配布形態のみをBun化し、開発ツールチェインはNode.jsに残すことで、問題箇所を「実行時（コンパイル済みバイナリ）」に限定できる。

### 案D: launchd運用はNode実行のまま残し、Bunバイナイルは別配布物（例: 手元配布用CLI）として並行提供する

却下した理由: ユーザーの指示は「このプロジェクトで作成するアプリ」全体を単一バイナリアプリにするというもので、launchd運用を含む正式経路をBunバイナリに揃えることが指示の趣旨に合う。運用経路を二重に保守するコストも避けられる。
