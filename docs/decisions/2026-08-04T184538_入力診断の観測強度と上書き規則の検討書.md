# 入力診断の観測強度と上書き規則

起草: `scale2sheet_architect_codex`（2026-08-04 JST）
検証: `scale2sheet_reviewer_claude`（初回レビュー済み、再レビュー予定）
決定: ユーザー

| 項目 | 値 |
| --- | --- |
| 起点 | Issue #77「入力段階の診断が、後の弱い観測で前の強い観測を上書きする」 |
| 関連 | PR #73 の non-blocking N-2、Issue #59、案件A、AC-42a |
| production gate | pipeline を shadow から出す前に解消する |
| 範囲 | 検討のみであり、実装は変更しない |

## 1. 現象

`readStableInputSnapshot` は、最大3回の attempt で得た失敗を `lastOutcome`、`lastDiagnostic`、`lastCounts` に保持する。
各変数は attempt の進行に合わせて別々に代入される。

この構造では、後の attempt が情報量の少ない観測でも、前の具体的な観測を上書きする。
main `d93f641` で、1回目に不正JSONを検出し、その後に対象ファイルを rotate する条件を再現した結果は次のとおりだった。

```json
{
  "outcome": "input-missing",
  "diagnostic": "no target-date files found for 2026-08-04",
  "counts": { "matchedFileCount": 0 }
}
```

この実行では「最終 attempt に対象ファイルが無かった」ことと「先行 attempt で不正JSONを読んだ」ことの両方が真である。
しかし、pipeline の集約結果が答える問いは「最後の瞬間に何が見えたか」ではなく、「安定した入力を返せなかった理由として、運用者が次に使うべき証拠は何か」である。

`failed:input-missing` は producer の出力を確認する行動へつながる。
`failed:input-invalid-or-partial` はファイル名と行番号を使って内容を調べる行動へつながる。
後の不在だけを残すと、既に得た故障箇所を捨て、運用者を別の調査先へ誘導する。

別の不整合もある。
読取後の snapshot が変わった経路は `lastOutcome` だけを `input-unstable` へ変更し、`lastDiagnostic` を更新しない。
先行 attempt に parse error がある場合、`input-unstable` と parse error の diagnostic が組み合わさり得る。

## 2. 既存契約

案件A と通知追補は、入力段階の outcome と運用者の行動を次のように分けている。

| outcome | 観測した事実 | 運用者の次の行動 |
| --- | --- | --- |
| `failed:input-missing` | 対象日ファイルを観測できない | producer の出力を確認する |
| `failed:input-unstable` | ファイル集合または属性が変化する | 次の実行を待つ |
| `failed:input-invalid-or-partial` | ファイルを読んだが parse できない | ファイル名と行番号から内容を確認する |
| `completed:no-data` | 安定して parse できたが period 適用後に0件 | 正常な no-transfer として扱う |

AC-42a は、入力段階の読取失敗でファイル名と行番号を残すことを求める。
Issue #59 の障害では、この diagnostic によって失敗ファイルと行を特定できた。

bounded stable snapshot の retry は、途中の失敗を必ず最終失敗にするための仕組みではない。
後の attempt で安定し、全行を parse できた場合に回復するための仕組みである。
したがって、安定して parse できた snapshot は従来どおり即座に成功として返す。

本件は既存の outcome 文字列を変更しない。
`input-missing`、`input-unstable`、`input-invalid-or-partial` の選択規則だけを変更対象とする。
`failed:` を付ける pipeline outcome、終了コード、通知段階、status のフィールドも維持する。

固定箇所は次の検索で確認した。

```bash
rg -n 'failed:input-missing|failed:input-unstable|failed:input-invalid-or-partial' src test scripts docs
```

主な固定箇所は `src/pipeline/pipeline.ts`、pipeline の unit test、compiled acceptance、`INSTALLATION_DESIGN.md`、案件A、status schema の検討書、通知追補である。
新しい outcome を追加しないため、これらの schema migration は発生しない。

## 3. 観測強度

失敗の強さは、障害の深刻度ではなく、入力処理が到達した深さと証拠の具体性で決める。
後の attempt で得たという時系列だけでは強さを決めない。

| 強度 | 観測 | 到達した処理 | 根拠 |
| ---: | --- | --- | --- |
| 3 | `input-invalid-or-partial` | 対象ファイルを列挙し、安定待機後に内容と失敗行まで読んだ | ファイル名と行番号を持つ最も具体的な証拠である |
| 2 | `input-unstable` | 対象ファイルを列挙し、集合または属性の変化を比較した | ファイルの存在と変化を観測している |
| 1 | `input-missing` | 対象名の列挙結果が0件だった | その attempt で存在を観測できなかったことだけを示す |

この順序では、`input-invalid-or-partial > input-unstable > input-missing` となる。
後の missing は、前に観測した不正行や属性変化を反証しない。

安定して全行を parse できた `ready` は失敗候補の強度比較へ入れない。
`ready` を得た時点で retry の目的を達成しているため、先行する失敗候補があっても成功を返す。

同じ強度の観測が複数ある場合は、後の attempt の観測を採用する。
同一分類のまま、より新しい証拠を返すためである。
この置換でも outcome、diagnostic、counts は必ず同じ attempt の組として扱う。

## 4. 選択肢

### D-0 最後の attempt を採用する

現状と同じく、各 attempt の失敗で保持値を上書きする。

この案が成立するには、次の条件をすべて満たす必要がある。

1. 後の観測が、前の観測を反証する。
2. outcome が変わっても、運用者の次の行動が変わらない。
3. ファイル名と行番号を失っても、別の記録から同じ故障箇所へ到達できる。
4. outcome、diagnostic、counts が常に同じ attempt から更新される。

現状はどの条件も満たさない。
missing は先行する parse failure を反証せず、3種類の outcome は異なる行動へつながり、AC-42a の diagnostic に代わる記録もない。
さらに、読取後の snapshot 不一致では outcome だけが更新される。

### D-1 最も強い失敗観測を採用する

各 attempt の失敗を、outcome、diagnostic、counts を含む不可分な**失敗観測**として生成する。
現在の観測と新しい観測を強度で比較し、強い側を保持する。
同じ強度なら新しい観測を組ごと採用する。

選択結果は次の表で一意に決まる。

| 保持中の観測＼新しい観測 | missing | unstable | invalid-or-partial |
| --- | --- | --- | --- |
| missing | 新しい missing | unstable | invalid-or-partial |
| unstable | 保持中の unstable | 新しい unstable | invalid-or-partial |
| invalid-or-partial | 保持中の invalid-or-partial | 保持中の invalid-or-partial | 新しい invalid-or-partial |

独立した `lastOutcome` と `lastDiagnostic` を持たず、失敗観測を一つの値として置換する。
型は outcome ごとに対応する diagnostic と counts を束ねる discriminated union とし、片方だけを更新できない境界を作る。

counts は関数終了時点の最新値ではなく、採用した失敗観測を得た時点の値を表す。
強い先行観測を保持した後に producer がファイルを追加しても counts は先行観測時点のままとなるが、別々の attempt から outcome、diagnostic、counts を合成しない一貫性を優先する。

`input-unstable` は発生点に対応する diagnostic を持つ。
安定待機中の変化ならその旨を記録し、読取後の再確認で変化した場合は読取中の変化として記録する。
parse error の diagnostic を引き継がない。

読取後の再確認で起きる変化は、現行の `delay` ポートだけでは決定的に試験できない。
実装では、`readSnapshot` の完了後から `afterRead` snapshot の取得前までに await 可能な hook を置くか、`readdir`、`stat`、`readFile` を file-system port として注入する。
試験は hook 内のファイル変更または fake port の応答制御によって、この分岐を外部処理との競合に頼らず再現する。
production path は no-op hook または実ファイルシステムの adapter を使い、seam の追加によって待機やファイル変更を増やさない。

この案は outcome schema を変えず、retry の回復能力も維持する。
一方、採用しなかった弱い観測の履歴は残さない。

### D-2 全 attempt の観測履歴を保存する

各 attempt の missing、unstable、invalid-or-partial をすべて保存し、最終 outcome と一緒に status または log へ出す。

この案は時系列を追跡できる。
しかし、attempt 履歴の status schema、保存上限、通知への出し方、diagnostic の秘匿範囲を新たに決める必要がある。
Issue #77 の目的は既存診断の劣化防止であり、全履歴の永続化は目的を超える。

## 5. 推奨

推奨は D-1 である。

D-1 は、観測強度を処理の到達深度として明示し、失敗情報を不可分な値として扱う。
これにより、選択順序と outcome／diagnostic の対応を別々の規約にせず、一つの更新規則で保証できる。

代表的な遷移は次の結果になる。

| attempt の順序 | 最終結果 | 保持する diagnostic |
| --- | --- | --- |
| invalid-or-partial → missing → missing | `failed:input-invalid-or-partial` | 最初の parse error のファイル名と行番号 |
| missing → unstable → missing | `failed:input-unstable` | 属性または集合が変化した段階 |
| unstable → invalid-or-partial → missing | `failed:input-invalid-or-partial` | 2回目の parse error のファイル名と行番号 |
| invalid-or-partial → ready | 成功 | 失敗 diagnostic を返さない |
| invalid-or-partial → invalid-or-partial → missing | `failed:input-invalid-or-partial` | 2回目の parse error のファイル名と行番号 |

`failed:input-missing` は、3回の attempt で missing より強い失敗を一度も観測しなかった場合だけ返す。
`failed:input-unstable` は、invalid-or-partial を観測せず、少なくとも一度 unstable を観測した場合に返す。
`failed:input-invalid-or-partial` は、成功しないまま少なくとも一度 parse failure を観測した場合に返す。

## 6. 合格条件

既存の AC-84 に続けて採番する。

- **AC-85**: 3種類の失敗観測に `input-invalid-or-partial > input-unstable > input-missing` の順序があり、処理の到達深度を根拠として実装とテストに同じ順序を使うこと。
- **AC-86**: outcome、diagnostic、counts を同じ attempt の不可分な観測として更新し、いずれか一部だけを更新する経路がないこと。
- **AC-87**: 不正行を検出した後に対象ファイルが rotate または消失しても、最終結果が `failed:input-invalid-or-partial` であり、最初に失敗したファイル名と行番号を保持すること。
- **AC-88**: `readSnapshot` の完了後から `afterRead` snapshot の取得前までに変化を決定的に注入できる seam を設け、先行 attempt が invalid-or-partial、後続 attempt が読取後の unstable となる試験で、最終結果が `failed:input-invalid-or-partial` と対応する parse error の diagnostic になること。
- **AC-89**: missing、unstable、invalid-or-partial の全組合せで上記の選択表どおりになり、同じ強度では後の観測を組ごと採用すること。
- **AC-90**: 先行 attempt が失敗しても、後の attempt で安定かつ parse 可能な snapshot を得た場合は従来どおり成功すること。
- **AC-91**: `completed:no-data`、`failed:input-missing`、`failed:input-unstable`、`failed:input-invalid-or-partial` の文字列と既存の終了コードを変更しないこと。
- **AC-92（負のコントロール）**: AC-88 の seam を使う試験を含め、独立した outcome 代入だけを復活させる変異、または強度比較を最後の attempt 優先へ戻す変異で、AC-86〜89 の試験が失敗すること。

## 7. 範囲外

- pipeline の実装変更
- outcome 文字列、終了コード、通知段階の追加または変更
- 全 attempt 履歴の status schema 追加
- **成功時の先行失敗の保存**：本件では扱わない。
  D-1 は現行の成功短絡を維持するため、後続 attempt が `ready` になった場合、先行 attempt の失敗観測を強度にかかわらず破棄し、その記録を status または log に残さない。
  したがって、不正行を検出したファイルが parse 可能なファイルへ入れ替わると、成功して先行する破損の証跡を残さない。
  この証跡を保存するかどうかは、案件A のファイル単位スキップと部分成功に関わる別の決定とする。
- #66 の命名不一致ファイル検出
- #78 を含む他の PR #73 non-blocking 指摘
- pipeline を shadow から出す作業

本書の決定後、programmer は D-1 の選択規則と不変条件を実装し、reviewer は AC-85〜92 を独立に検証する。

## 8. 実装状況

**決めたこと**：D-1 の post-read seam は `ReadStableInputSnapshotOptions.afterReadSnapshot` とする。

この hook は `readSnapshot` の完了後、再確認用 snapshot の取得前にだけ await する。

production 呼び出しでは hook を省略し、追加の待機やファイル操作はしない。

**動いていること**：失敗観測は outcome、diagnostic、counts、異常候補を一つの値として保持する。

強度が高い観測を優先し、同じ強度では後の観測を組ごと採用する。

後続 attempt が安定して parse できた場合は、先行する失敗観測を返さず成功する。
