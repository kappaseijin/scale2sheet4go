# 命名規約不一致ファイルの検出

起草: `scale2sheet_architect_codex`（2026-08-04）
検証: `scale2sheet_reviewer_claude`（依頼予定）
決定: ユーザー

| 項目 | 値 |
| --- | --- |
| 起点 | Issue #66「命名規約に一致しないファイルの存在に気づけない」 |
| 対象 | producer 出力ディレクトリの対象日ファイル |
| 関連 | 案件A（入力段階の失敗と部分成功）、G-1 / G-2 / G-3 |
| 範囲 | 検討のみ。Slice 2 の実装は変更しない |

## 1. 問題

現行 `src/sources/scale-exporter/reader.ts` は、次の正規表現に一致し、対象日が一致する名前だけを入力集合にする。

```text
^scale_exporter_(\d{4}-\d{2}-\d{2})_(apple-health|google-fit)_(\d{3})\.jsonl$
```

この設計は `.DS_Store` や Finder の複製を入力として誤読しない防御である。一方、producer の source mode が一部だけ変わると、正しい測定ファイルが存在するのに reader が静かに無視する。

2026-08-04 JST に、環境変数、settings、組み込み既定値の順で実効出力先を解決し、ディレクトリエントリを直接列挙した。
複製2件の生のファイル名は NFD であり、次の表は照合に使う NFC 表現で示す。

| ファイル | 分類の初期案 | 理由 |
| --- | --- | --- |
| `scale_exporter_2026-07-09_apple-health-file_001.jsonl` | **異常候補** | 正規表現の source 値域外で、測定ファイルらしい構造を持つ。producer の mode 変更を示し得る |
| `scale_exporter_2026-07-10_apple-health_001.jsonlのコピー` | **無視可能** | 正規名の Finder 複製であり、`.jsonl` の直後に複製語が続く。入力集合へ追加しない |
| `scale_exporter_2026-07-10_apple-health_001.jsonlのコピー2` | **無視可能** | 同上 |
| `.DS_Store` | **無視可能** | 測定ファイル名の形を持たない管理ファイル |

## 2. 検出の成立条件

検出対象は「正規表現に不一致なもの」全体ではない。不一致だけを通知すると、既知の複製や管理ファイルで通知が埋まり、通知を無視する状態を新たに作る。

候補を次の順に分類する。

1. **正規入力**: production reader と同一の `fileNamePattern` に一致し、対象日も一致する。従来どおり入力する。
2. **明らかな無視対象**: `.DS_Store` など測定ファイルの接頭辞・拡張子を持たない管理ファイル、または正規入力名の後ろに Finder 複製語（`のコピー`、`のコピー2` など）が付いたもの。通知しない。
3. **異常候補**: 対象日を含む `scale_exporter_YYYY-MM-DD_...jsonl` 形式に近いが、production reader の `fileNamePattern` に一致しないもの。入力には加えず、少なくとも status / log へ候補を記録し、通知するかを本書の決定対象とする。

ファイル名の文字列照合は、ディレクトリエントリの名前を NFC へ正規化した判定用文字列に対して行う。
macOS が返す NFD の生ファイル名は、ソースコードに NFC で記述した `のコピー` とそのままでは一致しないためである。
複製語の直前にスペースがあることは前提にせず、正規入力名の `.jsonl` の直後に続く接尾辞として照合する。
NFC 正規化は分類のための文字列比較だけに使い、ファイルアクセスにはディレクトリ列挙で得た元の名前を使う。

数字を使う選別規則は glob ではなく、production reader と同じ正規表現を基準にする。候補検出用の「近い名前」は、次の構造的な規則で列挙する。

```text
^scale_exporter_(\d{4}-\d{2}-\d{2})_.+\.jsonl$
```

この候補規則は入力採用規則ではない。候補を拾った後、複製語・管理ファイルを除外し、残りだけを異常候補とする。

## 3. 検出点の選択肢

| 案 | 検出点 | 内容 | 検出できるもの | 漏れるもの | Slice 2との関係 |
| --- | --- | --- | --- | --- | --- |
| D-0 | 検出しない | 現行 reader を維持する | 無し。全不一致が黙って無視される | 部分的な mode 変更、source 値域変更 | 衝突しないが問題を解決しない |
| D-1 | reader 内 | `listTargetFiles` と同じ列挙時に候補を分類し、異常候補を返す | reader が読む対象日ディレクトリの候補 | 別ディレクトリ、対象日として解釈できない名前 | **推奨**。入力集合と検出集合の基準が同じ |
| D-2 | pipeline | reader とは別にディレクトリを走査し、status / 通知へ反映する | pipeline 実行時に見える候補 | reader を直接使う既存 `run` 経路、pipeline 外の読取 | D-1と併用すると二重走査・二重通知になりやすい |
| D-3 | 別工程の survey / doctor | 実行時ではなく定期診断で候補を検出する | 実行されなかった日の候補、過去の候補 | 診断前の欠測、即時の入力失敗 | Slice 6 の診断へ拡張可能だが、Slice 2単独の解決にはならない |

**推奨は D-1** である。reader が入力へ採用する規則と、採用しない測定ファイル候補の規則を同じ境界に置けるため、検出対象と転記対象のずれを最小化できる。D-3 は履歴や実行されなかった日の補助検出として将来検討するが、本書では要求しない。

## 4. 通知の粒度と案件Aとの関係

案件A の G-1 / G-2 は、入力不在・不安定・parse不能という pipeline の実行結果を通知する。命名不一致は「対象日ファイルが無い」だけではなく、**ファイルはあるが reader が採用できない候補がある**という入力集合の異常である。

したがって、既存の `failed:input-missing` へ無理に統合しない。D-1 が異常候補を検出した場合は、次の順に扱う。

1. 正規入力が1件以上ある場合、正規入力の処理は継続する。ただし異常候補の存在を status / log に記録する。
2. 異常候補が測定ファイルである確証はないため、既存の input failure と同じ exit code 1へ自動格下げしない。通知は G-1 / G-2 の原因別通知体系に追加する候補として扱う。
3. 終端 status は `inputAnomalyCandidates` に候補を構造化して記録する。候補は生のファイル名と `file-name-pattern-mismatch` の理由を持つ。既存の `targetDate` と組み合わせて対象日を示す。候補がある終端 status では `targetDate` を必須とする。候補配列は生の名前の昇順にし、同じ名前と理由を重複させない。候補がない場合は空配列を書かず、field 自体を省略する。
4. 非空の候補配列は、終端 status と同じ時刻を `at` とする JSON 1行の log に、`event: "input-anomaly-candidates"`、`targetDate`、`inputAnomalyCandidates` とともに1実行1回だけ書く。running status と retry ごとの log には書かない。
5. 通知は今回配線しない。G-3 の最終文面と通知経路の決定後に扱う。
6. `のコピー` など無視対象だけの場合は、status / log へも記録しない。これが通知ノイズを抑える境界である。

本件は案件Aの G-3（原因別文面）そのものを再決定しない。G-1 / G-2と同じ input-stage の可視性へ接続するが、原因別の最終文面・通知経路は G-3 の追補で決める。

## 5. 現状維持 D-0 が成立する条件

D-0 は次の条件をすべて満たす場合に限り成立する。

- producer の source mode と filename pattern が固定契約として合意され、変更時に当方へ通知される
- 変更契約が無い場合でも、全不一致が `failed:input-missing` へ収束するため部分的な欠測が起きない
- 不一致ファイルを無視することが仕様として受容され、欠測の検知を別工程で保証する

現状は、`apple-health-file` が先方に実在する source mode であり、部分的な切替では正規ファイルが残るため `failed:input-missing` へ収束しない。よって D-0 の成立条件を満たさない。

## 6. 合格条件

- **AC-66**: production reader と同じ `fileNamePattern` を入力採用の基準として明記し、候補列挙には別の近似規則を使うことを区別する。
- **AC-67**: 対象日について、ファイル名を NFC へ正規化した判定用文字列により、正規入力、明らかな無視対象、異常候補を分類できること。実在3例と `.DS_Store` をこの分類へ再現可能に当てはめ、スペースを含まない `のコピー` と `のコピー2` を明らかな無視対象にする。
- **AC-68**: 異常候補が一部存在しても、正規入力の採用と転記を黙って中断しない。ただし候補名・対象日・不一致理由を status / log へ残す。
- **AC-69**: 明らかな無視対象だけの場合に通知を発火しないこと。
- **AC-70**: 異常候補がある場合の通知は、既存 G-1 / G-2 の入力段階通知と重複せず、候補を1実行1回へまとめること。最終文面は G-3 追補と整合する。
- **AC-71**: D-0 を採る場合、上記 §5 の成立条件を満たす証拠を提示すること。証拠が無い場合は D-0 を採用しない。

## 7. 範囲外

- producer の source mode や公開完了契約そのものを変更すること
- 異常候補の中身を parse して測定ファイルだと確定すること（候補検出と内容検証は別段階）
- #63 / #65 の測定同一性・件数単位の決定
- G-3 の最終的な通知文面・通知経路の再決定
- 日付のゼロ詰め漏れ、日付区切りの欠落、大文字拡張子、英語ロケールの複製接尾辞など、対象日をこの候補規則で特定できない近傍名の検出。これらは採用にも異常候補にも入らない。対象日を特定できない名前の扱いは別の診断設計で決める。

## 8. 実装契約

**決めたこと**：`PipelineStatus` の `inputAnomalyCandidates` は、`name` と `reason` を持つ候補配列である。

`reason` は現時点では `file-name-pattern-mismatch` だけを取る。

`name` には `readdir` が返した生の名前を保存する。

NFC 正規化は分類にだけ使い、status に保存する名前とファイルアクセスには使わない。

候補配列は `StableInputSnapshot` と `InputSnapshotError` が運ぶ。

各終端 status は、その終端結果で採用した input observation の候補だけを記録する。

pipeline は注入可能な `logger` を通じて JSON 1行を出力し、production の既定は `console` とする。

**動いていること**：終端 status の `inputAnomalyCandidates` と、同じ候補配列を持つ JSON 1行の log は実装済みである。

通知は本件では未配線であり、通知済みまたは通知仕様が確定済みとは扱わない。
