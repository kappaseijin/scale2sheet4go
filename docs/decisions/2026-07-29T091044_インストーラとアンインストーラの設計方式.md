# インストーラとアンインストーラの設計方式

## 位置づけ

本書は、ユーザーが決定済みの論点 A、E、H と AC-28 の例外境界を前提に、未決定の論点 B、C、D、F、G と `--purge` の方式を設計案へ落とす。

入力は `docs/decisions/2026-07-29T084808_インストーラとアンインストーラの目標定義.md`（commit `906d9bd`）である。

本書の推奨は採用決定ではない。
ユーザーが未決定論点を選んだ後に `status` を更新し、設計書を確定する。

## 決定済みの前提

### 独立配置

ユーザーは A-2 を採用した。
インストール後の `scale2sheet` はソースチェックアウト、`dist/`、Bun、npm、`node_modules/` を参照しない。

### アンインストールの既定

既定のアンインストールは実行体と launchd 登録だけを削除する。
`settings.json`、認証情報、ログは残す。

設定、認証情報、ログを削除するには `--purge` と確認を同時に指定する。
ただし、`--purge` を即時削除、退避、退避と wipe のどれにするかは未決定である。

鍵ファイルを削除しても、GCP 側の鍵は失効せず、サービスアカウントは Spreadsheet の共有先に残る。
アンインストーラは GCP の鍵失効と共有解除を実行できないため、`--purge` の前後に残作業として表示する。

### 内蔵 pipeline と通知境界

ユーザーは H-2 を採用した。
launchd はインストール済み単体バイナリの `pipeline` を直接起動し、シェルラッパと監視用の別ジョブを置かない。

実行体自体が欠落または実行不能な場合は通知コードも起動できないため、AC-28 の通知対象外とする。
登録時点の取り違えは実行体検査で防ぐ。
登録完了後の欠落は自動検出せず、Spreadsheet の行が増えていないことに利用者が気づく以外の検出手段を持たない。
体重計に乗らなかった日の no-op と未実行は Spreadsheet 上で同じ見た目になり、区別できない。
この沈黙期間はユーザーが受容した既知のリスクである。
`StandardErrorPath` は job の stderr であり、spawn 失敗が残る保証はない。
`doctor` は欠落した実行体と同じバイナリなので、欠落時には起動できない。
AC-36 は直近成功を報告するだけで、期待時刻超過を判定しない。
実行体が存在する状態の exporter 失敗と転記失敗は通知対象のままとする。

## 現行構造から導かれる追加条件

独立配置はバイナリをコピーするだけでは成立しない。
現行の launchd plist はチェックアウト内の `scripts/run-pipeline.sh` を起動し、その shell は `dist/scale2sheet` と `scale_exporter` の絶対パスを持つ。

したがって、次の二つを同時に除く必要がある。

- plist からチェックアウト内 shell への参照
- shell から `dist/scale2sheet` と `scale_exporter` への絶対パス参照

設定の `morning-cron` と `evening-cron` は `serve` 用であり、現行 launchd の拾い直し時刻を表していない。
今回の移行では launchd の既存時刻（朝 07:00 と 11:30、夜 21:00 と 23:30）を維持し、cron 設定の意味を変更しない。

## 統合方式の比較

### 方式 I：自己インストール CLI と内蔵パイプライン

コンパイル済みバイナリに `install`、`uninstall`、`doctor`、`pipeline` を追加する。
launchd はインストール済みバイナリの `pipeline --period <period>` を直接起動する。

初回だけ `scripts/install.sh` が依存関係の取得、Bun ビルド、`dist/scale2sheet install` の呼び出しを担う。
インストール後は shell を配置しない。

この方式では、配置と診断を既存の TypeScript、Commander、Vitest の範囲で実装できる。
パイプラインも TypeScript に移るため、現行 shell のリトライと通知を自動テストできる。

### 方式 II：自己インストール CLI と配置済み shell

`install`、`uninstall`、`doctor` はバイナリに持たせるが、`run-pipeline.sh` を Application Support などへコピーする。
インストーラは shell と plist の両方へ実行時パスを埋め込む。

この方式は現行 shell の移植量が少ない。
一方、バイナリ、shell、plist の三つを同じ版として管理する必要があり、更新時の atomic replacement とマニフェストが複雑になる。
shell の単体テストも Vitest に統合できない。

### 方式 III：shell だけで配置する

`scripts/install.sh` と `scripts/uninstall.sh` が、バイナリ、shell、plist、設定を直接管理する。

初回ビルド前から実行できる利点はある。
しかし JSON 設定の検証、マニフェスト、doctor、launchctl の状態判定を shell で再実装することになる。
インストール機能だけが TypeScript の型検査と Vitest から外れる。

### 推奨

方式 I を推奨する。

独立配置の障害は「バイナリの場所」だけではなく、「チェックアウト内 shell が運用経路に残っていること」だからである。
`pipeline` をバイナリへ移すと、launchd からチェックアウトまでの参照を一度に切れる。

方式 II は移行量を抑えるが、インストール後も shell を配布物として管理する。
方式 III は設定と診断の既存実装を再利用できない。

## 論点 B：インストール対象

### 選択肢

| 案 | 対象 | 帰結 |
| --- | --- | --- |
| B-1 | L1（バイナリ配置）のみ | 手動設定と手動 launchd 登録が残り、絶対パス問題を解消できない |
| B-2 | L1 と L2（設定初期化、認証確認、ログ作成） | 手動実行は整うが、日次自動化は移行されない |
| B-3 | L1、L2、L3（launchd 登録）を含め、L3 は `--launchd` で有効化 | 独立配置と日次自動化を両立し、継続的副作用を明示操作に限定できる |
| B-4 | L1、L2、L3 を既定で有効化 | 導入操作は短いが、`serve` との競合を利用者が選ぶ前に常駐化する |

### 推奨

B-3 を推奨する。

L1 と L2 は `install` の既定動作とする。
L3 は `--launchd` を指定した場合だけ実行する。

インストーラは既存 `settings.json` を上書きしない。
未作成時だけ既存の設定生成関数を使い、生成後に必要な認証ファイルを検査する。

認証ファイルが不足している場合は、不足ファイル名、配置先、入手方法を表示して非ゼロ終了する。
秘密情報を生成したり、GCP から取得したりしない。

## 論点 C：配置先

### 選択肢

| 案 | 配置 | 帰結 |
| --- | --- | --- |
| C-1 | `~/.local/bin/scale2sheet` 固定 | sudo 不要だが、別 prefix の検証と将来の配置変更に対応できない |
| C-2 | `/usr/local/bin/scale2sheet` 固定 | PATH に入りやすいが、sudo とシステム全体への書き込みを要求する |
| C-3 | `~/.config/scale2sheet/bin/scale2sheet` 固定 | 一か所にまとまるが、設定と実行体のライフサイクルが再び結合する |
| C-4 | `~/.local` を既定 prefix とし、`--prefix <dir>` を許可 | sudo 不要の既定を保ち、隔離テストと利用者指定を両立する |

### 推奨

C-4 を推奨する。

`--prefix` はインストールルートを表し、バイナリは `<prefix>/bin/scale2sheet` へ置く。
既定 prefix は `~/.local` とする。

インストール先は推測せず、`~/.config/scale2sheet/install-manifest.json` に記録する。
マニフェストは認証情報を含まず、配置先、launchd label、plist パス、ログディレクトリ、適用状態、バージョンだけを持つ。

アンインストーラはマニフェストを正本とする。
マニフェストが無い場合、暗黙の既定パスを削除しない。
未インストールとして報告し、明示的な `--prefix` が与えられた場合だけその対象を計画へ入れる。

## 論点 D：実装形態

### 選択肢

| 案 | 対応方式 | 評価 |
| --- | --- | --- |
| D-1 shell | 方式 III、または D-4 の初回 bootstrap | 単独採用では設定検証と manifest を再実装し、Vitest から外れる。bootstrap だけなら責務を限定できる |
| D-2 npm script | 独立方式なし | checkout、Node.js、npm への依存がインストール後も残り、A-2 と単体バイナリ配布に反する |
| D-3 Makefile | 独立方式なし | D-2 と同じ checkout 依存に加え、既存プロジェクトに無い Make の保守経路を増やす |
| D-4 バイナリ subcommand | 方式 I または II | 設定と型を再利用でき、install、uninstall、doctor を配布物だけで実行できる |

D-2 と D-3 は、初回ビルドの入口にはなれても、インストール後の更新と撤収の正本にはできない。
A-2 は checkout からの独立を要求するためである。

### 推奨

D-4 と極薄の D-1 を採用し、方式 I とする。

`scripts/install.sh` の責務は次に限定する。

1. `npm ci` で固定済み依存関係を取得する。
2. `npm run build:bun` で単体バイナリを生成する。
3. `dist/scale2sheet install "$@"` を実行する。

シェルは plist を生成せず、設定 JSON を読まず、アンインストールを実装しない。

バイナリへ追加する CLI は次のとおりとする。

```text
scale2sheet install [--prefix <dir>] [--launchd] [--dry-run] [--force]
scale2sheet uninstall [--dry-run] [--purge] [--yes] [--prefix <dir>]
scale2sheet doctor
scale2sheet pipeline --period <morning|evening>
```

`pipeline` は launchd 用の運用コマンドであり、現行 `run-pipeline.sh` の exporter リトライ、転記、macOS 通知を引き継ぐ。

## scale_exporter の解決

`scale_exporter` の配置規約を scale2sheet 側で固定しない。

設定へ `scale-exporter-command` を追加し、環境変数 `SCALE_EXPORTER_COMMAND` で上書きできるようにする。
値が絶対パスなら、そのファイルの存在と実行権限を検査する。
値がコマンド名なら、`PATH` で解決する。
既定値は `scale_exporter` とする。

生成する plist の `PATH` には、選択した prefix の `bin`、インストール時に解決済みの exporter ディレクトリ、macOS の標準コマンドディレクトリを含める。
相手プロジェクトが `~/.local/bin` を採用すればそのまま一致し、別配置でも設定上書きで対応できる。

`source` が `scale-exporter` で、`--launchd` を指定した場合は、exporter を解決できない状態で登録しない。
launchd を伴わないインストールでは警告にとどめ、`doctor` で再検査できる。

## 論点 F：冪等性と診断

### 必須にする故障対策

| 故障 | 設計 |
| --- | --- |
| bootstrap 重複 | label ごとに登録状態を判定し、登録済みなら `bootout` 後に plist を置換して `bootstrap` する |
| 実行中バイナリの破壊 | 同じディレクトリの一時ファイルへコピーし、実行権限と同期を確定してから `rename` する |
| `settings.json` 上書き | 未存在時だけ既存生成関数を呼び、既存ファイルは読取検証だけ行う |
| `serve` との二重書き込み | serve、pipeline、install、uninstall 共通の run receipt で検出し、既定は `--launchd` を中断する |
| 実行中 launchd job の中断 | pipeline の heartbeat 付き run receipt を検出し、既定は `bootout` せず中断する |

### F-e の選択肢

| 案 | 帰結 |
| --- | --- |
| F-e-1 無条件 bootout | 単純だが、実行中処理を停止して S-3 を破る |
| F-e-2 検出して中断（推奨） | 既定は処理を完走させる。`--force` 時だけ欠測リスクを表示して停止する |
| F-e-3 完了待ち | S-3 を守れるが、install の待ち時間に上限を置きにくい |
| F-e-4 plist だけ置換 | 処理は守れるが、更新が有効になる時点が暗黙になる |

run receipt は `open(path, "wx")`、15秒 heartbeat、60秒 stale 判定、owner token で管理する。
PID は診断表示と補助判定だけに使い、PID 再利用があるため生存判定の正本にしない。
60秒を超えた stale receipt は、次の取得者が atomic rename して回収する。
uninstall も receipt を取得し、実行中処理があれば `bootout` と削除の前に中断する。
推奨 F-e-2 では、`--force` は走行中処理の停止と当日データ欠測の可能性を明示する。

### dry-run の意味

`install --dry-run` と `uninstall --dry-run` は、副作用の無い操作計画表示とする。

ファイル作成、設定自動生成、バイナリコピー、plist 書き込み、状態を変える `launchctl`、Google 認証を含む外部 API 通信を実行しない。
読取専用の `launchctl print` は planned と skipped を区別するために許可する。
認証ファイルは `stat` による存在確認までとし、内容を読まず、認証クライアントを生成しない。
既存状態の読取結果と、実行時に行う操作を順序付きで表示する。

疎通診断は `dry-run` と混同しない。
明示的な `doctor` だけが Google 認証、Spreadsheet の読取、当日行の特定を行う。
`doctor` は Spreadsheet とローカル状態を書き換えず、鍵不足、認証失敗、シート未共有、当日行なしを区別して報告する。
`install` と `uninstall` は `doctor` を内部から呼ばない。

### 推奨

F-a から F-e、`--dry-run`、`doctor` をすべて必須とし、F-e は F-e-2 を推奨する。

各操作は `[planned]`、`[done]`、`[skipped]`、`[failed]` のいずれかで表示する。
途中失敗時は、完了した操作、未実行の操作、再実行方法を表示する。

### 対抗案

| 案 | 帰結 |
| --- | --- |
| F-a から F-e だけ | 冪等性の既知故障は防げるが、破壊操作の事前点検と翌朝を待たない疎通確認が無い |
| F-a から F-e と dry-run | 副作用を事前確認できるが、認証切れ、未共有、当日行不足を導入時に切り分けられない |
| F-a から F-e、dry-run、doctor | 操作計画と外部疎通を異なる副作用契約で検証できる |

dry-run と doctor は目的が異なるため、一方で他方を代替しない。

## 論点 G：作るか

### 選択肢

| 案 | 帰結 |
| --- | --- |
| G-1 作る | 実行時パスを持つ plist を生成でき、独立配置を実現できる |
| G-2 README だけ更新する | 利用者が plist と shell の絶対パスを手で実体化する必要が残る |
| G-3 plist 生成だけ作る | バイナリ配置、マニフェスト、診断、再実行安全性が手作業のまま残る |

### 推奨

G-1 を推奨する。

A-2 を決定した以上、実行時にしか分からない prefix、home、ログ、exporter のパスを plist へ反映する処理が必要である。
README はその処理主体になれない。

## 論点 H：run-pipeline.sh の処遇

### 選択肢

| 案 | 帰結 |
| --- | --- |
| H-1 script を独立配置 | 現行機能を小さな差分で保てるが、shell と TypeScript に運用ロジックが分かれ、配布物が増える |
| H-2 本体へ内蔵 | 単体バイナリを launchd が直接起動でき、リトライ、通知、ログ、period 検証を Vitest へ載せられる |
| H-3 併存 | 移行中の比較はできるが、同じ運用機能を二重保守する |

### ユーザー決定

H-2 を採用する。
初回を含む計3回の exporter 試行、60秒間隔、exporter 失敗時の転記中断、時刻ログ、period 検証を内蔵 pipeline へ移す。
通知 port を設け、exporter 失敗と転記失敗を区別して macOS 通知を要求する。

実行体自体が欠落または実行不能な場合は通知を要求しない。
自己欠落を実行体自身では検出できないためであり、シェルラッパへ検知不能点を移す案は採らない。
`--launchd` 登録直後の検査は必須にするが、登録後の欠落は自動検出しない。
AC-33、AC-34、AC-36 は実行体が起動できる範囲では有効だが、実行体自体の欠落には適用できない。

## `--purge` の派生仕様

| 案 | 挙動 | 帰結 |
| --- | --- | --- |
| P-1 即時削除（推奨） | 確認後に設定、認証情報、ログを削除する | `purge` の意味と一致するが不可逆 |
| P-2 退避 | timestamp 付きディレクトリへ移す | 復旧できるが、削除したつもりの秘密情報が残る |
| P-3 退避と wipe | 既定は退避し、追加フラグで削除する | 意図を表せるが、CLI と試験経路が増える |

P-1 を推奨する。
秘密情報を別名ディレクトリへ退避すると、利用者が削除したつもりの鍵がディスクへ残るためである。
ただし、方式はユーザー未決定であり、決定前に実装しない。

対話端末では削除対象と GCP 側の残作業を表示し、確認を求める。
非対話端末では `--yes` が無い限り失敗する。
`--yes` は GCP 側の鍵失効や Spreadsheet の共有解除を代行しない。

既定アンインストール後は実行体が消えるため、完了画面には残存パスと手動削除コマンドを表示する。
後から `--purge` を使う場合は、再取得した単体バイナリまたは再ビルドした `dist/scale2sheet` から実行する。

## 採用時に有効になる合格条件

推奨を採用すると、目標定義の AC-01 から AC-38 をすべて実装対象にできる。

AC-12 はローカル削除の成否ではなく、外部権限が残ることの表示を検証する。
表示には次を含める。

- GCP Console でサービスアカウント鍵を失効すること
- Spreadsheet の共有先からサービスアカウントを削除すること
- ローカル鍵ファイルの削除だけでは上記二つが行われないこと

## ユーザー決定事項

pm は次をユーザーへ提示する。

- **B-3（推奨）**：L1、L2、L3 を含め、launchd は `--launchd` で有効化する。
- **C-4（推奨）**：`~/.local` 既定と `--prefix` を採用し、マニフェストを持つ。
- **D-4 と極薄 D-1（推奨）**：自己インストール CLI と内蔵 `pipeline` を採用する。
- **F 全項目（推奨）**：F-a から F-e、副作用ゼロの `--dry-run`、読取専用の `doctor` を必須にし、F-e-2 を採用する。
- **G-1（推奨）**：インストーラを作る。
- **P-1（推奨、未決定）**：`--purge` は確認後にローカル対象を即時削除する。

H-2 と AC-28 の実行体欠落例外はユーザー決定済みであり、再提示しない。

ユーザー決定後、architect は本書と `docs/INSTALLATION_DESIGN.md` の `status` を更新する。
その後に実装計画と programmer への実装指示を作成する。
