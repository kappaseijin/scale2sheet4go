# Node.jsビルドスクリプトをbuild:nodeへ改名する検討書

## 背景

ユーザーから「node.jsのビルドを `build:node` としてください」と要望があった。

現行の `package.json` には、Node.jsで実行するJavaScriptを生成する `build` と、Bun単体バイナリを生成する `build:bun` がある。
しかし、配布と自動運用の正式経路はBun単体バイナリであり、未修飾の `build` がNode.js用であることを名前から判別できない。

過去のPh.12とPh.13では、Bunを配布時の第一選択にしつつ、Node.js経路を開発とデバッグ用に残す方針を採用した。
今回の要望はNode.js経路を削除するものではなく、そのビルド名を実行環境別の名前へ揃える変更として扱う。

2026-07-29、ユーザーは案Aを採用した。
未修飾の `build` を削除し、同じNode.jsビルドを `build:node` へ置き換える。

## 調査基準

調査は `origin/main` の commit `3bb21ec1c462038cbf047e810585a95460953532` を基準にした。
作業ツリーは `feature/bun-priority-rename` の古いcommitを指しているため、作業ツリーの内容を現行仕様の根拠には使っていない。

コード構造はcodebase-memory-mcpで確認し、npm scriptと文書内のコマンドはGitオブジェクトに対する文字列検索で補完した。
Git履歴とローカルのエージェント履歴も確認した。

履歴では、`build` は初期実装 commit `9221a1a` から存在し、`build:bun` は commit `3d5c7b4` で追加されている。
Node.js経路を開発用に残すユーザー方針は、ctxのClaude session `b849fce8-ecc7-7155-bf35-3002b41743ea` event `394d2cbf-9908-73b5-b605-cc2b705803ca` と、Codex session `eed286b5-b8ad-77db-ac0c-929e89d4606c` event `d5a471d9-4d68-7a09-a52c-fe3ea031b62e` でも確認できた。
この方針は既存のPh.12とPh.13の検討書にも記録されている。

## 現在のビルド境界

| npm script | コマンド | 目的 | 出力 |
| --- | --- | --- | --- |
| `build` | `tsc -p tsconfig.json` | Node.jsで実行するJavaScriptの生成 | `dist/index.js`、宣言ファイル、source map |
| `build:bun` | `bun build ./src/index.ts --compile --outfile dist/scale2sheet` | 配布と自動運用に使う単体バイナリの生成 | `dist/scale2sheet` |
| `typecheck` | `tsc -p tsconfig.json --noEmit` | emitを伴わない型検査 | なし |

`build` と `typecheck` は同じ `tsconfig.json` を読むが、目的が異なる。
`build:node` はNode.js実行用ファイルをemitし、`typecheck` はファイルを生成せず型検査だけを行う。

`build:node` から `typecheck` を呼び出す構成にはしない。
`tsc -p tsconfig.json` 自体が型エラーを検出するため、先に `typecheck` を実行すると同じ型解析を二重に行うからである。

リポジトリにGitHub ActionsなどのCI設定はない。
ソースコード、テスト、launchd plistは未修飾の `npm run build` を呼んでいない。
自動運用スクリプトとBun smoke testは `npm run build:bun` を明示している。

`package.json` は `private: true` であり、公開npm packageの利用者に対するscript互換性はない。
互換性の対象は、リポジトリ内の文書と開発者が記憶しているコマンドに限られる。

## 採用案

### 案A: buildをbuild:nodeへ置き換える

次のように `build` を削除し、同じ処理を `build:node` として定義する。

```json
{
  "scripts": {
    "build:node": "tsc -p tsconfig.json",
    "build:bun": "bun build ./src/index.ts --compile --outfile dist/scale2sheet",
    "typecheck": "tsc -p tsconfig.json --noEmit"
  }
}
```

未修飾の `build` は残さない。

この案を推奨する理由は、ユーザーがNode.jsビルドの名前を明示的に指定しており、`build:node` と `build:bun` を対称な名前にすると生成物をコマンド実行前に判別できるためである。
正式な配布経路がBunである状況では、未修飾の `build` をNode.js専用として残すと優先経路を誤認しやすい。

後方互換の必要性は低い。
CIと自動運用は未修飾の `build` を使っておらず、現行文書の参照箇所はすべて同じリポジトリ内で更新できる。

古い `npm run build` を実行した場合は明示的に失敗する。
この失敗によって、開発者はNode.js用の `build:node` と配布用の `build:bun` のどちらを使うか選び直せる。

## 不採用案

### 案B: build:nodeを追加し、buildをエイリアスとして残す

```json
{
  "scripts": {
    "build": "npm run build:node",
    "build:node": "tsc -p tsconfig.json"
  }
}
```

不採用理由は、既存コマンドを無期限に成功させると、文書、インストーラ、開発者の手順が未修飾の `build` を使い続けるためである。
実行環境を名前で区別するという変更目的を、互換エイリアスが弱める。

公開packageや外部CIが存在する場合は移行期間の選択肢になる。
本リポジトリでは該当する利用者とCIを確認できないため、移行期間を設ける根拠がない。

### 案C: buildをBunビルドへ変更し、Node.jsビルドをbuild:nodeとして追加する

```json
{
  "scripts": {
    "build": "npm run build:bun",
    "build:node": "tsc -p tsconfig.json"
  }
}
```

不採用理由は、既存の `npm run build && node dist/index.js` が `dist/index.js` を生成しなくなり、同じコマンド名の意味が無言で変わるためである。
これは案Bより大きな互換性破壊であり、ユーザーの要望にも未修飾の `build` をBunへ割り当てる指示は含まれていない。

### 案D: buildでNode.js出力とBunバイナリを両方生成する

不採用理由は、Node.jsだけを使う開発者にもBunを要求し、異なる用途の成果物を一つの操作へ結合するためである。
片方だけを検証したい場合にも両方のコストと失敗条件を負うため、現在の分離より扱いにくい。

READMEのlaunchdインストールは単純な改名ではない。

この箇所は既存の不整合を直し、正式な配布物を生成する `npm run build:bun` へ変更する。

### 変更しない対象

| 対象 | 理由 |
| --- | --- |
| `docs/ACCEPTANCE_TEST_REPORT.md` | commit `6367113` に対する過去の実行記録であり、当時実行したコマンドを書き換えると記録が不正確になる |
| 既存の `docs/decisions/*.md` | 過去の判断時点では `npm run build` が正しい名前だったため、履歴本文を遡及修正しない |
| `scripts/run-bun-binary-smoke.sh` | すでに `npm run build:bun` を使っている |
| `scripts/run-pipeline.sh` | ビルドを実行せず、Bunバイナリがない場合の通知も `npm run build:bun` を案内している |
| launchd plist | `scripts/run-pipeline.sh` を起動するだけで、npm scriptを参照しない |
| `tsconfig.json` | Node.jsビルドの処理内容は変えない |
| `package-lock.json` | npm script名はroot packageのlockfile情報に保存されないため、今回の改名に対応する変更はない |
| ソースコードとテストコード | npm script名への参照がない |

既存の検討書へ注記は追加しない。
本書が新しい命名判断を記録するため、過去の記録へ同じ説明を重複させる必要がない。

`docs/ACCEPTANCE_TEST_REPORT.md` は次回の受け入れテスト実施時に新しいコマンドで更新する。
今回の改名だけを理由に、過去の結果を新しいコマンドで実行したかのように書き換えない。

現行の `package-lock.json` はroot packageの名前とbinが `package.json` と一致していない。
この不整合は今回のnpm script改名より前から存在するため、npmコマンドがlockfileを再生成しても、その差分を本案件へ混在させない。

## インストーラ案件との境界

インストーラがエンドユーザー向けの正式配布物を作る場合は `npm run build:bun` を使う。
インストーラがNode.js開発環境を補助対象として扱う場合だけ `npm run build:node` を使う。
未修飾の `npm run build` は新規手順へ追加しない。

この境界をインストーラ案件のinnovatorへ共有済みである。
innovatorの目標定義に別のビルド要件が含まれる場合は、ユーザー決定前に本書へ反映する。

## 受け入れ条件

採用案の実装は、次の条件を満たす。

1. `package.json` の `scripts` に `build:node` と `build:bun` が存在し、未修飾の `build` が存在しない。
2. `npm run build:node` が成功し、`dist/index.js` を生成する。
3. `node dist/index.js --help` が成功する。
4. `npm run typecheck` が成功する。
5. `npm test` が成功する。
6. `npm run build:bun` が成功し、`dist/scale2sheet` を生成する。
7. `./scripts/run-bun-binary-smoke.sh` が成功する。
8. 現行文書のNode.js開発手順が `npm run build:node` を使う。
9. READMEのlaunchdインストール手順が `npm run build:bun` を使う。
10. 既存の検討書と過去の受け入れテスト結果は変更されない。
