# Go正本ツールチェーンとpackage.jsonの扱いについての検討書

## 背景

Issue #2 の Go ポートが main へ取り込まれた後も、ルートの `package.json` と `package-lock.json` は Node/npm の依存関係、TypeScript の build、Vitest、旧 Bun 用の説明を保持している。

現行の製品は `cmd/scale2sheet` と `internal/` の Go 実装であり、`go.mod` と `go.sum` が実際の依存関係を表す。
したがって、package.json を残したままにすると、Go アプリに Node の package metadata が必要だという誤解と、二重の依存管理経路が残る。

## 調査結果

- [Go Modules Reference](https://go.dev/ref/mod) と [go.mod file reference](https://go.dev/doc/modules/gomod-ref) は、`go.mod` を module path、依存モジュール、最低 Go バージョンの定義とする。
- [Go の依存管理](https://go.dev/doc/modules/managing-dependencies) は、依存追加・削除・整合化を `go get` と `go mod tidy` で行う。`go.sum` は依存内容の checksum を保持する。
- [Go Toolchains](https://go.dev/doc/toolchain) は、`go.mod` の `go` / `toolchain` 行と `GOTOOLCHAIN` による Go CLI の toolchain 選択を定義する。Go バージョンの CI 固定や更新方針は Issue #5 で独立に確定する。
- [GitHub の Go build/test 手順](https://docs.github.com/en/actions/tutorials/build-and-test-code/go) は `actions/setup-go` と Go CLI の `go build` / `go test` を推奨する。

現行リポジトリを確認すると、製品 README は `npm run build:go`、`npm test`、`npm run test:legacy-ts` を利用者へ提示し、`scripts/run-pipeline.sh` の失敗案内も npm を参照している。
また、`scripts/check-binary-source-drift.py` には `npx tsx` の fallback が残っている。
これらは Go 製品の既定経路から除去できる。

## 採用した案

### Go Modules と Go CLI を唯一の正本にする

次を Issue #4 の成果物とする。

- `go.mod` / `go.sum` を依存管理と checksum の正本として保持する。
- README と現行 acceptance の手順は `go build`、`go test`、`go vet`、`gofmt`、既存 shell/Python acceptance を直接呼ぶ。
- `package.json` と `package-lock.json` を削除する。
- `scripts/check-binary-source-drift.py` の Node/tsx fallback を削除し、Go 側で生成した source help を明示的に受け取る。
- 現行 `scripts/run-*.sh` の利用者向けエラー案内から npm/Bun を除去する。
- 旧 TypeScript の `src/`、`test/`、`tsconfig.json`、`vitest.config.ts` は比較履歴としてこの Issue では削除しない。将来削除または別配置する場合は別 Issue にする。
- Issue #5 の Go バージョン固定・CI 品質ゲート、Issue #6 の macOS 本番配布は本 Issue に混ぜない。

## 却下した案

### 案A: package.json を Go の wrapper として維持する

却下した理由: `npm test` や `npm run build:go` は Go の必須機能ではなく、npm の存在を開発者へ要求する。
Node の依存と旧 TypeScript の scripts が残り、Go Modules が正本であることも package metadata から判別しにくい。

### 案B: Makefile を package.json の置換として追加する

却下した理由: Make はよく使われる補助ツールだが Go の依存管理・実行に必須ではない。
この小さな CLI では `go` コマンドを README に直接記載した方が、追加の wrapper と command drift を避けられる。

### 案C: 旧 TypeScript ソース・テストも同じ PR で削除する

却下した理由: Issue #2 で比較履歴として保持する境界を定めており、資産削除は package metadata の正本化とは別の目的である。
削除の要否、履歴の残し方、docs の参照整理を別 Issue で判断できるようにする。

## 結論

Go アプリの正本として package.json は不適切であり、Go Modules と Go CLI へ置き換える。
ただし旧 TypeScript 資産の削除と Go の toolchain/CI version policy は別課題として扱う。
