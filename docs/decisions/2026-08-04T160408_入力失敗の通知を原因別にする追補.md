# 入力失敗の通知を原因別にする（案件A の追補）

検証: `scale2sheet_reviewer_claude`
決定: ユーザー

| 項目 | 値 |
| --- | --- |
| 位置づけ | 案件A（`2026-08-04T151338_…`、PR #61 マージ済み）の**追補** |
| 起点 | 実装レビューでの検出 G-3（innovator、pm が現物で確認済み） |
| 基準 HEAD | `3cbe34e` |

**本書は 2 つのことを行う。**

1. 案件A の AC-49（連続失敗と単発失敗の区別）を、**原因別の区別**まで細分化する

---

## 1. 何が起きているか

`src/pipeline/notifier.ts` は通知文面を `stage`（`input` / `transfer`）と `period` だけで作る。

```ts
const message = `${stage === "input" ? "入力" : "転記"}に失敗しました（period=${period}）`;
```

したがって **3 つの異なる失敗が、同一の文面になる。**

| outcome | 実際に起きていること | 利用者が次にすべきこと |
| --- | --- | --- |
| `failed:input-missing` | 対象日の入力ファイルが 1 本も無い | **先方（producer）側を見る** |
| `failed:input-unstable` | 読んでいる間にファイルが変化し続けた | **待つ**（次の実行で解消することが多い） |
| `failed:input-invalid-or-partial` | ファイルは在るが読めない | **ファイルの中身を見る** |

**「次に何をすればよいか」が 3 つとも違うのに、通知は同じである。**

これは #46 と同型である。#46 は「1 日目の失敗と 10 日目の失敗が同じ扱いだった」ことが問題だった。
ここでは**原因の違う 3 つの失敗が同じ扱い**になっている。

`docs/decisions/2026-08-04T152300_pipeline実装判断_status通知schema.md`（commit `9cc8612`）は
この文面を実装判断として固定している。**4 項目のうち atomic replacement と件数キーの欠落は
純粋な実装判断だが、通知文面だけは目標定義側の論点である。**
利用者の次の行動を決める情報だからである。

## 2. 選択肢

| | 案 | 内容 | 実装量 |
| --- | --- | --- | --- |
| **N-0** | 現状維持 | 段階（入力 / 転記）と period のみ | 0 |
| **N-1** | **原因を含める** | outcome ごとに文面を変える。「何が起きたか」を書く | 文面 3 本 |
| **N-2** | 原因 + 次の行動 | N-1 に加えて「次に何をすればよいか」を 1 行入れる | 文面 3 本 |
| **N-3** | 原因 + 次の行動 + 経過 | N-2 に加えて連続失敗回数を入れる（案件A の C-1 と連動） | 文面 3 本 + status 参照 |

## 3. 帰結

| 案 | #46 の 10 日連続 | 単発の unstable | 利用者が調査を始める場所 |
| --- | --- | --- | --- |
| N-0 | 10 回同じ文面。**何を見ればよいか分からない** | 同じ文面。**先方を疑ってしまう** | 不明。ログを開くしかない |
| N-1 | 「入力ファイルがありません」が 10 回 | 「読み取り中に変化しました」 | **正しい場所**（先方 / 待つ / ファイル） |
| N-2 | 同上 + 「先方の出力を確認してください」 | 同上 + 「次回の実行で解消することがあります」 | 同上 |
| N-3 | 同上 + 「4 日連続」 | 同上（連続していないので経過は出ない） | 同上。**深刻度も分かる** |

**通知が届くかどうかは、どの案でも変わらない。** これは案件A の 6.4 で確認済みである
（#46 の本質は「出ていた通知が読まれなかった」ことであり、文面の改善では閉じない）。
**本書が改善するのは「読まれたときに正しい場所へ誘導できるか」だけである。**

## 4. 推奨

**推奨は N-3。ただし N-2 との差は小さく、N-2 でも十分である。**

- N-1 で足りない理由: 「読み取り中に変化しました」だけでは、利用者は待てばよいのか
  対応が要るのか判断できない。**原因を書くことと、行動を示すことは別である**
- N-3 を推す理由: 連続失敗回数は案件A の C-1 で `pipeline-status.json` に持つと決まっており、
  **文面へ載せる追加コストがほぼ無い**。深刻度（1 日目か 4 日目か）は行動を変える
- **N-0 を採るべき条件**: 通知を廃止して `doctor` へ一本化する場合。
  案件A の決定（C-1 + C-3）は通知を残しているので、本書は N-0 を推奨しない

## 5. 合格条件

案件A の AC-49 を置き換えず、**細分化する**。番号は #63 の AC-53〜65 に続けて **AC-66** から採番する。

- **AC-66**: 入力段階の失敗通知が、`failed:input-missing` / `failed:input-unstable` /
  `failed:input-invalid-or-partial` の 3 つで**異なる文面になること**
- **AC-67**: 各文面に「次に何をすればよいか」が 1 行含まれること
  （先方の出力を確認する / 次回の実行を待つ / ファイルの内容を確認する）
- **AC-68**: 連続失敗回数が 2 回以上のとき、文面に回数が含まれること（案件A の C-1 と連動）
- **AC-69（負のコントロール）**: 3 つの outcome で**同一の文面が出ないこと**を試験で固定する。
  文面を 1 つに統合する変更が入ったら試験が落ちること

**AC-49（連続失敗と単発失敗の区別）は変更しない。** 本書はその下に原因の軸を足す。

| 軸 | 決定 | 出典 |
| --- | --- | --- |
| 段階（入力 / 転記） | 区別する | 案件A（実装済み） |
| 連続か単発か | 区別する | 案件A の AC-49 |
| **原因（3 種）** | **区別する** | **本書 AC-66** |

## 6. この追補で捕まらないもの

1. **通知が読まれないこと自体**。案件A の 6.4 のとおり本書の範囲外である
2. **転記段階の失敗の原因の区別**。`failed:transfer` は 1 つのままである。
   Sheets API の失敗の内訳（認証 / 権限 / ネットワーク）は本書で扱わない

## 9. 案件A の一次データの訂正

**案件A の目標定義（`2026-08-04T151338_…`、PR #61 でマージ済み）の基数に誤りがある。**
決定に影響しないが、正本に誤った数字を残さないために訂正する。

### 9.1 何が誤っていたか

| 箇所 | 誤 | 正 |
| --- | --- | --- |
| §2 ファイル数 | 577 | **576** |
| §2 行数 | 56,848 | **56,847** |
| §2.1 `source` の値域 | google_fit 54,780 / kappa-AppleWatchSeries11 2,030 / omron connect 32 / Xiaomi Home 5 / **apple_health 1** | google_fit 54,780 / kappa-AppleWatchSeries11 2,030 / omron connect 32 / Xiaomi Home 5（**`apple_health` は含まれない**） |
| §4.3・§8.4 の同数値 | 同上 | 同上 |

### 9.2 なぜずれたか

集計スクリプト `scripts/survey-input-corpus.py` の照合パターンが、
**production の reader と別物だった。**

```
reader.ts:38                   (apple-health|google-fit)
survey-input-corpus.py（旧）   (apple-health|apple-health-file|google-fit)
```

旧命名 `scale_exporter_2026-07-09_apple-health-file_001.jsonl`（1 行）を数えていた。
**このファイルを当方の reader は読まない。**

`reviewer_claude` が #63 の検証中に指摘し、`scale2sheet_pm_claude` が独立に検算して確認した。

**この数字は、起草者と検証者が独立に集計して一致していた。** 起草者は自作スクリプトで、
検証者は `glob("scale_exporter_*.jsonl")` で数え、どちらも 577 / 56,848 を得ていた。

> **一致は正しさの証明ではない。** 2 つの集計は独立だったが、
> **「入力ディレクトリにある `scale_exporter_*.jsonl` が当方の入力集合である」という同じ前提**を共有していた。
> 前提が共有されている限り、独立に数えても同じ誤りへ収束する。
> **突き合わせるべきだったのは互いの数字ではなく、production の `reader.ts` の照合パターンだった。**
> 独立再集計は「計算間違い」を捕まえるが、「対象の取り違え」は捕まえない。

**スクリプトの修正は PR #64（#63 の目標定義）に含まれる。** 本 PR には含めない
（同じ変更を 2 つのブランチへ入れると衝突するため）。
修正後のスクリプトは `reader.ts:38` と同じパターンを使い、
**「reader.ts:38 と同一にすること」というコメントを添えている。**

### 9.3 `apple_health` が値域から消えることの意味

**訂正の副産物として、観測された `source` の値域から `apple_health` が消える。**

`apple_health` は #59 で誤りと判明した旧契約の値である。
**その値を持つレコードは、当方が読まないファイルにしか存在しなかった。**
つまり **当方の入力集合には、旧契約の値を持つレコードが 1 件も無い。**

これは案件A の AC-50（値域を閉じる条件には実出力の集計を根拠として併記する）の
**適用例としてより正確である。** 誤った契約値が観測データに 1 件混ざっているように見えていたが、
実際には当方が読む範囲に存在しなかった。

### 9.4 結論への影響（すべて実測で確認）

| 案件A の結論 | 影響 | 根拠 |
| --- | --- | --- |
| parse 不能行 0 件（F-1） | **無し** | 除外したファイルの 1 行は正常なレコードである |
| 夜 0 件率 p = 10/36（F-3） | **無し** | 日単位の存否であり、2026-07-09 の朝の体重は google-fit 側にも存在する |
| 連続長の分布 {2 連続 4 回 / 単発 2 回}（5.3.1） | **無し** | 同上 |
| **B-3 の N = 4** | **無し** | 上記 2 つが変わらないため |
| A-1 / C-1 / C-3 の帰結 | **無し** | 件数を根拠にしていない |

**決定のやり直しは 1 件も不要である。**

### 9.5 訂正の載せ方

**案件A の文面を書き換えない。** AT-10 と同じ形を採る。

案件A の文書に **§16「一次データの訂正（2026-08-04）」** を追加し、
9.1 の表と、9.2 の原因、9.4 の影響（無し）を書く。
**当時の数字は残し、正しい数字と訂正日を併記する。**

> **教訓（起草者による記録）**: 前回の教訓は「集計スクリプトが出力しない量は検討に上がらない」だった。
> 今回は **「集計スクリプトが実装と違うものを見ていた」**である。
> 出力の有無ではなく、**入力の集合が実装と一致しているか**という一段手前の問題だった。
> **当方が『読む対象』を数えるスクリプトは、production の reader と同じ判定を使わなければならない。**
