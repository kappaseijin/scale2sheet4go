# Go開発品質ゲートとCIの採否についての検討書

## 背景とプロジェクト全体での妥当性

Issue #5 は、Go へ移植した scale2sheet を単一エージェント運用でも再現可能に保守するための開発環境の課題である。
Issue #2 の受け入れ試験は移植結果と製品動作を確認するものであり、整形、依存整合性、コンパイル、単体テスト、標準静的検査という日常的な回帰ゲートを代替しない。
したがって、ローカルと CI が同一の入口から同じ検査を実行できることは、将来の Issue の実装方法に依存しないプロジェクト全体の基盤として妥当である。

## 調査結果

- [Go command documentation](https://go.dev/doc/cmd) は `gofmt`、`go test`、`go vet`、`go build` などを Go の標準 CLI として提供している。
- [Go toolchains](https://go.dev/doc/toolchain) は `go.mod` の `go` / `toolchain` と `GOTOOLCHAIN` による toolchain 選択を定義している。現リポジトリの `go.mod` は `go 1.22` であり、CI は `actions/setup-go` の `go-version-file: go.mod` でこの宣言を読む。
- [GitHub の Go build/test 手順](https://docs.github.com/en/actions/tutorials/build-and-test-code/go) は `actions/setup-go` で Go を用意し、ローカルと同じ Go CLI で build/test する構成を案内している。
- [GitHub-hosted runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) では `macos-14` が Apple silicon の macOS runner として提供されている。現行 Go の `internal/scheduler` は Darwin 固有の lease を要求するため、Ubuntu runner では製品と同じ構成の全パッケージ検査にならない。
- [Staticcheck の getting started](https://staticcheck.dev/docs/getting-started/) と [CI guide](https://staticcheck.dev/docs/running-staticcheck/ci/) は Staticcheck を `go vet` に追加する第三者静的解析として案内している。現環境の導入済み版で実行すると、既存コードのエラー文規約、未使用コード、非推奨 API、無意味な数値検査などの指摘が残る。現時点で必須化すると Issue #5 の品質基盤整備と既存コード修正が混ざり、ツールの版・導入方法も追加管理になる。

## 現行コードから確認した制約

`internal/scheduler` の `AcquireRunLease` は、オプション未指定時に `runtime.GOOS` を使い、`darwin` 以外をエラーとして扱う。
このため CI の主 runner は Linux ではなく macOS とする。
検査コマンド自体は `CGO_ENABLED=0` と `GOTOOLCHAIN=local` を明示し、外部 C ランタイム依存と実行時の暗黙 toolchain ダウンロードを避ける。

## 採用する品質ゲート

次の順序を `scripts/check-go-quality-gates.sh` に固定し、README と GitHub Actions から同じスクリプトを呼ぶ。

1. `gofmt -l cmd internal` が空であることを確認する。整形の修正は `gofmt -w cmd internal` で行う。
2. `GOTOOLCHAIN=local go mod verify` で依存モジュールの checksum を検証する。
3. `GOTOOLCHAIN=local CGO_ENABLED=0 go test -count=1 ./...` で全パッケージをテストする。
4. `GOTOOLCHAIN=local CGO_ENABLED=0 go vet ./...` で標準静的検査を実行する。
5. `GOTOOLCHAIN=local CGO_ENABLED=0 go build -o dist/scale2sheet ./cmd/scale2sheet` で配布対象を build する。
6. Issue #4 で固定した `scripts/check-go-toolchain-contract.sh` を実行し、Go Modules/Go CLI が現行正本であることを確認する。

CI は `.github/workflows/go.yml` で `push` の `main` と `pull_request` の `main` を対象にし、`macos-14`、`actions/checkout@v6`、`actions/setup-go@v5`、`go-version-file: go.mod` を使用する。
権限は `contents: read` のみにする。

## 採用しないものと理由

### Staticcheck の必須化

今回は必須ゲートへ追加しない。
`go vet` は Go 標準のため導入経路と版管理を増やさずに CI へ置ける一方、Staticcheck は第三者ツールであり、現行コードに既存指摘がある。
まず標準ゲートを main の品質基準として固定し、Staticcheck の既存指摘を修正して導入版・実行方法・許容する既存警告を別 Issue で一つの目的として判断できる状態にする。
必要な開発者はローカルで `staticcheck ./...` を実行できるが、CI の合否には使わない。

### race detector と coverage の必須化

パイロットの標準ゲートには追加しない。
race detector は通常の `go test` より実行条件と時間が増え、coverage は閾値を決めない限り合否基準にならない。
必要性が確認できた時点で、対象範囲・閾値・macOS runner コストを明示した別 Issue に分割する。

### Linux runner の追加

追加しない。
現行コードの Darwin 固有 lease を検査できず、製品と CI のプラットフォーム契約が分かれるためである。

## 結論

Go 標準 CLI と Go Modules を品質ゲートの正本として採用し、ローカルと macOS GitHub Actions が同じ `scripts/check-go-quality-gates.sh` を実行する。
Go の最低宣言は `go.mod` の `go 1.22` とし、CI は `go-version-file: go.mod` で読み、`GOTOOLCHAIN=local` で暗黙の別 toolchain へ切り替えない。
Staticcheck、race、coverage は今回の必須経路へ追加せず、将来の独立 Issue で採否を再判断する。
