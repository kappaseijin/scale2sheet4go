## 1. サクセスストーリー

**一度スプレッドシートへ入った正しい値が、後から静かに別の値へ置き換わることがない。**
置き換わる場合は、それが訂正なのか事故なのかを人が判断できる。

## 2. 一次データ（起草時に実測、2026-08-04）

対象は本番の入力ディレクトリ `~/Dropbox/data/private/健康/scale_exporter`。
**選別規則は `src/sources/scale-exporter/reader.ts:38` の `fileNamePattern` と同一**
（`(apple-health|google-fit)`、旧命名は除外）。**576 ファイル / 36 日 / 56,847 行。**

### 2.1 再公開は通常運用で起きている

**選別規則**: 同一日・同一経路で、**2 つ以上の連番のファイルに現れた** `(measuredAt, kind)` の個数。
**単位は「測定値の数（distinct）」であり、レコードの出現件数ではない。**

| kind | 再公開された測定値の数（distinct） | **うち値が複数あったもの** |
| --- | --- | --- |
| heartRate | 111 | **53** |
| bloodPressureSystolic | 6 | **0** |
| bloodPressureDiastolic | 6 | **0** |
| **weight** | **7** | **0** |
| bodyTemperature | 1 | **0** |

> **初稿は単位を取り違えていた。** レコードの出現件数で数え、
> heartRate 119 / 血圧 9+9 / weight 9 / 体温 1 と書いていた。
> 同一ファイル内に同じキーが 2 回入っていると 1 回の再公開が 2 件に膨らむため、
> **血圧は 50% の水増しだった**（9 に対し実際は 6）。
> `reviewer_claude` の独立再集計により訂正（2026-08-04）。
> **本文の「再公開された測定値の数」という読みに合わせ、distinct を正とする。**
> スクリプトは両方の単位を出力する。

**R-1. 再公開は例外ではない。** #54 に記録された closed boundary の挙動
（対象日に既存ファイルがある状態で再実行すると末尾レコードが新連番へ再出力される）が、
実データで確認できる。

**R-2. ただし、転記に使う 5 種類のうち weight / 血圧 / 体温では、値が変わった再公開は 1 件も無い。**
**値が変わったのは heartRate の 53 件だけである。**
**heartRate は脈拍として転記対象なので、無関係ではない。**

### 2.2 producer 以外の書き手が存在する

**選別規則**: 各ファイルの `mtime` を対象日と比較。

| 指標 | 値 |
| --- | --- |
| `mtime` が対象日より後のファイル | **295 / 576（51%）** |
| うち 2026-07-28 18:13〜18:25 に集中しているもの | **約 280** |
| 対象日から `mtime` までの最大日数 | **+27 日** |

2026-07-28 の 12 分間に、06-29 から 07-28 までの広い範囲のファイルが一括で touch されている
（1 分あたり 25〜49 ファイル）。

**R-3. 入力ディレクトリは Dropbox 配下にあり、producer 以外の書き手が存在する。**
同期・復元・ディレクトリ移動のいずれでも、**producer が何もしていないのにファイルが書き換わる。**

> **正確に書く。** 実測できたのは `mtime` の変化であって、**内容の変化ではない。**
> 過去の内容が残っていないため、内容が変わったかは確認できない。
> しかし **「入力ファイルは producer だけが書く」という前提が成り立たない**ことは確定している。
> **上書きの原因を producer に限定した設計は、この経路を捕まえられない。**

### 2.3 スプレッドシートは「消える」ことがない

**選別規則**: `src/sheets/adapter.ts` の実装を読む。

- `buildMeasurementUpdateData`（155 行）は `setDefinedValue`（270 行）で
  **`undefined` の kind をマップへ入れない**
- したがって値が無い kind のセルは**更新対象に含まれず、既存の値が残る**

**R-4. 上書きで値が空になることはない。起こりうるのは「別の値へ置き換わる」ことだけである。**

> **これは案件A の 13.1 に記録した負のコントロールの前半を否定する。**
> 当時の記述は「**68.6 が消えるか**古い値へ戻る」だったが、
> **消えることはない。** 置き換わるだけである。**失敗様式が 1 つ狭まった。**

### 2.4 読み戻しに追加の権限は要らない

`src/sheets/adapter.ts` は転記のたびに `spreadsheets.values.get` を **2 回**呼んでいる
（48 行のヘッダ行、56 行の日付列）。

**R-5. 読み取り権限は既にある。** 対象行の読み戻しは `values.get` を 1 回増やすだけで、
新しい権限も新しい認証も要らない。

## 3. 何を検出したいのか（失敗様式の定義）

実測を踏まえて、検出したい事象を狭く定義する。

> **転記済みの kind の値が、同じ対象日・同じ period について、
> 前回と異なる値へ置き換わること。**

含まないもの（実測により除外）。

| 除外するもの | 理由 |
| --- | --- |
| 値が空になること | 起こらない（R-4） |
| 追加（前回無かった kind が増える） | 情報が増えるだけで失われない |
| 同じ値の再出力 | 実データで最も多い（R-1）。**これを異常とすると毎日発火する** |

## 4. 論点1: 「前回と同じか」を判定する材料

### 4.1 選択肢

| | 案 | 保持するもの | 突き合わせる相手 | 照会1 への依存 |
| --- | --- | --- | --- | --- |
| **P-0** | **検出しない** | 何も | — | 無し |
| **P-1** | **転記済み値の保持** | 転記した値と、その元になった測定の identity | 今回の転記候補 | **無し** |
| **P-2** | 入力の digest 保持 | 対象日のファイル集合の内容ハッシュ | 今回の入力 | 無し |
| **P-3** | producer の publish 世代 | `publishId` / `files[].digest` | 前回の publish 世代 | **有り（回答未着）** |
| **P-4** | **Sheets の読み戻し** | 何も（毎回読む） | スプレッドシートの現在値 | 無し |

### 4.2 帰結（何が検出でき、何ができないか）

| 案 | 検出できる | **検出できない** |
| --- | --- | --- |
| P-0 | — | すべて |
| P-1 | 当方が転記した値と異なる値を書こうとしていること | **当方以外がセルを変更した場合**（手入力の訂正など） |
| P-2 | 入力ファイル集合の内容が変わったこと | **変化が転記結果に影響するかどうか**。R-1 より毎日発火する |
| P-3 | producer が同じ対象日を再公開したこと | 同上（再公開＝異常ではない）。**加えて回答が無ければ何も検出できない** |
| P-4 | **セルの現在値と書こうとする値の差**（原因を問わず） | 差の原因（producer の訂正か、事故か、手入力か） |

**P-2 と P-3 は「入力が変わったか」を見る。** しかし R-1 のとおり入力は毎日変わる。
**「変わった」ことは異常の証拠にならない。**

**P-1 と P-4 は「転記結果が変わるか」を見る。** これは 3 節で定義した失敗様式と一致する。

### 4.3 P-1 と P-4 の違い

| | P-1（転記済み値の保持） | P-4（Sheets の読み戻し） |
| --- | --- | --- |
| 器 | **新設が要る**（#65 の status に相乗り可能） | **不要** |
| 追加コスト | ファイル 1 つの読み書き | **API 1 リクエスト**（R-5 より権限は既にある） |
| 当方以外の変更 | 検出できない | **検出できる** |
| 当方の記録が消えた場合 | 検出できなくなる | 影響なし |
| **オフラインでの判定** | できる | できない（API を叩く） |

**P-4 が構造的に強い。** 保持する状態が無いので、状態が失われる経路も無い。
そして **R-5 により追加コストが 1 リクエストしかない。**

**P-1 が従として残る理由は、P-4 だけでは区別できないものがあるからである。**

P-4 が読むのは「セルの現在値」であり、**その値を誰が書いたかは分からない。**
既存値には次の 2 つがありうる。

| 既存値の出所 | P-4 だけで分かるか | P-1 があれば分かるか |
| --- | --- | --- |
| **前回の当方の転記** | 分からない | **分かる**（`lastTransfer` と一致する） |
| **人が手で直した値** | 分からない | **分かる**（`lastTransfer` と一致しない） |

この区別は通知の文面を変える。前者なら「producer の出力が変わった」であり、
後者なら「あなたが直した値を上書きしようとしている」である。
**利用者の次の行動が違う**（G-3 の追補で入力失敗を原因別にしたのと同じ理由）。

したがって **P-1 は検出のためではなく、検出した差を説明するために持つ。**

### 4.4 推奨

**推奨は P-4（Sheets の読み戻し）を主、P-1（転記済み値の保持）を従とする。**

- 検出は P-4 で行う。**書く直前に対象セルを読み、既存値と書こうとする値を比べる**
- P-1 は記録のために持つ。#65 で決めた `pipeline-status.json` に
  **最後に転記した内容の要約**を持たせる（4.5）。**検出の根拠には使わない**

**P-3（照会1 依存）は推奨しない。** 理由は 2 つ。

1. **回答が来なくても P-4 で成立する。** 待つ理由が無い
2. 回答が来ても、**publish 世代は「再公開が起きたか」しか教えない。**
   R-1 のとおり再公開は毎日起きているので、**それ自体は異常の証拠にならない**

> **照会1 の回答が来た場合の使い道は残る。** `files[].digest` があれば、
> **入力段階で「前回読んだファイルと同一か」を安く判定できる**ので、
> P-4 の読み戻しを「入力が変わった日だけ」に絞れる。**最適化として有効だが、成立条件ではない。**

### 4.5 #65 で決めた版の仕組みとの関係

**相乗りできる。** #65 で `pipeline-status.json` にトップレベルの
`definitionsVersion` / `definitionsLabel` を持たせることが決まっている。
本書の P-1 は、同じファイルへ**最後に転記した内容の要約**を足すだけである。

```json
{
  "definitionsVersion": 2,
  "lastTransfer": {
    "targetDate": "2026-08-04",
    "period": "evening",
    "values": { "weight": 68.8, "pulse": 62 },
    "transferredAt": "2026-08-04T21:05:12+09:00"
  }
}
```

**新しい器を作らない。** これは #65 の決定が先に着地していることの利益である。

> **保持の範囲を最小にする。** 上書きが起きうるのは**同一対象日の再実行**（拾い直し）であり、
> 期間をまたがない。したがって **`(targetDate, period)` の直近 1 件だけ**あればよい。
> 履歴を持たない。

## 5. 論点2: 正当な再公開と事故をどう区別するか

**ここが本書の中心である。** 区別を誤ると、**訂正のたびに通知が出て、通知が無視される状態を新しく作る**（#46 と同じ構図）。

### 5.1 選択肢

| | 案 | 異常とみなす条件 |
| --- | --- | --- |
| **Q-1** | 差があれば異常 | 既存値と新値が異なる |
| **Q-2** | **方向で分ける** | 既存値がある kind の値が**変わる**場合のみ異常。増加（新しい kind の追加）は正常 |
| **Q-3** | 大きさで分ける | 差が測定機器の分解能を超える場合のみ異常 |
| **Q-4** | **時間で分ける** | 同一対象日の**再実行**で差が出た場合のみ異常。初回転記は常に正常 |
| **Q-5** | 人が決める | 差が出たら常に人へ問い、判断を記録する |

### 5.2 帰結（実データで示す）

観測期間 36 日で、各案が**何回発火するか**を見積もる。

| 案 | 発火回数の見積もり | 根拠 |
| --- | --- | --- |
| Q-1 | **weight / 血圧 / 体温では 0 回。heartRate だけが残る** | R-2 のとおり、値が変わった再公開は heartRate の 53 件のみ。**heartRate も、転記されるのは「体重の時刻に最も近い 1 件」なので、選ばれた 1 件が変わるとは限らない** |
| Q-2 | 0 回 | 同上。Q-1 との差は「追加」の扱いだけ |
| Q-3 | 0 回 | 同上 |
| Q-4 | 0 回 | 同上 |
| Q-5 | 0 回 | 同上 |

**5 案とも、weight / 血圧 / 体温では観測期間に 1 度も発火しない。**
**残る可能性は heartRate（脈拍）だけであり、それも発火するとは限らない**（次の注記）。 これは #63 の D-5 と同じ構図であり、
**将来の堅牢性のための機構である。「現在の取りこぼしを救う」ではない。**

> **heartRate の 53 件について正確に書く。** 同一日・同一経路で `(measuredAt, kind)` が同じで
> 値が違う再出力が 53 件ある。ただし転記されるのは
> `selectClosestToReference`（`src/domain/measurement.ts:142`）が選ぶ**体重の時刻に最も近い 1 件**である。
> **その 1 件が 53 件に含まれていたかは、当時の転記記録が無いため確認できない**（#65 の M-1）。
> **「発火 0 回」は入力データ側の見積もりであり、転記結果の実測ではない。**

### 5.3 区別の基準として何が使えるか

**実測できるものが無い以上、基準は原理から選ぶ。**

| 基準 | 使えるか | 理由 |
| --- | --- | --- |
| 値の差の大きさ（Q-3） | **使えない** | 訂正も事故も、差の大きさは同じ範囲に入る。**測定値の訂正は必ず分解能を超える** |
| 変化の方向（Q-2） | **部分的に使える** | 「増える（kind が追加される）」は情報が失われないので安全。**値の置換だけを異常候補にできる** |
| 時間（Q-4） | **使える** | 初回転記は比較対象が無いので常に正常。**異常候補は再実行時に限られる** |
| producer の意図 | **使えない** | 当方からは観測できない。照会1 の回答が来ても「再公開した」しか分からない |

**Q-2 と Q-4 は組み合わせられる。** 両方を満たすとき（再実行、かつ既存値の置換）だけを異常候補とする。

### 5.4 推奨

**推奨は Q-2 + Q-4。**

異常候補の定義:

> **同一対象日・同一 period の再実行で、既にセルに値がある kind について、
> 異なる値を書こうとしたとき。**

- 初回の転記は常に正常（Q-4）
- kind の追加は常に正常（Q-2）
- **同じ値の再書き込みは正常**（R-1 のとおり毎日起きる）

**Q-1（差があれば異常）を推奨しない理由**: kind の追加まで異常になる。
**Q-5（常に人へ問う）を推奨しない理由**: 判断の頻度が読めない。**発火 0 回の機構に人の判断を組み込むと、
初めて発火したときに手順が忘れられている。**

## 6. 論点3: 検出したときにどうするか

### 6.1 選択肢

| | 案 | 挙動 |
| --- | --- | --- |
| **S-1** | 上書きして通知 | 新しい値で上書きし、変更を通知する |
| **S-2** | **上書きせず通知** | 既存値を残し、差異を通知する。**人が判断して手で直す** |
| **S-3** | 上書きせず失敗 | `failed:transfer` として exit 1。次回も同じ結果になる |
| **S-4** | 両方書く | 別の列やコメントへ新値を書き、既存値は残す |

### 6.2 帰結

| 案 | producer が正しく訂正した場合 | 事故で壊れた値が来た場合 |
| --- | --- | --- |
| S-1 | **訂正が反映される**（望ましい） | **正しい値が失われる**（望ましくない） |
| S-2 | 訂正が反映されない。人が手で直す | **正しい値が守られる** |
| S-3 | 同上。加えて**毎回失敗し続ける**（次回も差があるため） | 守られる。ただし失敗が続く |
| S-4 | 両方残る。**スプレッドシートの構造を変える必要がある** | 守られる |

**S-3 は同じ失敗を繰り返す。** 差は次回も存在するので、`failed:transfer` が続き、
案件A の C-1（連続失敗回数）が増え続ける。**訂正されるまで通知が鳴り続ける。**

**S-4 はスプレッドシートの構造変更を伴う。** 転記先は利用者が日々見る表であり、
**列を増やすのは本書の範囲を超える。**

### 6.3 推奨

**推奨は S-2（上書きせず通知）。**

- **復旧コストの非対称性で決める。** 正しい値が失われた場合、**元の値はどこにも残っていない**
  （producer 側も上書き済みかもしれない）。一方、訂正が反映されない場合は**手で直せる**
- 通知には**既存値と新値の両方**を含める。人はそれだけで判断できる（AC-80）
- outcome は `completed:transferred` でも `failed:transfer` でもない。**新設せずに済ませる**（6.4）

### 6.4 outcome の扱い

案件A で決まった outcome 集合を変えない。

| 状況 | outcome | exit |
| --- | --- | --- |
| 差があり、上書きを見送った | **`completed:transferred`** | 0 |
| 差が無い、または初回 | `completed:transferred` | 0 |

**見送りを失敗として扱わない。** 転記処理そのものは正常に完了しており、
**判断を人へ渡しただけ**である。S-3 を採らない理由と同じで、
**失敗にすると連続失敗回数が増え続けて #46 と同じ構図になる。**

代わりに `pipeline-status.json` へ **`overwriteDeclined`** を記録する（AC-81）。
`doctor` がこれを報告する。

## 7. 現状維持（P-0）が成立する条件

**成立する。** 次の 2 点を認める場合。

**(1) 実例が 1 件も無い。**
36 日の観測で、転記に使う kind の値が変わった再出力は 0 件である（R-2）。
案件A の 13.1 で範囲外にしたのも、**理屈上の穴だと判断したから**である。

**(2) 起きても気づける可能性がある。**
転記先は利用者が日々見る表であり、**体重が明らかにおかしければ人が気づく。**
自動検出が唯一の防衛線ではない。

**ただし (2) には限界がある。** 置き換わる値は「もっともらしい値」である可能性が高い
（同じ測定の別サンプル、あるいは別時刻の測定）。**68.8 が 69.4 になっても人は気づかない。**

**P-0 を選んだ場合に残るもの**: heartRate の 53 件（値が変わった再公開）のうち、
**実際に転記された 1 件が含まれた日があったかどうかは、永久に分からない。**
当時の転記記録が無く（#65 の M-1）、本書の実装が入らなければ今後も残らないためである。

**(1) を根拠に「いまはやらない」と決めるのは筋が通る。** その場合、
**#66 の命名不一致や #63 の同一性と同じく「将来の堅牢性」の列に置いて、優先度で並べればよい。**

## 9. 合格条件

#65 の AC-70〜76 に続けて **AC-77** から採番する。

- **AC-77**: 転記の直前に対象行の対象セルを読み、**既存値と書こうとする値を比較すること**。
  **読みと書きは同一の row / column 解決結果を使うこと**（別々に解決しないこと）。
  別々に解決すると、誤った行を指したときに読みと書きが別々の行を指す（10 節の 6）
- **AC-78**: 既にセルに値があり、**書こうとする値と異なる場合、上書きしないこと**。
  **試験は「上書きしないと判断したこと」ではなく、
  実際にセルが変化していないことを読み戻しで確認するまで含めること**
- **AC-79**: 値が無いセルへの書き込みと、**同じ値の再書き込みは、通常どおり行うこと**
  （R-1 より、同じ値の再書き込みは日常的に起きる）
- **AC-80**: 上書きを見送ったとき、**既存値と新値の両方**、および
  **どの kind・どの period・どの対象日か**を含む通知を出すこと。人が通知だけで判断できること。
  さらに、既存値が `lastTransfer` と一致するか（＝前回の当方の転記か、人の手入力か）を
  **文面で区別すること**（4.3）
- **AC-81**: 上書きを見送ったことを `pipeline-status.json` に記録し、`doctor` が報告すること。
  **outcome は `completed:transferred` のままとし、失敗として扱わないこと**
- **AC-82（負のコントロール）**: 次の 3 つが**発火しない**ことを試験で固定する。
  1. 初回の転記（比較対象が無い）
  2. 同じ値の再書き込み
  3. 値が無かった kind への追加
- **AC-83（負のコントロール）**: 既存値と 1 目盛だけ異なる値（体重 0.1 kg 差）で**発火すること**。
  **差の大きさで見逃さないこと**（5.3 のとおり、訂正も事故も差の大きさは同じ範囲に入る）
- **AC-84**: `pipeline-status.json` の `lastTransfer` は `(targetDate, period)` の直近 1 件のみとし、
  **履歴を持たないこと**。
  **`(targetDate, period)` が変わったとき、前の記録が消えることを試験で固定すること。**
  消えなければ事実上の履歴になり、本条件が空文化する

## 10. この定義では捕まらないもの（範囲外の明示）

1. **当方が転記した後、人が手で直した値を、次回の転記が上書きすること。**
   P-4 は「セルの現在値」と比べるので、**手入力の訂正も「既存値」として保護される。**
   これは意図した挙動だが、**逆に言えば手入力を「正しい」と仮定している**
2. **producer 側で値が壊れ、それが初回転記で入る場合。** 比較対象が無いので検出できない。
   これは入力段階の値の妥当性の問題であり、案件A の 13.2 で範囲外としたもの
3. **転記後にスプレッドシート側で失われた値。** 当方は書く直前しか見ない
4. **Dropbox の同期・復元による入力の書き換え**（R-3）。
   **本書の検出は転記結果の比較なので、原因が producer でも Dropbox でも同じように検出できる。**
   ただし**原因の切り分けはできない**
5. **転記先そのものがずれる失敗（値は健全で座標が壊れている）**
   （`reviewer_claude` 提示の負のコントロール NC-1、2026-08-04）

   **本書の保護は「既にセルに値がある」場合しか働かない。**
   AC-79 が「値が無いセルへの書き込みは通常どおり行う」と定め、
   AC-82 の 1 と 3 がそれを**発火してはならない**として固定する。
   **この 2 つの条件が、空のセルへ着地する失敗に対する穴を明示的に作っている。**

   ```
   対象日が 1 日ずれる（TIME_ZONE の相違、または日付をまたぐ遅延起動）
     → findTodayRowNumber が別の日の行を返す
     → その行のその period は空
     → AC-79 により通常どおり書かれ、AC-82.1 により発火しない
     → outcome は completed:transferred、lastTransfer にも整合した記録が残る
   ```

   period の取り違え（morning のデータが evening 列へ）も同じ構図である。
   **`targetDate` は `resolvePipelineSettings` の timeZone で決まり、
   環境変数 `TIME_ZONE` が `settings.json` より優先される。**

   さらに悪いことに、**`lastTransfer` は「ずれた側」を正として記録する**ので、
   次回以降の比較も汚染される。

   **本書の範囲外とする。** 本書は「同じ座標に別の値が来たか」を扱い、
   **座標が正しいかは扱わない。** ただし上記のとおり、
   **AC-79 と AC-82 がこの穴を明示的に作っている**ことを認めたうえで範囲外とする。
   §10.2（初回転記で壊れた値が入る）とは別物である。あちらは**値が壊れている**話、
   こちらは**値は健全で座標が壊れている**話である。

6. **行の同定が誤ったとき、読み戻しが自己整合すること**
   （`reviewer_claude` 提示の負のコントロール NC-2、2026-08-04）

   `findTodayRowNumber`（`src/sheets/adapter.ts:138-153`）は条件に合う**最初の行**を返す。
   同じ日付の行が 2 つあれば常に先頭である。

   **P-4 は「これから書く行のセル」を読んで比べるので、行の選択が誤っていても
   読みと書きが同じ誤った行を指し、比較は必ず整合する。**
   **読み戻しは「書く場所が正しいか」を一切検証しない。**

   これは P-4 の構造的な限界であり、読み戻しの回数を増やしても解決しない。
   **範囲外とする。** ただし実装では、
   **読みと書きが同一の row/column 解決結果を使うこと**を条件とする（AC-77）。
   別々に解決すると、NC-2 が「同じ誤った行を見る」ではなく
   「別々の誤った行を見る」に悪化する。

7. **heartRate の選択が変わったかどうか。** 5.2 のとおり、53 件のうち転記対象が含まれていたかは
   当時の転記記録が無いため確認できない。**本書の実装後は `lastTransfer` に残るので、
   次回以降は確認できるようになる**

## 11. 推奨のまとめ

| 論点 | 推奨 | 主たる根拠 |
| --- | --- | --- |
| 1. 判定材料 | **P-4（Sheets の読み戻し）を主、P-1（転記済み値の記録）を従** | 読み取り権限は既にあり、追加コストは 1 リクエスト（R-5）。保持する状態が無いので失われる経路も無い |
| 2. 正当な訂正との区別 | **Q-2 + Q-4**（再実行、かつ既存値の置換のみ異常候補） | 同じ値の再出力は毎日起きる（R-1）。これを異常とすると #46 と同じ構図を新しく作る |
| 3. 検出時の挙動 | **S-2（上書きせず通知）** | 復旧コストの非対称性。失われた値は戻らないが、反映されなかった訂正は手で直せる |
| 照会1 | **依存しない** | 回答が来ても「再公開が起きた」しか分からず、それは異常の証拠にならない |
| 現状維持 | **成立する**（7 節） | 実例 0 件。ただし「もっともらしい値」への置換は人が気づけない |

**この案件は「将来の堅牢性」の列に属する。** 観測期間で 1 度も発火しない（5.2）。
**#63 の D-5 と同じ性質であり、優先度は他の案件と並べて決めるべきである。**
