# Bun CLI化についての検討書

## 背景

scale2sheetは現在Node.js（>= 22）専用のTypeScript CLIアプリである（`npm install` → `tsc`ビルド → `node dist/index.js`）。ユーザーから「Node.jsアプリであることを保ちつつ、Bunで動くCLIアプリにできるか」という要望があった。

「Node.jsアプリであることを保つ」を制約として明確化すると、以下を満たす必要がある。

- `npm install && npm run build && node dist/index.js` という既存の利用方法・launchd運用（`scripts/run-pipeline.sh`, `scripts/launchd/*.plist`）を後退させない
- ソースコードはNode.js専用API（`Bun.file`、`Bun.serve`等）に依存させず、Node.js上でも動き続ける
- Node.jsが第一級（primary）の実行環境であり続け、Bunはあくまで追加の選択肢とする

その上で「Bunで動くCLIアプリ」を何によって実現するかが検討対象。

## 採用した案

**案A: Bunをビルド専用ツールとして追加し、`bun build --compile`でOS依存のない単一実行バイナリを生成する。npm/node経路は完全に現状維持し、Bun経路は追加のオプションとする。**

具体的には次を追加する。

- `package.json`に`build:bun`スクリプトを追加: `bun build ./src/index.ts --compile --outfile dist/scale2sheet-bun`
- 開発時の簡易確認用に、コンパイルせず`bun run src/index.ts`でソースを直接実行する経路も補助的にサポートする（ビルド不要でBun互換性を素早く確認できるため）
- README/PLAN.mdにBun版のインストール手順・既知の検証ポイント（後述のリスク）を追記する
- 既存の`npm run build`・`node dist/index.js`・launchd運用には一切手を入れない

採用理由:

- ユーザーの要求「Node.jsアプリであることを保ちつつ」を最も素直に満たす。Node.js経路に変更が入らないため、既存のlaunchd自動実行・README記載手順・受け入れテスト（AT-01〜AT-18）への影響がゼロ
- Bunは高いNode.js API互換性を持ち、本プロジェクトの依存（commander, googleapis, luxon, zod, saxes, node-cron, pino）はいずれも純JSでネイティブバインディングを持たないため、コード変更なしでBun実行に載る可能性が高い
- `--compile`による単体実行ファイルは「Bunの**CLIアプリ**」という言葉に最も直接対応する成果物であり、Node/npmが入っていない環境でも配布・実行できるという明確な価値を持つ

残存リスク（実装フェーズで検証が必要、計画書のフェーズ計画に記載）:

- `googleapis`はAPI面が大きいSDKであり、`bun build --compile`のバンドル・コンパイル過程で動的requireや遅延読み込みに起因する問題が起きないか実機確認が必要
- `node-cron`・`saxes`はネイティブ依存を持たない純JSのため問題は起きにくいと想定されるが、念のため既存のvitestスイートをBunランタイム上でも実行して確認する

## 却下した案

### 案B: プロジェクトの主要な実行・開発フローをBunへ置き換える（`bun install`・`bun run`を標準にし、tscビルドを廃止。Node実行は互換性維持のみの位置づけにする）

却下した理由: ユーザーが明示的に「Node.jsアプリであることを保ちつつ」と要求しており、Node.jsを従属的な「互換性のみ」の位置づけに落とすのはこの制約に反する。また`scripts/run-pipeline.sh`・`scripts/launchd/*.plist`・README・受け入れテスト設計書など、`node dist/index.js`を前提にした既存ドキュメント・運用への影響範囲が広く、変更コストとレビュー負荷が高い。

### 案C: Node版とBun版で実装そのものを分岐させる（Bun専用API（`Bun.file`等）を使ったアダプタ層を用意し、ランタイムごとに最適化した実装を持つ）

却下した理由: 「Bunでも動くCLIにする」というユーザーの要求に対して過剰な複雑さを持ち込む。単一実行バイナリの配布という目的は、既存コードをそのままBunでビルドするだけで達成できる可能性が高く、ランタイム分岐を今の時点で持ち込む必要性がない。将来Bun固有APIでの最適化が必要になった場合に改めて検討する。

### 案D: `bun run src/index.ts`によるソース直接実行のみをサポートし、`--compile`による単体バイナリ化は行わない

却下した理由（単独案としては）: 開発時の動作確認には有用だが、「Bunの**CLIアプリ**」という言葉が示す配布可能な成果物としては弱い。ただし低コストであるため、案Aの補助的な検証手段として採用案に含めた（却下ではなく統合）。
