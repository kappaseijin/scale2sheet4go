# デスクトップとメニューバーへの常設状態表示

検証: `scale2sheet_reviewer_claude`

| 項目 | 値 |
| --- | --- |
| 起点 | Issue #46、U-1 の経路設計 |
| ユーザー回答 | 利用者が毎日見る場所は端末のデスクトップまたはメニューバー |

## 1. 結論

**推奨は M-1、native menu bar app である。**

SwiftUI の `MenuBarExtra` を持つ menu helper を macOS app bundle に内包し、user login item として登録する。
helper は versioned な `pipeline-status.json` を read-only で読む。
メニューバーには正常時も `S2S ✓` のような短い表示を残し、異常時だけ現れる表示にはしない。
表示の詳細では morning と evening を分け、最後の `done` と最後の転記を別々に示す。

表示 app は status の置換を契機に再読込するだけでは足りない。
pipeline が起動しない場合にも時刻は進むため、壁時計 timer と sleep 復帰を契機に再判定する。
ファイル変更の監視は表示を早める補助であり、正しさは bounded timer が担う。

この推奨には、**2026-07-29 にユーザーが決めた「配布物はバイナリ1つ、監視用の別 job を増やさない」への明示的な例外**が要る。
メニューバー項目は実行中の GUI process が所有するため、この既決定を保ったまま当方所有の常設表示を作ることはできない。
例外を採らない場合、M-4 の SwiftBar または xbar という外部常駐 app へ依存するか、U-0 を受け入れる必要がある。

desktop widget は M-1 の補助にはなるが、production の唯一の経路にはしない。
desktop file は内容が常時見えず、pipeline が止まったとき自力で更新できないため採らない。

## 2. 固定する前提

本書は Issue #46 で採用済みの次の決定を変更しない。

| 論点 | 固定する内容 |
| --- | --- |
| 判定材料 | T-1 の status を主、T-3 の Sheets 読み戻しを従とする。T-3 は U-3 の `doctor` が担う |
| 観測軸 | V-3 を主、V-1 を従とする |
| `done` | pipeline の完了であり、転記成功を意味しない |
| V-3 | 実行時に window 内の体重があり、転記しなかった実行は1回で異常 |
| V-1 | 最後の `done` から2日以上を異常とする |
| 通知 | alert 状態が変わったときだけ出し、同じ異常の継続中は繰り返さない |
| 能動照会 | U-3 の `doctor` を残す |
| Slice 境界 | status の器を先に入れ、U-1 の表示経路は Slice 6 で作る |

2026-08-04 19:46 JST の実測では、`~/.config/scale2sheet/pipeline-status.json` は存在しなかった。
production CLI に pipeline subcommand がまだ無いためである。
したがって表示 app の初回状態は「正常」ではなく「未観測」でなければならない。

## 3. platform の事実

### 3.1 メニューバー

Apple は [`MenuBarExtra`](https://developer.apple.com/documentation/swiftui/menubarextra) を、app が active でないときも system menu bar に残る persistent control と定義している。
window を持たず、メニューバーだけを表示する utility app も構成できる。
一方、menu bar extra を利用者が取り除いた場合、menu bar only app は自動終了し得る。

AppKit の [`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem) も system menu bar に個別 item を置ける。
macOS 13 以降だけを対象にできる現在の端末では `MenuBarExtra` を第一選択とし、より低い deployment target が必要な場合だけ `NSStatusItem` を再検討する。

メニューバー項目は process なしでは存在できない。
したがって M-1 は常駐 process を要する。

### 3.2 login item と再起動

Apple は macOS 13 以降の login item と LaunchAgent の登録に [`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice) を使うよう案内している。
user は System Settings の Login Items で提供元と許可状態を確認できる。

[`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29) の契約では、`SMAppService.loginItem(identifier:)` で登録した login item は登録直後と次回以降の login 時に起動し、crash または nonzero exit 後は system が再起動する。
これは process crash への回復を与えるが、利用者が明示的に終了または無効化した場合、app bundle が消えた場合、署名または実行権限が壊れた場合まで別経路で通知するものではない。

Apple は menu bar extra のような補助 UI を LaunchAgent の用途としても例示している。
ただし本書では raw plist や別の LaunchAgent を重ねない。
[Apple の helper 更新ガイド](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos)に沿って、配布用 app bundle の `Contents/Library/LoginItems` に一つの menu helper app を内包し、host app から `SMAppService.loginItem(identifier:)` でその helper だけを登録する。

### 3.3 desktop widget

Apple の [`WidgetKit`](https://developer.apple.com/documentation/widgetkit/) は macOS desktop と Notification Center に glanceable content を置ける。
ただし widget extension は画面に表示中でも常時 active ではなく、別 process で system が描画する。

Apple の [widget 更新ガイド](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date) では、更新は timeline と system の budget に従う。
典型的な budget は1日40〜70回、概ね15〜60分間隔であり、timeline entry は少なくとも約5分離すことが求められる。
よって1日または2日の閾値を表示するには使えるが、status 置換直後の更新時刻を当方が保証できない。

desktop widget は user が desktop へ追加する操作も要る。
window が desktop を覆う場合、利用者がその状態を常時見るとは限らない。

### 3.4 既存ツールへの相乗り

[`SwiftBar`](https://github.com/swiftbar/SwiftBar) と [`xbar`](https://github.com/matryer/xbar) は、script または program の標準出力を macOS menu bar へ置く既存 app である。
SwiftBar は plugin 名に refresh interval を持たせられ、xbar も同じ plugin 形式を扱う。

この案では当方が書くものを read-only の表示 command に絞れる。
一方で第三者 app の導入、login 時の起動、plugin folder、更新、停止時の復旧は当方の installer の外に残る。

### 3.5 launchd の時刻とファイル監視

macOS 26.6（build 25G72）に同梱された `launchd.plist(5)` は、`StartInterval` が sleep 中の発火を取り逃すことを明記している。
同じ system manual は `WatchPaths` と `PathState` の file-system monitoring を race-prone かつ lossy とし、変更を取り逃し得ると警告している。
根拠は `MANWIDTH=160 man 5 launchd.plist | col -b` の `StartInterval`、`WatchPaths`、`PathState` 節で再現できる。

したがって「status が書き換わったときだけ起動する短命 process」は本件の正本にしない。
常駐 app の file event も補助にとどめ、wall-clock timer と wake 後の再判定を必須にする。

## 4. 選択肢

| 案 | 表示場所 | 当方から書けるもの | 常駐 | pipeline 停止中の時刻更新 | 主な弱点 |
| --- | --- | --- | --- | --- | --- |
| M-0 | 無し | 現行通知だけ | 無し | 無し | 60回以上の通知が行動につながらなかった実績を繰り返す |
| M-1 | menu bar | native app bundle、menu helper、status reader、通知 receipt、login item 登録 | 必要 | できる | pipeline binary 以外の bundle と常駐 process が要る |
| M-2 | Mac desktop widget | app extension、timeline provider | project process は常駐しない | system timeline の範囲でできる | user の配置が必要、更新時刻を保証できない、window に覆われる |
| M-3 | Desktop の file | file 名または内容 | pipeline 更新だけなら不要 | できない | 内容が常時見えず、pipeline 不起動を検出するには結局別 job が要る |
| M-4 | menu bar | SwiftBar / xbar plugin または表示 command | 第三者 app が必要 | plugin interval でできる | 外部依存の停止と設定を当方だけで閉じられない |

### 4.1 M-1 native menu bar app

**production の推奨である。**

状態を読む code、壁時計による判定、表示、状態遷移通知を一つの process に閉じられる。
同じ評価結果から menu bar と通知を作るため、表示と通知が別の状態を告げる経路を作らずに済む。

利用者は app の存在を menu bar の正常表示で毎日確認できる。
process が無くなれば item も無くなるため、正常表示そのものが表示機構の heartbeat になる。

ただし icon の不在を、停止した app 自身が通知することはできない。
system の login item 再起動を一段目、正常 icon の不在を人が気づく二段目とし、第三の watchdog は置かない。
watchdog を増やすと、その watchdog の停止を誰が監視するかという同じ問題が再帰するためである。

### 4.2 M-2 desktop widget

M-1 の補助表示としては成立する。
大きい表示で最後の転記時刻と period ごとの状態を示しやすい。
相対時刻の表示は extension が実行中でなくても system が更新できる。

production の唯一の経路にはしない。
user が widget を置かなければ存在せず、system の refresh budget により status 更新直後の反映を保証できないためである。

### 4.3 M-3 desktop file

採らない。

file の内容は desktop icon だけでは読めない。
状態を file 名へ埋め込んでも、pipeline が止まれば「正常」の file 名が残り続ける。
別の launchd job で定期的に rename すれば時刻更新はできるが、それは表示の弱い M-1 を別 process で作ることになる。

### 4.4 M-4 SwiftBar / xbar

prototype または利用者が既に当該 app を常用している場合の移行案として成立する。
plugin は60秒または5分ごとに status 表示 command を実行し、menu bar の title と dropdown を作れる。

production の標準経路にはしない。
第三者 app の導入と自動起動が新しい成立条件になり、app が停止すると icon が消える限界も M-1 と同じだからである。

### 4.5 M-0 現状維持

次をすべて受け入れる場合だけ成立する。

1. 10日程度の転記停止に実害が無い。
2. 33日のうち evening 18日、morning 16日が全滅した状態が今後も続いてよい。
3. 60回以上の通知が行動につながらなかった実績を許容する。
4. 障害は別件の調査で偶然見つかるまで分からなくてよい。

これは Issue #46 のサクセスストーリー「止まったら人が気づく」を達成しない。

## 5. M-1 の構成

```text
pipeline
  │ atomic replace
  ▼
pipeline-status.json
  │
  ├─ directory file event ─────┐
  ├─ wall-clock timer ─────────┤
  └─ wake / app restart ───────┤
                               ▼
                    read-only state evaluator
                      │                 │
                      ▼                 ▼
               persistent menu     transition notifier
                                         │
                                         ▼
                              indicator-notification.json
```

### 5.1 artifact と登録

`scale2sheet-status.app` を user local の署名済み app bundle として配布する。
この bundle は登録を担う host と、`Contents/Library/LoginItems/scale2sheet-status-menu.app` に内包した menu helper を持つ。
常駐するのは helper だけであり、helper は Dock と application switcher に出ず、`MenuBarExtra` だけを持つ。

host は `SMAppService.loginItem(identifier:)` で内包 helper を一つだけ登録する。
installer は user の明示的な opt-in を得て host の登録処理を呼び、System Settings で approval が必要ならその状態を明示する。
uninstaller は host の解除処理で helper を unregister し、その後に app bundle と notification receipt を除去する。
測定結果と `pipeline-status.json` は既存の data preservation 方針に従って残す。

一つの `.app` として配送しても、内部には host と helper の複数 executable がある。
したがって現在の「配布物は compiled Bun binary 一つ」という決定を変更する。
実装着手前に、U-1 の UI artifact に限る例外としてユーザーが採否を決める必要がある。

### 5.2 read-only 境界

app は次のものだけを読む。

- versioned な `pipeline-status.json`
- 自分が最後に評価した表示状態と通知済み遷移を持つ `indicator-notification.json`

app は Google Sheets、producer、network、credential、測定値へアクセスしない。
T-3 の直接的な Sheets 読み戻しは U-3 の `doctor` または pipeline 側の責務に残す。
menu bar は pipeline が実行時に status へ記録した「入力に window 内の体重があったか」「実際に転記したか」を使う。

notification receipt は status と別 file にし、status の single writer を崩さない。
receipt は mode `0600` の atomic replacement とし、secret、Spreadsheet ID、測定値を入れない。

### 5.3 状態モデル

period ごとに次の4状態を持つ。

| 状態 | 条件 | menu bar | 通知対象 |
| --- | --- | --- | --- |
| `unobserved` | 有効な終端 status を一度も得ていない | `? 未観測` | 対象外。初回を異常にしない |
| `healthy` | version が読め、V-3 と V-1 のいずれも正常 | `✓ 正常` | alert 状態から戻ったときだけ recovery |
| `anomalous` | V-3 が成立、または V-1 の2日閾値を超過 | `! 要確認` | 別状態から入った遷移時だけ alert |
| `status-unavailable` | 以前は読めた status が消失、破損、未知 version、必要 field 欠落 | `× 状態不明` | 別状態から入った遷移時だけ alert |

`unobserved` と `status-unavailable` を分ける。
production status がまだ一度も無い導入直後を、破損や停止と同じ異常にしないためである。
一度でも有効な status を読んだ後の消失は `unobserved` へ戻さず、`status-unavailable` とする。

overall state は morning と evening の worst state を取る。
優先順位は `status-unavailable > anomalous > unobserved > healthy` とする。
片方だけ健康でも、もう片方が異常または未観測なら overall を健康にしない。

### 5.4 表示

menu bar label は正常時も常に存在する。

| overall | label 例 | accessibility label |
| --- | --- | --- |
| `healthy` | `S2S ✓` | scale2sheet 正常 |
| `unobserved` | `S2S ?` | scale2sheet 未観測 |
| `anomalous` | `S2S !` | scale2sheet 要確認 |
| `status-unavailable` | `S2S ×` | scale2sheet 状態不明 |

色だけで状態を伝えず、symbol と text を併用する。
menu を開くと次を表示する。

- overall state と判定時刻
- morning と evening の state
- period ごとの最後の `done`
- period ごとの最後の転記
- V-3 が異常なら、対象日と「window 内の体重あり、転記なし」
- V-1 が異常なら、最後の `done` からの経過時間と2日閾値
- status の `definitionsVersion`
- `doctor` を実行するための導線

測定値そのものは表示しない。

### 5.5 更新契機

次の三つを併用する。

1. status の atomic replacement を directory event で観測し、速やかに再読込する。
2. 少なくとも60秒ごとの wall-clock timer で再評価する。
3. sleep 復帰と app restart の直後に再評価する。

directory event を取り逃しても timer で回復する。
pipeline が最後に健康な status を書いた後に停止しても、file 変更なしで V-1 の2日閾値を越えて `anomalous` へ変わる。

端末が sleep または shutdown 中は表示も通知もできない。
復帰後60秒以内に現在時刻から再計算し、sleep 中に越えた閾値を反映する。

### 5.6 通知

通知は補助であり、menu bar の代替ではない。

通知対象の state machine は durable receipt に保存する。
同じ `anomalous` が続く間は、pipeline 実行、timer、app restart の回数にかかわらず再通知しない。
`anomalous` から `healthy` へ戻ったときは recovery を1回通知する。
`status-unavailable` との間の遷移も別 state change として1回だけ通知する。

| 前回 state | 今回 state | 通知 |
| --- | --- | --- |
| receipt 無し | 任意 | 無し。今回 state を baseline として保存 |
| `unobserved` | `healthy` | 無し。最初の正常観測として保存 |
| `healthy` / `unobserved` | `anomalous` / `status-unavailable` | alert を1回 |
| `anomalous` / `status-unavailable` | `healthy` | recovery を1回 |
| `anomalous` | `status-unavailable`、または逆 | 変化後の alert を1回 |
| 同じ state | 同じ state | 無し |

receipt が無い初回起動では現在 state を baseline とし、通知しない。
初回が異常でも常設表示には現れるため、過去の state が無いのに「変化した」と偽らない。

notification permission が拒否されても menu bar の状態表示は継続する。

### 5.7 常駐 app 自身の停止

system が crash または nonzero exit 後に app を再起動することを第一の防御とする。
再起動後は現在の status と receipt を読み、同じ異常通知を繰り返さない。

次は検出できない。

- user が login item を無効化した
- user が menu bar item を削除または app を明示終了した
- app bundle が削除または実行不能になった
- user session が無い
- 端末が sleep または shutdown 中である

これらの場合、正常時にも存在する menu bar item が消える。
item の不在を利用者が見て気づくことが、この host 内で置ける最後の検出境界である。
別 watchdog は置かず、完全な自己監視を保証しない。

`doctor` は app bundle と内包 helper の存在、login item の登録と authorization state、status の読取可否を能動照会できるようにする。
ただし `doctor` 自身を実行しなければ気づけない限界は残る。

## 6. 既存決定との衝突

[2026-07-29 のインストーラ目標定義](2026-07-29T084808_インストーラとアンインストーラの目標定義.md)は、次をユーザー決定として固定した。

- launchd は compiled Bun binary を直接起動する
- shell launcher を持たない
- 配布物は binary 一つを維持する
- 監視用の別 job を増やさない
- binary 欠落時の自動検出手段を用意しない

M-1 はこのうち「配布物は binary 一つ」と「監視用の別 job を増やさない」に抵触する。
抵触を隠して既存決定と両立するものとして実装してはならない。

選択肢は三つである。

| 選択 | 帰結 |
| --- | --- |
| R-1 | U-1 の UI に限って既存決定へ例外を設け、host と menu helper を含む native app bundle と login item を認める。**推奨** |
| R-2 | 既存決定を保ち、利用者が導入した SwiftBar / xbar を成立条件にする |
| R-0 | 既存決定を保ち、U-1 を作らず U-0 を受け入れる |

R-1 は pipeline の実行経路を helper 経由へ戻すものではない。
pipeline は引き続き compiled Bun binary を直接起動し、UI app は status を read-only で読むだけである。
例外の範囲を UI artifact とその login item に限定する。

## 7. 検証境界

### 7.1 自動検証

次は macOS UI または実 launchd を使わず自動検証する。

- versioned status fixture と fake clock による4状態の判定
- morning と evening の worst state 集約
- `done` と転記の取り違えが無いこと
- file event、timer、wake を port 化した更新 controller
- healthy status を最後に書いたまま pipeline を止め、clock だけ2日進める負のコントロール
- 同じ異常で timer と restart を繰り返しても通知要求が1回であること
- receipt の mode `0600` と atomic replacement
- status、network、Sheets、credential への read / write port が UI app に無いこと
- installer と uninstaller が登録、解除、配置の引数を組み立てること

### 7.2 代理指標

app bundle の host と内包 helper、両方の `Info.plist` と署名対象、helper の `LSUIElement`、ServiceManagement 登録対象を静的に検査する。
実 user の Login Items を自動テストで変更しない。

### 7.3 手動検証

本番と衝突しない test bundle identifier を使い、次を手動で確認する。

- `unobserved`、`healthy`、`anomalous`、`status-unavailable` の全状態で item が表示される
- 色を使わなくても symbol と accessibility label で区別できる
- nonzero exit 後に system が app を再起動し、bounded time 内に item が戻る
- sleep 復帰後60秒以内に閾値が再評価される
- System Settings で login item を無効化すると item が消え、再有効化で戻る
- notification permission を拒否しても item が残る

手動確認は `docs/ACCEPTANCE_TEST_REPORT.md` に記録する。

## 8. 合格条件

### 8.1 production 経路と表示

- **AC-110**: production の U-1 経路として M-1 を採る場合、host と `MenuBarExtra` helper を含む native app bundle と user login item を使い、SwiftBar / xbar、desktop widget、desktop file、通知だけへ成立を依存しないこと。
  2026-07-29 の「binary 一つ、別監視 job なし」決定に対する UI 限定の例外を、実装前にユーザー決定として記録すること。
- **AC-111**: `unobserved`、`healthy`、`anomalous`、`status-unavailable` の全状態で menu bar item が存在し、正常時にも消えないこと。
  色だけに依存せず、symbol、text、accessibility label で状態を区別すること。
- **AC-112**: menu の詳細で morning と evening を分け、各 period の最後の `done` と最後の転記を別々に表示すること。
  overall は2 period の worst state とし、片方だけ健康な場合に全体を健康と表示しないこと。

### 8.2 判定と初回状態

- **AC-113**: 判定は T-1 を主、T-3 を従、V-3 を主、V-1 を従とし、`done` を転記成功の代用にしないこと。
  U-1 の UI app は Sheets を直接読まず、pipeline が実行時に status へ記録した入力と転記結果を使うこと。
  T-3 の Sheets 読み戻しは U-3 の `doctor` に残し、常駐 helper へ credential と network access を持ち込まないこと。
- **AC-114**: 有効な終端 status が一度も無い初回は `unobserved` とし、異常通知を出さず、健康とも表示しないこと。
  一度読めた status の消失、破損、未知 version、必要 field 欠落は `status-unavailable` とし、`unobserved` へ戻さないこと。

### 8.3 更新と通知

- **AC-115**: status の atomic replacement、60秒以内の wall-clock timer、sleep 復帰、app restart の四つを再評価契機にすること。
  file event は低遅延の補助とし、取り逃しても timer で回復すること。
- **AC-116（負のコントロール）**: 最後に健康な status を書いた後で pipeline と status 更新を止め、file event を発生させずに clock だけ V-1 の2日閾値より先へ進めたとき、60秒相当以内に `anomalous` へ変わること。
  pipeline 実行時だけ評価する実装は不合格とする。
- **AC-117**: alert と recovery の通知は、最後に評価した state と通知済み遷移を持つ durable receipt に基づき、通知対象の state transition ごとに1回とすること。
  同じ異常の継続中、timer、pipeline 再実行、app restart で繰り返さないこと。
  receipt が無い初回は現在 state を baseline とし、通知しないこと。

### 8.4 常駐の生存性と限界

- **AC-118**: app bundle に内包した `MenuBarExtra` helper を user の同意を得て `SMAppService.loginItem(identifier:)` で一つだけ登録し、login 後に起動し、crash または nonzero exit 後に再起動されること。
  実 user の Login Items を変更する自動テストは行わず、adapter test と一時 identifier の手動試験を分けること。
- **AC-119**: UI app 自身の完全な自己監視を保証しないことを設計書と利用者向け文書に明記すること。
  user による無効化、明示終了、app bundle 欠落、user session 不在、sleep、shutdown では item が消えることを限界とし、再帰的な watchdog を追加しないこと。

### 8.5 data と lifecycle

- **AC-120**: UI app は versioned `pipeline-status.json` と自分の notification receipt だけを読み、Google Sheets、producer、network、credential、測定値へアクセスしないこと。
  receipt は別 file の mode `0600`、atomic replacement とし、status の single writer を崩さないこと。
- **AC-121**: installer は host と helper を含む署名済み app bundle の配置と、内包 helper の login item 登録を user opt-in で行い、approval 待ちを成功と誤報しないこと。
  uninstaller は unregister 後に UI artifact と receipt を除去し、既存方針どおり pipeline status と測定 data を既定で残すこと。

### 8.6 代替案と検証

- **AC-122**: desktop widget は M-1 の補助、SwiftBar / xbar は prototype または明示的な外部依存、desktop file は不採用として文書化すること。
  いずれも単独で production の U-1 を満たしたと判定しないこと。
- **AC-123**: state evaluator、更新 controller、通知 de-dup、receipt、installer adapter は fake clock と isolated HOME で自動検証し、native item の表示、ServiceManagement の実登録、sleep 復帰は代理指標と一時 identifier の手動試験として分け、`docs/ACCEPTANCE_TEST_REPORT.md` に確認種別を記録すること。

## 9. 決定が必要な1点

> **R-1 を採り、U-1 の UI に限って host と menu helper を含む native app bundle と user login item を認めますか。**

推奨は R-1 である。
採らない場合、当方だけで閉じる常設 menu bar 経路は存在しない。
その場合は R-2 の外部 tool 依存または R-0 の現状維持を選ぶ必要がある。

## 10. 範囲外

- `pipeline-status.json` の schema を本書で実装すること
- production の通知を本書で配線すること
- Google Sheets を menu bar app から読むこと
- desktop widget を M-1 と同時に実装すること
- helper の停止を別 watchdog で再帰的に監視すること
- 端末が sleep または shutdown 中に利用者へ表示すること
