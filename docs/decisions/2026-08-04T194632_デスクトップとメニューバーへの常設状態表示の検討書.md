# 常設状態表示の検討結果と通知のみの構成

起草: `scale2sheet_architect_codex`
検証: `scale2sheet_reviewer_claude`

| 項目 | 値 |
| --- | --- |
| 起点 | Issue #46、U-1 の経路設計 |
| 最終決定 | 常設表示を作らず、通知だけを能動的な伝達経路にする |
| 決定記録 | [Issue #46 の user comment](https://github.com/kappaseijin/scale2sheet/issues/46#issuecomment-5178625244) |

## 1. 結論

**M-1 の native menu bar app は採用しない。**
M-2 の desktop widget、M-3 の desktop file、M-4 の SwiftBar / xbar も採用しない。
選択は R-0 に相当し、2026-07-29 の「配布物は compiled Bun binary 一つ」「監視用の別 job を増やさない」を維持する。

能動的に人へ届ける経路は、既存 pipeline が状態変化時に発火する macOS 通知だけである。
ただし状態の記録と能動照会は残す。

- T-1 の `pipeline-status.json` へ状態を記録する
- T-3 の Sheets 読み戻しを `doctor` で確認する
- U-3 の `doctor` が最後の `done`、最後の実転記、各経過日数、異常継続日数を報告する
- 正常から異常、異常から正常へ変化したときだけ通知を1回試みる

**この構成に第二の能動的な伝達経路は無い。**
利用者が通知を見逃した場合、通知が OS 側で抑制された場合、pipeline 自体が起動しなかった場合、その時点で別の process が異常を知らせることはない。
状態 file、log、Sheets の空白、`doctor` は後から調べる証拠にはなるが、自発的に利用者を気づかせない。

Issue #46 の一次データは、通知が少なくとも60回鳴り、一度も行動につながらなかったことを示している。
今回の通知は異常の継続中に繰り返さず、状態変化時だけに絞るため、当時と頻度特性は同一ではない。
発火頻度を下げることで行動率が改善するかは実測根拠がなく、観測にも長期間を要する。
したがって「通知だけで人が気づく」という効果は保証しない。

## 2. 固定する前提

| 論点 | 固定する内容 |
| --- | --- |
| 判定材料 | T-1 の status を主、T-3 の Sheets 読み戻しを従とする。T-3 は U-3 の `doctor` が担う |
| 観測軸 | V-3 を主、V-1 を従とする |
| `done` | pipeline の完了であり、転記成功を意味しない |
| V-3 | 実行時に window 内の体重があり、転記しなかった実行は1回で異常 |
| V-1 | 最後の `done` から2日以上を異常とする |
| 通知 | 正常と異常の状態が変わったときだけ試み、同じ異常の継続中は繰り返さない |
| 能動照会 | U-3 の `doctor` を残す |
| Slice 境界 | status の器を先に入れ、通知と `doctor` はその記録を使う |
| 配布・常駐 | compiled Bun binary 一つを維持し、別の app、widget、job、第三者常駐 tool を成立条件にしない |

2026-08-04 19:46 JST の実測では、`~/.config/scale2sheet/pipeline-status.json` は存在しなかった。
production CLI に pipeline subcommand がまだ無いためである。
過去の状態が無いことだけでは、最後の成功からの経過を定義できず、異常として通知しない。
ただし最初の実行自体が V-3 または明示的な失敗 outcome を観測した場合は、その異常を通知対象にする。

## 3. 常設表示について確定した platform の事実

本節は不採用案の再提案ではない。
将来、制約を変えて再検討するときの一次資料として残す。

### 3.1 native menu bar

Apple は [`MenuBarExtra`](https://developer.apple.com/documentation/swiftui/menubarextra) を、app が active でないときも system menu bar に残る persistent control と定義している。
window を持たず、メニューバーだけを表示する utility app も構成できる。
AppKit の [`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem) でも system menu bar に item を置ける。

いずれも、メニューバー項目を所有する process が必要である。
**「メニューバーに常設するが、process は常駐させない」という構成は成立しない。**
この制約をユーザーへ提示した結果、常設表示を諦める決定になった。

### 3.2 M-1 を作る場合の成立条件

Apple は macOS 13 以降の login item と LaunchAgent の登録に [`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice) を使うよう案内している。
[`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29) の契約では、`SMAppService.loginItem(identifier:)` で登録した login item は登録直後と次回以降の login 時に起動し、crash または nonzero exit 後は system が再起動する。

[Apple の helper 更新ガイド](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos)に沿う構成は、次のとおりである。

- 配布用 app bundle の `Contents/Library/LoginItems` に menu helper app を内包する
- host app から `SMAppService.loginItem(identifier:)` で helper を登録する
- helper が `MenuBarExtra` と壁時計 timer を所有する

この構成は技術的に成立する。
ただし compiled Bun binary 以外の複数 executable と常駐 process が増えるため、既存の配布・常駐決定と両立しない。
ユーザーは例外を設けないと決めたため、実装しない。

### 3.3 desktop widget、desktop file、既存 tool

Apple の [`WidgetKit`](https://developer.apple.com/documentation/widgetkit/) は desktop へ glanceable content を置ける。
しかし extension は別 executable であり、user による配置と system の更新 budget に依存する。
[widget 更新ガイド](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date)が示すとおり、status 変更直後の反映時刻を当方は保証できない。

desktop file は別 executable を要しないが、pipeline が止まると最後の正常表示が残り続ける。
時刻だけを進めるには別 job が必要になる。

[`SwiftBar`](https://github.com/swiftbar/SwiftBar) と [`xbar`](https://github.com/matryer/xbar) は script の標準出力を menu bar へ置ける。
ただし第三者の常駐 app が成立条件になるため、R-2 として不採用になった。

### 3.4 launchd の限界

macOS 26.6（build 25G72）に同梱された `launchd.plist(5)` は、`StartInterval` が sleep 中の発火を取り逃すことを明記している。
同じ system manual は `WatchPaths` と `PathState` の file-system monitoring を race-prone かつ lossy とする。
根拠は `MANWIDTH=160 man 5 launchd.plist | col -b` の該当節で再現できる。

短命 process を file event だけで起動する案も、常設表示の代替にはしない。

## 4. 選択肢と最終決定

| 案 | 構成 | 常駐 | 最終決定 | 主な帰結 |
| --- | --- | --- | --- | --- |
| M-0 / R-0 | 既存 pipeline の状態記録、状態遷移通知、`doctor` | 追加無し | **採用** | 通知を見逃した場合の第二防御が無い |
| M-1 / R-1 | native app bundle + menu helper + login item | 必要 | 不採用 | 技術的には成立するが、単一 binary と別 job 無しに反する |
| M-2 | desktop widget | system 管理の extension | 不採用 | 別 executable、配置操作、更新 budget が要る |
| M-3 | desktop file | 更新 job を置かなければ無し | 不採用 | pipeline 停止時に正常表示が残る |
| M-4 / R-2 | SwiftBar / xbar plugin | 第三者 app が必要 | 不採用 | 外部依存と常駐を増やす |

M-0 は Issue #46 のサクセスストーリー「止まったら人が気づく」を保証しない。
ユーザーは、その限界と一次データを確認したうえで M-0 を選んだ。

## 5. 採用する notification-only 構成

```text
existing launchd schedule
          │
          ▼
compiled Bun pipeline
          │
          ├─ evaluate T-1 / V-3 / V-1
          ├─ atomic replace pipeline-status.json
          └─ state transition only
                      │
                      ▼
              bounded osascript
                      │
              ┌───────┴────────┐
              ▼                ▼
        macOS accepted      nonzero / timeout
              │                │
      delivery is unknown      ▼
                         log + status diagnostic

manual doctor ── status + Sheets readback + last notification attempt
```

### 5.1 状態の記録と判定

pipeline は実行のたびに、既存 AC-96〜104 が定めた観測量を更新する。
V-3 は実行時に得た入力と実転記の組を使う。
V-1 は最後の `done` と現在時刻の差を使う。
`done` と実転記は別 field とし、一方を他方の代用にしない。

status は、少なくとも次を後続の pipeline と `doctor` が再現できる形で持つ。

- period ごとの最後の `done` と実転記
- V-3 と V-1 の現在の判定材料
- `unobserved`、`normal`、`alert` の前回 state
- 最後に通知を試みた transition と、`osascript` の結果

具体的な schema は status の器を実装する設計で固定する。
本書は field 名を先に固定しない。
notification state を terminal status と別の receipt file へ分離しない。
同じ versioned status の中に置き、片方だけを読んで初回判定しない。

### 5.2 通知する transition

通知判定は `unobserved`、`normal`、`alert` の三状態を使う。
`unobserved` は過去成功が無いことだけを表し、現在の実行で得た明示的な異常を覆い隠さない。
本当の初回と notification state の喪失も分ける。
有効な terminal history が status にあるのに notification state だけが無い場合は、初回ではなく記録喪失である。

| 前回 state | 今回 state | 動作 |
| --- | --- | --- |
| terminal history も notification state も無し | `unobserved` / `normal` | 本当の初回として保存し、通知しない |
| terminal history も notification state も無し / `unobserved` | `alert` | 現在の実行で得た明示的な異常として alert 通知を1回試みる |
| terminal history 有り、notification state 無し | `alert` | 記録喪失として diagnostic を残し、alert 通知を1回試みる |
| terminal history 有り、notification state 無し | `normal` | 記録喪失の diagnostic と `normal` を保存し、recovery 通知は出さない |
| `unobserved` | `normal` | 最初の正常観測として保存し、通知しない |
| `unobserved` | `unobserved` | 通知しない |
| `normal` | `alert` | alert 通知を1回試みる |
| `alert` | `normal` | recovery 通知を1回試みる |
| `alert` | `alert` | 通知しない。原因の変化だけでは再通知しない |
| `normal` | `normal` | 通知しない |
| 任意 | 上記以外 | 通知しない。terminal history があり notification state が無い場合は、記録喪失 diagnostic だけを残す |

同じ異常が続く間は、pipeline が何回起動しても通知を繰り返さない。
通知の音、文面、回数を増やすことで U-1 の不在を代替しない。

status file 全体が失われ、terminal history も notification state も無い場合は、初回導入と完全な削除を区別できない。
この場合は本当の初回と同じ扱いになり、現在の実行が明示的な異常を観測しない限り通知しない。

### 5.3 `osascript` の実行結果

通知 adapter は timeout を持ち、exit code、stderr、経過時間を同じ attempt の結果として返す。
nonzero exit または timeout は pipeline log と status diagnostic の両方へ記録する。
通知失敗の diagnostic で、本来の pipeline outcome、V-3、V-1、件数を上書きしない。
`doctor` は最後の通知 attempt の transition、時刻、結果を報告する。

同じ transition を restart 後に再送しないため、次の順序を使う。

1. 新しい alert state と notification attempt の claim を、一つの atomic status replacement で先に保存する。
2. `osascript` を1回だけ呼ぶ。
3. success、nonzero、timeout の結果を、次の atomic status replacement で保存する。

claim 後に process が停止した場合、同じ transition は再送しない。
したがって claim と `osascript` の間で停止すると通知は失われ、`osascript` と結果保存の間で停止すると配送結果は `unknown` のままになる。
OS 通知と status file を一つの transaction にできないため、重複防止と配送保証を同時には満たせない。
本書は状態変化時だけという決定に合わせ、at-most-once の attempt を選ぶ。

通知失敗を知らせる第二の通知は送れない。
同じ state のまま次回 pipeline が起動しても、自動 retry はしない。
これは「同じ異常の継続中は繰り返さない」という決定を優先した帰結である。

`osascript` が exit 0 を返しても、通知が利用者へ表示された証拠にはならない。
Focus、Notification Center の設定、OS の抑制、利用者の見逃しを sender から判別できる acknowledgement は無い。
macOS 26.6 の Standard Additions dictionary では `display notification` に result parameter が定義されておらず、配送または既読の戻り値を受け取れない。
この事実は `sdef /System/Library/ScriptingAdditions/StandardAdditions.osax` の `display notification` command で再現できる。

### 5.4 pipeline が起動しない場合

通知の評価と送信は既存 pipeline の process 内でだけ行う。
したがって次の場合、時刻が V-1 の2日閾値を越えても、その時点では通知されない。

- launchd job が unload または無効化されている
- compiled Bun binary が欠落または実行不能である
- 端末が sleep または shutdown 中である
- pipeline が通知判定へ到達する前に停止する

後から pipeline が起動できれば、その時点で status の古さを再計算して alert へ遷移できる。
起動しないままなら、Sheets の空白に人が気づくか、利用者が `doctor` や log を調べるまで分からない。
binary 自体が欠落していれば、その binary の `doctor` も実行できない。

これは 2026-07-29 にユーザーが受け入れた自己参照の限界を維持する。

### 5.5 `doctor` と T-3

U-3 は残す。
`doctor` は AC-48 と AC-107 に従い、次を報告する。

- period ごとの最後の `done` と、その経過日数
- period ごとの最後の実転記と、その経過日数
- 現在の異常状態が継続している日数
- 実行中 binary の build 識別子
- T-3 の Sheets 読み戻しによる直近転記の確認
- 最後の notification attempt と `osascript` の結果

`doctor` は能動照会であり、利用者が実行しなければ気づきは生じない。

## 6. 通知経路が壊れた場合

| 事象 | sender が検出できるか | 記録 | 第二防御 |
| --- | --- | --- | --- |
| `osascript` nonzero exit | できる | log + status + `doctor` | 無し |
| `osascript` timeout | できる | log + status + `doctor` | 無し |
| `osascript` 起動前の process 停止 | その process 自身ではできない | 記録できない場合がある | 無し |
| OS が通知を抑制したが exit 0 | できない | accepted としか記録できない | 無し |
| 利用者が通知を見逃した | できない | delivery / read receipt 無し | 無し |
| pipeline が起動しない | できない | status が古いまま | Sheets の空白または後日の能動照会だけ |

**「accepted」は「delivered」または「read」を意味しない。**
通知の実配送と利用者の認知を acceptance test で自動的に証明しない。

## 7. 効果測定の限界

過去の60回以上の通知は、異常のたびに繰り返され、行動につながらなかった。
新しい構成は状態変化時だけに減らすため、通知疲れを減らす可能性はある。
しかし、その差が認知率を改善するという evidence は無い。

発火回数が減るため、観測期間を短くすると「通知が無かった」のか「見たが行動しなかった」のかを区別できない。
既読 acknowledgement も無い。
したがって通知だけの有効性を、本実装の短期 acceptance として置かない。

## 8. 検証境界

### 8.1 自動検証

- fake clock と status fixture で V-3 / V-1 の alert state を再現する
- `normal -> alert -> alert -> normal` で通知要求が2回だけになることを確認する
- 初回に過去成功が無いだけなら通知せず、最初の実行で明示的な V-3 または失敗 outcome があれば alert を1回要求する
- terminal history を残したまま notification state だけを欠落させ、現在が alert なら記録喪失 diagnostic と alert を1回要求する
- status file 全体を欠落させた場合は初回と区別できない限界を確認する
- fake notifier の success、nonzero、timeout を決定論的に起こす
- claim 後かつ notifier 前、および notifier 後かつ結果保存前の crash seam で停止し、restart 後に同じ transition を再送しないことを確認する
- notifier failure が pipeline outcome と diagnostic を上書きしないことを確認する
- isolated HOME に2日閾値を越えた status を置き、pipeline を起動しない bounded window では通知要求と status 更新が生じないことを確認する
- 同じ fixture を `doctor` が stale と報告し、次の pipeline 起動が alert transition を1回だけ要求することを確認する
- isolated HOME と network deny を使い、実 Notification Center に依存しない
- installer と plist に MenuBarExtra、WidgetKit、SwiftBar、xbar、追加監視 job の成立条件が増えていないことを静的に検査する

### 8.2 手動検証

実 macOS 通知は test title を使い、alert と recovery を各1回だけ確認する。
通知を OS 側で抑制した状態では、`osascript` の exit 0 が delivery を証明しないことを記録する。
手動試験でも利用者が通知を読んだことまでは判定しない。

結果は `docs/ACCEPTANCE_TEST_REPORT.md` に、自動、代理指標、手動を分けて記録する。

## 9. 合格条件

PR #91 で予約した AC-110〜123 のうち、最終決定に必要な8条件を AC-110〜117 へ定義する。
未使用の末尾 AC-118〜123 は台帳規約に従って `UNUSED` へ戻し、別案件への再割当を可能にする。

- **AC-110**: production の能動的な伝達経路を既存 pipeline 内の macOS 通知だけとし、native menu bar app、desktop widget、desktop file、SwiftBar / xbar、追加の常駐 job を実装または成立条件にしないこと。
  2026-07-29 の「compiled Bun binary 一つ、別監視 job なし」に例外を設けないこと。
- **AC-111**: T-1 を主、T-3 を従、V-3 を主、V-1 を従とし、status の器を通知より先に入れること。
  `done`、実転記、各経過日数を別々に記録し、`done` を転記成功の代用にしないこと。
- **AC-112**: 通知は `normal -> alert`、`unobserved -> alert`、`alert -> normal` の transition ごとに1回だけ試み、同じ state の継続中は通知しないこと。
  過去成功が無いことだけなら `unobserved` として通知せず、最初の実行で明示的な V-3 または失敗 outcome を得た場合は alert を1回試みること。
  terminal history がある status から notification state だけが失われた場合は初回扱いせず、現在が alert なら記録喪失 diagnostic と alert を1回試みること。
  status file 全体が失われた場合は初回導入と区別できない限界を明記すること。
  異常原因だけが変わっても alert state が同じなら再通知しないこと。
- **AC-113**: notification adapter は bounded timeout を持ち、exit code、stderr、経過時間を同じ attempt の組として返すこと。
  transition の claim を atomic status replacement で保存してから1回だけ呼び、結果を次の replacement で保存すること。
  nonzero または timeout を log と status へ記録し、本来の pipeline outcome、diagnostic、V-3、V-1、件数を上書きしないこと。
  claim 後の crash では再送せず、通知または結果が失われ得る at-most-once の限界を明記すること。
- **AC-114**: `doctor` が AC-48 / AC-107 の情報に加え、最後の notification attempt の transition、時刻、exit または timeout を報告すること。
  T-3 の Sheets 読み戻しは `doctor` に残し、通知 process から Sheets を読まないこと。
- **AC-115（負のコントロール）**: isolated HOME に V-1 の2日閾値を越えた status を置き、pipeline を起動しない bounded window では通知要求と status 更新が生じないことを確認すること。
  同じ fixture を `doctor` が stale と報告し、次の pipeline 起動が alert transition を1回だけ要求することを対で確認すること。
  pipeline の非起動、binary 欠落、sleep 中は検出できず、次回起動または能動照会まで分からない限界を利用者向け文書へ明記すること。
- **AC-116**: `osascript` が exit 0 でも OS による抑制と利用者の見逃しは検出できず、第二の能動的な伝達経路が無いことを設計書と利用者向け文書へ明記すること。
  60回以上の通知が行動につながらなかった実測と、状態変化時だけに減らす効果が未検証であることを併記すること。
- **AC-117**: transition 表の全組合せと de-dup、初回 `unobserved` と初回明示異常、terminal history を残した notification state 喪失、status 全損、notifier success / nonzero / timeout、claim 前後の crash seam、diagnostic の対応、pipeline 非起動の負のコントロールを fake clock と isolated HOME で自動検証すること。
  実通知は手動確認とし、delivery または既読の証明として扱わないこと。
