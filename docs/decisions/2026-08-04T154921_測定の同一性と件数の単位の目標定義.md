## 1. サクセスストーリー

**「今日は何件測った」と当方が言うとき、その数が物理的な測定の回数と一致している。**

現在は一致していない。同じ体重計に 1 回乗った測定が、Apple Health 経由と Google Fit 経由の
2 レコードとして数えられている。転記される値は同じなので**スプレッドシートは正しい**が、

### 2.0 数え方の単位（本書の集計すべてに適用）

**「同一の測定」を数えるとき、キーを数えるのかレコードのペアを数えるのかで結果が変わる。**
本書は次の 3 つを区別し、表ごとにどれで数えたかを明示する。

| 記号 | 単位 | 定義 |
| --- | --- | --- |
| **K** | キー | 両経路に存在する `(day, measuredAt, kind)` の個数 |
| **R** | レコード | apple-health 側のレコード数（同一キーに複数レコードがあれば複数と数える） |
| **P** | 値ペア | 経路をまたぐ (apple 値, google 値) の全組み合わせ |

実測値（**当方の reader が実際に読むファイルだけを基数とする**）: **K = 2,060 / R = 2,060 / P = 2,066**。

> **基数から除外したファイルが 1 件ある。** 2026-07-09 の `…_apple-health-file_001.jsonl` である。
> `src/sources/scale-exporter/reader.ts:38` の `fileNamePattern` は
> `(apple-health|google-fit)` しか受け付けないため、**当方はこのファイルを読まない。**
> producer 側の出力としては同じ経路の由来だが、**当方の入力集合には入らない。**
> 本書は「当方が何を同一の測定として扱うか」を定義するので、**読まないレコードを基数に含めない。**
>
> 含めた場合は K = 2,061 / weight 6 になる（初稿はこの立場だった。
> `reviewer_claude` の指摘により実装の挙動へ合わせて訂正、2026-08-04）。
> スクリプトは既定で除外し、`--include-legacy` で含めた数も出せる。
>
> **このファイルが読まれないこと自体は別の問題である**（11 節の 7）。

### 2.1 経路をまたいだ同一測定（単位 = K）

| 指標 | 値 |
| --- | --- |
| 両経路に存在する `(day, measuredAt, kind)` | **K = 2,060** |
| うち値が完全一致 | 2,044 |
| うち値の差が 1e-3 未満 | 16 |
| **それ以外（中間帯）** | **0** |
| 経路をまたぐ差の最大値 | **3.05e-06** |
| kind 別（K） | heartRate 2,032 / bloodPressureSystolic 9 / bloodPressureDiastolic 9 / **weight 5** / bodyTemperature 5 |

**H-1. 経路をまたいだ「同時刻・同種別」のペアには曖昧な中間帯が無い。**
値は一致するか、float 表現の差（最大 3.05e-06）で違うかのどちらかである。

### 2.2 負のコントロール（同一 platform 内の同時刻・同種別）

| platform | 同キーで値が異なるキー数（K） | 隣接値ペア数（P） | 内訳 |
| --- | --- | --- | --- |
| **google-fit** | **4,033** | **4,060** | **すべて heartRate**。最大差 60.0 bpm、中央値 1.02 bpm |
| apple-health | 0 | 0 | — |
| weight / bloodPressure / bodyTemperature | **0** | 0 | — |

**H-2. 「同じ時刻・同じ種別なら同じ測定」は heartRate では成立しない。**
同一秒に最大 60 bpm 違う 2 値が存在する。**脈拍は転記対象である。**

**H-2b【決定的】経路内の値の差は、いくらでも小さくなりうる。**

| 相対許容差 | この許容差を経路内へ適用したとき、**誤って併合される**隣接値ペア数 |
| --- | --- |
| 1e-6 | **1** |
| **1e-5** | **21** |
| 1e-4 | 77 |
| 1e-3 | 406 |

経路内の最小の相対差は **5.56e-07**（絶対差 5.34e-05 bpm） であり、**経路をまたぐ差の最大値 3.05e-06 より小さい。**

**つまり「経路をまたぐ差」と「経路内の本物の差」は、値の大きさでは分離できない。**
どんな許容差を選んでも、経路内へ適用すれば本物の測定が併合される。
**分離できる軸は値ではなく経路である。**

### 2.3 重複を消すと何を失うか

| 指標 | 値 |

**H-3. apple-health 経由のレコードは、7 件を除いてすべて google-fit 側にも存在する。**

### 2.4 現在どちらの値が転記されているか

**H-4. 現在は apple-health 側の値（丸められた方）が転記されている。ただし偶然である。**

根拠は 3 点。

1. `src/sources/scale-exporter/reader.ts:104-109` の `listTargetFiles` は
   ファイル名を `.sort()` で並べる。`…_apple-health_001.jsonl` は `…_google-fit_001.jsonl` より前に来る

   **狭義の比較**（`<` / `>`）で置き換えを判定する。`measuredAt` が同一なら置き換えは起きない
3. したがって**先に読まれた apple-health 側が残る**

つまり `68.19999694824219` ではなく `68.2` が入る。**結果は望ましいが、根拠がファイル名の
アルファベット順である。** プラットフォーム名が変わる、または 3 つ目の経路が増えた時点で反転する。
**現状の「正しさ」は仕様ではなく副作用である。**

### 2.5 経路内の完全重複

各日 1〜9 行、google-fit 側にのみ存在する（例: 07-04 に 9 行、07-10 に 9 行）。
**これらは現行キーで既に除去されている。** 本書の変更対象ではない。

## 3. 論点1: 測定の同一性を何で判定するか

### 3.1 分岐軸の選択（選択肢を並べる前に）

素直に考えると分岐軸は **kind** に見える。heartRate だけが同時刻・別値を持つからである（H-2）。
**しかし実測は別の軸を指している。**

| 軸 | 同時刻・同種別で値が違う組 |
| --- | --- |
| 経路を**またぐ**組 | **0 件**（全 kind。差は最大 3.05e-06 の表現差のみ） |
| 経路の**内側**の組 | **4,060 ペア**（すべて heartRate、最大 60 bpm） |

**危険なのは kind ではなく「経路の内側へ適用すること」である。**
同一性の判定を**経路をまたぐ組に限定**すれば、kind 別の例外を 1 つも置かずに heartRate の問題が消える。

**そして H-2b により、値による分離は原理的に不可能である。**
経路内の最小相対差 5.56e-07 は、経路をまたぐ最大差 3.05e-06 より**小さい**。
**許容差をどこに置いても、経路の内側へ適用する限り本物の測定を併合する。**

したがって選択肢は「値をどう比べるか」ではなく、**「どの範囲に適用するか」**で並べる。

### 3.2 選択肢

| | 案 | 適用範囲 | 一致条件 |
| --- | --- | --- | --- |
| **D-0** | 現状維持 | — | `(measuredAt, kind, value, source)` 完全一致のみ |
| **D-1** | `source` を落とす | 全体 | `(measuredAt, kind, value)` 完全一致 |
| **D-2** | 値を許容差で比較 | **全体** | `(measuredAt, kind, value ± 相対許容差)` |
| **D-3** | 時刻と種別のみ | 全体 | `(measuredAt, kind)` |
| **D-4** | kind ごとに規則を変える | 全体 | kind 別 |
| **D-5** | **経路をまたぐ組に限定** | **経路をまたぐ組のみ** | `(measuredAt, kind, value ± 相対許容差)`。**経路の内側は現行のまま** |

### 3.3 帰結（観測期間 36 日）

**単位を明示する。** 「消える」は K（両経路に存在するキー）、
「誤って併合」は P（隣接値ペア）で数えた。

| 案 | 経路をまたぐ重複のうち消える（K） | 残る（K） | **本物の測定を誤って併合（P）** |
| --- | --- | --- | --- |
| D-0 | 0 / 2,060 | 2,060 | 0 |
| D-1 | 2,044 / 2,060 | **16**（うち weight 5） | 0 |
| D-2（許容差 1e-5） | **2,060 / 2,060** | 0 | **21** |
| D-2（許容差 1e-6） | 2,060 / 2,060 | 0 | **1** |
| D-3 | 2,060 / 2,060 | 0 | **4,060** |
| D-4（heartRate だけ値も見る） | 2,060 / 2,060 | 0 | 21（heartRate に許容差 1e-5 を使う場合） |
| **D-5（許容差 1e-5、経路をまたぐ組のみ）** | **2,060 / 2,060** | **0** | **0** |

- **D-1 は weight を消せない。** #63 の起点となった 68.2 / 68.19999694824219 が残る
- **D-2 は許容差をどう選んでも経路内で誤併合する**（H-2b）。1e-6 まで下げても 1 ペア残り、
  かつ経路をまたぐ差の最大 3.05e-06 を下回るので**本来消すべき重複を消せなくなる**
- **D-3 は 4,060 ペアを潰す。** 最大 60 bpm の差を同一視する
- **D-4 は kind 別の分岐を置いてなお、heartRate の許容差の問題が残る**（D-2 と同じ理由）
- **D-5 だけが、消すべきものを全部消し、誤併合が 0 になる**

### 3.4 許容差の値と、許容差を超えたときの挙動（D-2 / D-4 / D-5 の成立条件）

**(a) 値の選択**

観測された経路間の最大差は **3.05e-06**。これは `float32` の仮数部 24 bit で
68 前後の値を往復した丸め誤差（68 × 2^-24 ≈ 4.05e-06）と桁が一致し、**表現形式から説明できる差**である。

提案する相対許容差 **1e-5** は、観測最大差の約 3 倍。
一方、意味のある測定差の下限（体重計 0.05 kg / 血圧計 1 mmHg / 体温計 0.1 ℃ / 脈拍 1 bpm）は
相対で 1e-3 以上であり、**3 桁近い空白がある。**

> **これは「実測で決めた閾値」ではない。** 実測が示すのは経路間の中間帯が空だったことまでである。
> 1e-5 は**浮動小数点誤差の上限と機器の分解能の間の空白**から選んだ。
> 案件A の N の教訓（観測値の直上に貼り付けない）を適用している。

**(b) 許容差を超えたときの挙動**

| 状況 | 挙動 |
| --- | --- |
| 経路をまたぐ組で、差が許容差を**超えた** | **両方を残す**（別の測定として扱う）。失敗にしない |
| 経路をまたぐ組で、差が許容差**以内** | 1 件に併合する |
| **経路の内側の組** | **判定しない。現行の完全一致 dedup のみ。4,060 ペアはすべて両方残る** |

**失敗にしない理由**: 差が許容差を超えた組は「同時刻に別の測定があった」だけであり、
異常ではない。経路内では 4,060 件が正常に起きている。**失敗にすると正常な入力で pipeline が止まる。**

**この挙動を経路内の 4,060 ペアへ当てはめた場合**（D-2 / D-3 / D-4 を採った場合に起きること）:
21 ペア（許容差 1e-5）が併合され、**最大 60 bpm 違う 2 値のうち一方が消える。**
D-5 では経路内を判定しないため、**4,060 ペアはすべて現行どおり両方残る。**

### 3.5 kind ごとに分けるか（D-4 の是非）

**経路軸（D-5）で分ければ足りるので、kind 軸は不要である。**

kind で分ける案が成立するのは、**経路軸で分けても残る問題がある場合**だけである。
本書の実測ではその問題が見つかっていない。経路をまたぐ組は全 kind で中間帯が空であり（H-1）、
経路の内側は D-5 では触らない。

> 私の AGENT.md には「例外の境界が曖昧なとき、条件を増やす前に『選ばずに全部やる』で
> 閉じられないか試す。判断点を消すと矛盾も消える」がある。
> **ここでは D-5 が判断点を消す案である。** kind で分ければ
> 「この kind はどちらの規則か」という判定が kind の追加ごとに必要になる。

### 3.6 推奨

**推奨は D-5（経路をまたぐ組に限定した、相対許容差 1e-5 での同一性判定）。**

> **許容差 1e-5 も母数 36 日の観測に対する選択である。** 観測窓の外では保証されない。
> 案件A の N=4 と同じく、**確定値ではなく、観測窓とその外の区別を伴う選択**として読むこと。
> 再監査（AC-65）で経路間の最大差を数え直し、1e-5 との隔たりが保たれているかを確認する。

1. 観測期間の経路重複 2,060 件（K）をすべて消し、**誤併合が 0 ペア**（3.3）
2. kind 別の分岐を置かない（3.5）
3. **経路の内側の挙動を一切変えない。** 現行の完全一致 dedup がそのまま残るので、
   本変更による退行の範囲が「経路をまたぐ組」に閉じる

**D-0（現状維持）を採るべき条件**は 3.7 に分けて書く。

### 3.7 D-0（現状維持）が成立する条件

現状維持は**成立しうる**。ただし無料ではない。次の 2 点を両方認める場合に限り成立する。

**(1) 転記結果は変わらない。**
`buildLatestMeasurementSet` は体重を anchor に選び、他の kind は体重の時刻に最も近いものを選ぶ。
重複した 2 レコードは `measuredAt` が同一なので、**どちらが選ばれても選択結果の時刻は変わらない。**
値は実質一致（最大差 3.05e-06）なので、**転記される数値も変わらない。**
実測でも、観測期間 36 日で重複が転記値を変えた日は **0 日**である。

**(2) 件数の意味は変わる。**
重複は `readLineCount` と `windowedReadingCount` を膨らませる。これは案件A で決定した 3 件数であり、
#38 の報告と Slice 7 の観測ゲートの材料である。**「転記には影響しないが、件数は物理測定の回数ではない」**
ことを、#38 / #54 / Slice 7 / 案件A の該当箇所すべてに書き直す必要がある（論点3 の F-0）。

**(1) だけを根拠に現状維持を選ぶことはできない。** (2) の書き直しが伴う。

## 4. 論点2: 重複時にどちらの値を採るか

### 4.1 何が問われているか

H-4 のとおり、**現在は apple-health 側（丸められた値）が採られているが、
根拠はファイル名のアルファベット順である。** 仕様として書かれていない。

### 4.2 選択肢

| | 案 | 内容 |
| --- | --- | --- |
| **E-0** | 現状維持 | ファイル名順で先に読まれた方。**仕様として書かない** |
| **E-1** | **経路の優先順位を明示** | 「apple-health 側を優先する」を仕様として書く。理由は値が丸められているため |
| **E-2** | 値の桁数で選ぶ | 有効数字が少ない方（丸められた方）を採る。経路名に依存しない |
| **E-3** | 転記時に丸める | どちらを採るかは決めず、転記の直前に kind ごとの分解能で丸める |

### 4.3 帰結

| 案 | 観測期間で転記値が変わる日数 | 3 つ目の経路が増えたとき | 経路名が変わったとき |
| --- | --- | --- | --- |
| E-0 | 0 日（現状） | **未定義のまま反転しうる** | **反転しうる** |
| E-1 | 0 日 | 優先順位に追記が必要 | 追記が必要 |
| E-2 | 0 日 | 影響なし | 影響なし |
| E-3 | 0 日 | 影響なし | 影響なし |

**4 案とも観測期間の転記値を 1 日も変えない。** 現在たまたま望ましい値が入っているためである。
違いは**将来の安定性**だけである。

### 4.4 推奨

**推奨は E-3（転記時に kind ごとの分解能で丸める）。**

1. **どちらを採るかという問いを消す。** D-5 で 2 件が 1 件になった後、
   代表値がどちらでも、丸めれば同じ値になる（68.2 と 68.19999694824219 は 0.1 kg 丸めで一致）
2. 経路名にも経路数にも依存しない
3. **スプレッドシートに `68.19999694824219` が入る可能性を構造的に消す。**
   これは経路の重複とは独立に存在するリスクである（google-fit 単独の日でも起こりうる）

**丸めの単位は kind ごとに置く**: 体重 0.1 kg / 体温 0.1 ℃ / 血圧 1 mmHg / 脈拍 1 bpm。

> **成立しない範囲を書く。** E-3 は「表示のための丸め」であり、**元の値を復元できなくする。**
> 現在スプレッドシートは表示専用で、値を再計算する用途が無いため許容できると判断した。
> 将来、転記後の値から統計を取る用途が生まれた場合は再検討が要る。

**E-1 を採るべき条件**: 経路によってデータの信頼度が違うと判断する場合。
本書は「同一の物理測定であり、差は表現形式だけ」という立場（H-1）なので、信頼度の差を認めていない。

## 5. 論点3: 件数を何単位で数えるか

### 5.1 何が問われているか

案件A の決定（#61）で、`pipeline-status.json` に 3 つの件数を記録することが決まっている。

| `readLineCount` | 読んだ行数 |

物理測定 1 回が 2 と数えられる。

### 5.2 選択肢

| | 案 | 内容 |
| --- | --- | --- |
| **F-0** | 公開レコード単位 | 現状。dedup 前の数 |
| **F-1** | 物理測定単位 | dedup 後の数 |

### 5.3 帰結（用途ごとに必要な単位が違う）

| 用途 | 必要な単位 | 理由 |
| --- | --- | --- |
| #54 先方との件数比較 | **公開レコード単位** | 先方が数えているのは自分が公開したレコードである |

換算に必要な情報（何件が重複だったか）は、記録した時点でしか分からない。

## 8. 合格条件

### 8.1 同一性の判定

## 11. この定義では捕まらないもの（範囲外の明示）

1. **同一の測定が 3 秒ずれて 2 経路に出る場合。** AC-54 は `measuredAt` の完全一致を要求する。
   照会4 の回答次第で判定条件を近接へ寄せる（10.1）
2. **値も時刻も同じだが、実際には別の測定である場合。** 原理的に区別できない。
   H-2 の負のコントロールが示すのは「観測期間では weight/血圧/体温で起きていない」ことまでである
3. **producer の再公開による上書き**（Issue #62）。本書の範囲外。転記段階の比較が要る
4. **値そのものの妥当性**（単位取り違えなど）。本書は「同じ測定か」だけを扱う
5. **丸めによる情報の欠落**（E-3）。転記後の値から元の精度は復元できない（4.4）
6. **数え方の定義が変わる前後で、観測日が比較不能になること**（`reviewer_claude` 提示の負のコントロール）

   案件A の B-3（連続 N=4）と Slice 7 の連続 7 日観測は、**日をまたいで件数を比較する**仕組みである。
   本書の決定で「同一の測定」の定義が変わると、決定前に記録した日と決定後の日で件数の意味が変わる。
   ところが `pipeline-status.json` には**どの定義で数えたかが入らない**。

   ```
   決定前の日: windowedReadingCount = 100（重複込み）
   決定後の日: windowedReadingCount =  60（重複除去後）
   → 減少が「重複除去の効果」なのか「供給の減少」なのか区別できない
   ```

   **本書の同一性定義をどう厳密にしても、この経路は捕まらない。** 定義を変えた事実が
   観測記録の側に残っていないためである。潰すには status に**数え方の版**
   （`countingDefinitionVersion` 等）を持たせることになる。

   **本書の範囲外とする。** ただし**放置すると案件A の B-3 と Slice 7 の観測が、
   本書の決定日をまたいだ時点で無効になる**ので、`pipeline-status.json` の項目追加として
   別 Issue で扱うことを提案する。**優先度は本書の実装より前**である
   （版を持たせる前に定義を変えると、変えた事実を記録できない）

7. **reader が認識しないファイルに実データが入っていても、当方は気づかない**
   （`reviewer_claude` が本書の検証中に発見、2026-08-04）

   入力ディレクトリに、`fileNamePattern` に一致しないエントリが 4 件ある。
   `.DS_Store` を除く 3 件に**合計 11 行の実レコード**が入っている。

   ```
   scale_exporter_2026-07-09_apple-health-file_001.jsonl   （1 行）
   scale_exporter_2026-07-10_apple-health_001.jsonlのコピー  （5 行）
   scale_exporter_2026-07-10_apple-health_001.jsonlのコピー2 （5 行）
   ```

   **`apple-health-file` は先方に実在する source モードである。**
   先方がモードを切り替えると、**当方は黙って一部を落とす。**
   対象日のファイルが全部見えなくなれば `failed:input-missing` で検知できるが（#49）、
   **一部だけ命名が変わった場合は「ファイルはある」と判定され、欠けた分に気づかない。**
   実際 2026-07-09 は 1 件が見えないまま google-fit だけで処理されている。

   **本書の範囲外とする。** 同一性の定義ではなく、入力集合の認識の問題である。
   **pm へ別 Issue 化を依頼した。** 案件A の `matchedFileCount` が
   「認識した名前のファイル数」でしかないことと対になる。
