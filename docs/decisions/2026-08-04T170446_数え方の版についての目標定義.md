## 2. 一次データ（起草時に実測、2026-08-04）

### 2.1 既存の status 記録は 1 件も存在しない

**選別規則**: `find ~ -maxdepth 5 -name "pipeline-status.json"`（本機の実測）。

| 探索対象 | 結果 |
| --- | --- |
| `pipeline-status.json`（設計上の配置先は `~/.config/scale2sheet/`、`docs/INSTALLATION_DESIGN.md:120`） | **0 件** |
| `~/.config/scale2sheet/` 配下の status 系ファイル | 0 件 |

**M-1. 移行対象の既存記録は存在しない。**

> **この事実には期限がある。** M-1 は **2026-08-04 時点の実測**であり、
> **Slice 2 が main へ入った翌日には成立しない可能性がある。**
> 決定が遅れた場合は、**着手前に再測定すること**（`find ~ -maxdepth 6 -name "pipeline-status.json"`）。
> 案件A の N=4 に「母数 36 日」を添えたのと同じ趣旨で、
> **観測窓の外では保証されない主張**であることを明示する。

理由は 2 つある。

1. `pipeline` コマンドは production の launchd に載っていない（Slice 2 は shadow path であり、
   本番は従来どおり `scripts/run-pipeline.sh` で動いている）
2. `AtomicPipelineStatusWriter` はどこからも参照されていない（G-2 として報告済み。
   `feat/pipeline-shadow-path` の実装で `src/pipeline/status.ts` 以外に出現しない）

**これは本書の前提を大きく変える。** 「既存の記録の後方互換」は**理論上の論点であり、現時点で実体が無い。**
版を導入するコストは、**いま入れれば移行 0 件**である。

### 2.2 ただし猶予は Slice 2 の着地までしかない

`pipeline` が本番で 1 度でも走った瞬間、版の無い記録が生まれる。
**Slice 2 の実装が完了して launchd へ載った時点で、M-1 の条件は失われる。**

**版を入れる最も安い時点は「いま」であり、それは Slice 2 の着地前という制約と一致する。**

### 2.3 定義文書の SHA は、定義より速く変わる

**選別規則**: `git log --follow` で案件A の目標定義ファイルを追跡（2026-08-04 時点）。

| 指標 | 値 |
| --- | --- |
| ファイルに触れたコミット数（作成から 24 時間以内） | **5** |
| うち**件数の数え方の定義**を変えたもの | **0** |

5 コミットの内訳は、起草・N の根拠の訂正・AC の追加・決定の反映・一次データの訂正である。
**どれも件数の数え方を変えていない。**

**M-2. 文書の SHA は、定義が変わらなくても変わる。** 24 時間で 5 回変わり、定義は 0 回変わった。

## 3. 論点1: 版をどこに持たせるか

### 3.1 選択肢

| | 案 | 位置 | 例 |
| --- | --- | --- | --- |
| **V-0** | **持たせない** | — | 現状 |
| **V-1** | **status のトップレベル** | `pipeline-status.json` の直下 | `"definitionsVersion": 1` |
| **V-2** | `counts` の中 | `counts` オブジェクトの内側 | `"counts": { "version": 1, … }` |
| **V-3** | 別ファイル | 変更履歴ファイル（`definitions-changelog.json` 等） | 版と適用開始日の対応表 |
| **V-4** | **定義そのものを埋め込む** | status の直下に定義の実値 | `"definitions": { "identity": "cross-path-1e-5", "window": {…} }` |

### 3.2 帰結（何が復元でき、何ができなくなるか）

| 案 | 復元できる | **復元できない** |
| --- | --- | --- |
| V-0 | 件数そのもの | **件数の意味。定義変更と供給変動の区別が永久にできない** |
| V-1 | 件数と、その日の定義の識別子 | 版番号が指す定義の中身（**定義文書を別途参照する必要がある**） |
| V-2 | 同上 | 同上。加えて `counts` 以外の値（outcome の意味など）の版を表せない |
| V-3 | 同上 | **別ファイルが失われると全記録の意味が失われる**。status 単体で自己完結しない |
| V-4 | 件数と、その日の定義の中身**そのもの** | ほぼ無い。ただし**定義の増加に応じて status が肥大する** |

**V-3 の弱点は結合である。** status は 1 実行 1 ファイルの独立した記録なのに、
解釈が別ファイルへ依存する。**片方だけバックアップされた場合に意味が失われる。**

**V-2 の弱点は範囲である。** 論点4 のとおり版が要るのは件数だけとは限らない。
`counts` の中に置くと、outcome の意味や window の定義の版を表せない。

### 3.3 推奨

**推奨は V-1（status のトップレベル）+ 定義文書への参照。**

- V-4 は理想だが、**定義が増えるたびに status の schema が変わる。**
  それ自体が版を要する変更になり、問題が入れ子になる
- V-1 の弱点（版番号だけでは中身が分からない）は、**版と定義の対応表を定義文書側に置く**ことで補える。
  対応表は本書の 8 節に置く

**ただし V-1 と V-4 の中間を採る。** 版番号に加えて、**人が読める短い識別子**を 1 つ持たせる。

```json
{
  "definitionsVersion": 1,
  "definitionsLabel": "2026-08-04/pre-63",
  "counts": { … }
}
```

`definitionsLabel` は「いつ時点の定義か」を人が status だけ見て推測できるようにするためのもので、
**機械判定には使わない**（判定は `definitionsVersion` の整数で行う）。

## 4. 論点2: 版の表現

### 4.1 選択肢

| | 案 | 例 | 変わるタイミング |
| --- | --- | --- | --- |
| **W-1** | **整数の連番** | `1`, `2`, `3` | **定義が変わったときだけ**（人が上げる） |
| **W-2** | 定義を識別する文字列 | `"counts/physical-measurement"` | 同上 |
| **W-3** | **定義文書の SHA** | `"6683ee1"` | **文書に触れるたび**（M-2: 24 時間で 5 回） |
| **W-4** | 日付 | `"2026-08-04"` | 同上（決定日を人が入れる） |

### 4.2 帰結

| 案 | 「定義が変わった」を機械判定できるか | 運用コスト | 誤検知 |
| --- | --- | --- | --- |
| W-1 | **できる**（整数の不一致） | 定義変更時に 1 箇所を +1 | 無し |
| W-2 | できる（文字列の不一致） | 命名を毎回考える | 無し |
| W-3 | できる（SHA の不一致） | **0**（自動） | **多い。M-2 より 24 時間で 5 回の偽の変更** |
| W-4 | できる | 決定日を入れる | 同日に 2 回変えると区別できない |

**W-3 は運用コストが 0 に見えるが、実測では 24 時間で 5 回変わり、定義は 0 回しか変わっていない。**
これを使うと **Slice 7 の連続 7 日観測が、typo 修正のたびに「定義が変わった」と判定して中断する。**

**W-3 が成立する条件**: 定義文書を「決定が変わるときにしか触らない」運用にする場合。
本書の実測（訂正・AC 追加・決定反映が同じファイルへ入る）はその運用になっていない。
**運用を変えれば成立するが、変えるコストの方が大きい**と判断する。

### 4.3 推奨

**推奨は W-1（整数の連番）。**

- 判定が整数の一致比較で済む
- **上げるのが人の判断なので、「定義が変わった」の意味を人が決められる**。
  これは W-3 に対する利点である。SHA は「文書が変わった」しか表せない
- 上げ忘れのリスクは残る。**合格条件で塞ぐ**（AC-72: 定義を変える PR は版を上げること）

**W-2 を併用する。** 3.3 の `definitionsLabel` がこれにあたる。人が読むためだけに使う。

## 5. 論点3: 版が変わったときに過去の記録をどう扱うか

### 5.1 選択肢

| | 案 | 内容 |
| --- | --- | --- |
| **X-1** | **遡って再解釈しない** | 過去の記録は当時の版のまま。読む側が版を見て解釈する |
| **X-2** | 遡って書き換える | 新しい定義で過去の記録を再計算して上書きする |
| **X-3** | 両方持つ | 過去の記録に新定義での値を追記する |

### 5.2 帰結

| 案 | 復元できる | 復元できない |
| --- | --- | --- |
| X-1 | 当時の記録そのもの。**「その日、当方が何を観測したか」** | 新定義で数え直した場合の値（**入力ファイルが残っていれば再計算できる**） |
| X-2 | 新定義での一貫した系列 | **当時の記録。何を観測したかが失われる** |
| X-3 | 両方 | ほぼ無い。ただし過去の status を書き換える処理が要る |

**X-2 は観測記録の改変である。** status は「その実行が何を見たか」の記録であり、
後から書き換えると**記録としての性質を失う。**

**X-3 は魅力的に見えるが、過去の status を書き換える処理が必要になる。**
書き換えの最中に失敗したら記録が壊れる。**得られるもの（系列の一貫性）に対してリスクが大きい。**

### 5.3 推奨

**推奨は X-1（遡って再解釈しない）。**

起草者は案件A の反映（`6683ee1`）と AT-10 の改訂で既に同じ方針を採っている。
**「当時の記録を残したまま、現行を別に示す」**が本プロジェクトの一貫した扱いであり、本書もそれに揃える。

**代わりに、読む側の負担を合格条件で下げる。** 版が混在する系列を読むとき、
**版の変わり目がどこかが分かる**必要がある（AC-73）。

## 6. 論点4: 版が要るのは件数だけか

### 6.1 版を持つべき候補（実測に基づく）

| 定義 | いま変わりうるか | 根拠 |
| --- | --- | --- |
| **件数の数え方** | **変わる**（#63 の決定で変わる） | 本書の起点 |
| **outcome の意味** | 変わりうる | 案件A で `failed:input-*` の粒度が決まった。A-1 で `completed:transferred` に部分入力が含まれるようになる |
| **period window** | 変わりうる | morning 05:00-12:00 / evening 20:00-23:30 は `src/service/measurements.ts:135-142` の定数。照会3 の回答次第で見直す可能性がある |
| 連続 no-data の閾値 N | 変わりうる | 案件A の AC-44 で「設定可能とし再監査時に変更できること」と決まっている |
| 同一性の許容差 | 変わりうる | #63 の AC-54。再監査（AC-65）で見直す |

### 6.2 選択肢

| | 案 | 内容 |
| --- | --- | --- |
| **Y-1** | **単一の版に束ねる** | `definitionsVersion` 1 つ。上記のどれかが変わったら上げる |
| **Y-2** | 値ごとに版を持つ | `countsVersion` / `outcomeVersion` / `windowVersion` … |
| **Y-3** | 件数だけに版を持つ | #65 の起点に限定する |

### 6.3 帰結

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| Y-1 | **判定が 1 つ。** 版が違えば「何かが変わった」と分かる | **何が変わったかは status からは分からない**（定義文書の対応表を見る） |
| Y-2 | 何が変わったかが status だけで分かる | **版が増えるほど「どの版がどの値に効くか」の判定が増える。** 新しい定義のたびに schema が変わる |
| Y-3 | 最小 | window や outcome が変わったときに同じ問題が再発する |

### 6.4 推奨

**推奨は Y-1（単一の版に束ねる）。**

> 私の AGENT.md には「例外の境界が曖昧なとき、条件を増やす前に『選ばずに全部やる』で
> 閉じられないか試す。**判断点を消すと矛盾も消える**」がある。
> Y-2 は判断点を増やす方向であり、**「この値にはどの版が効くか」という問いが恒久的に残る。**

Y-1 の欠点（何が変わったか分からない）は、**8 節の対応表で補う。**
版が違うことさえ分かれば、対応表を引いて差分を知ることができる。
**status に必要なのは「同じ定義かどうか」の判定であり、差分の中身ではない。**

## 7. 現状維持（V-0）が成立する条件

**版を持たせない選択も成立する。** ただし次のいずれかを認める場合に限る。

**(a) #63 の実装を諦める場合**
定義が変わらなければ版は要らない。ただし #63 で決定済みの D-5 / F-2 / E-3 が実装されないことになる。

**(b) 比較可能性を捨てる場合**
「件数の系列を日をまたいで比較しない」と決める。すると案件A の B-3（連続 N=4）と
Slice 7 の連続 7 日観測が**件数を根拠にできなくなる。**
両者は「0 件かどうか」の存否と「転記が成立したか」で判定しているので、
**厳密には件数の絶対値に依存していない。** したがって (b) は成立しうる。

> **(b) の成立範囲を正確に書く。** B-3 は「夜 window に体重があるか」の存否で判定するので、
> 同一測定が 2 件でも 1 件でも判定は変わらない（#63 の 9.1 で確認済み）。
> Slice 7 も「転記が成立した日」で数える。**したがって定義変更で直ちに壊れるのは、
> #38 の「何件読んで何件使ったか」の報告と、#54 の先方との件数比較である。**
> この 2 つを「参考値であり、日をまたいで比較しない」と位置づけるなら、V-0 は成立する。

**(a) と (b) のどちらも認めない場合、版が要る。**

## 8. 版と定義の対応表（本書が正本）

**この表を版の正本とする。** status の `definitionsVersion` はこの表の行を指す。

| 版 | 期間 | 件数の数え方 | outcome | window | 同一性 | 備考 |
| --- | --- | --- | --- | --- | --- | --- |
| **1** | 〜#63 実装前 | **公開レコード単位**。`readLineCount` / `windowedReadingCount` は重複を含む | 案件A の決定（A-1 / `failed:input-*` 3 種） | morning 05:00-12:00 / evening 20:00-23:30 | `(measuredAt, kind, value, source)` 完全一致のみ | **版 1 の記録は現時点で 0 件**（M-1） |
| **2** | #63 実装以降 | **公開レコード単位と物理測定単位の両方**（`windowedReadingCount` と `uniqueMeasurementCount`） | 版 1 と同じ | 版 1 と同じ | 経路をまたぐ組に限り `(measuredAt, kind, value ±1e-5)` | #63 の決定（D-5 / F-2） |

**版 3 以降は、定義を変える決定のたびにこの表へ行を足す。**

> **版 1 を定義する理由**（記録が 0 件でも）: Slice 2 の実装が着地してから #63 の実装が入るまでの間に、
> **版 1 の記録が生まれる可能性がある。** 生まれなければ版 1 は「使われなかった版」として残るだけで害は無い。
> **生まれてから版を定義するのでは間に合わない**（それが #65 の起点である）。

## 9. 移行手順

### 9.1 いつから適用するか

| 段階 | やること | 前提 |
| --- | --- | --- |
| **1. いま** | status に `definitionsVersion: 1` と `definitionsLabel` を持たせる | Slice 2 の実装へ組み込む。**記録が 0 件のうちに入れる**（M-1） |
| 2. #63 の実装時 | 同じ PR で版を 2 へ上げ、8 節の表に行を足す | **定義の変更と版の更新を同じ PR に入れる**（別々にすると片方だけ入る） |
| 3. 以降 | 定義を変える PR は必ず版を上げる | AC-72 |

### 9.2 版が無い既存の記録の扱い

**現時点で該当する記録は 0 件である**（M-1）。それでも規則は決めておく。

**版フィールドが無い status は「版 0」として読む。**
版 0 は「版の概念が導入される前の記録」を意味し、**8 節の表に行を持たない。**
すなわち**定義が不明である**ことを表す。**版 1 と同じとみなさない。**

> **版 1 とみなさない理由**: 版フィールドが無い記録は、
> 「版 1 の定義で書かれた」のか「版の導入前に書かれた」のかを区別できない。
> **区別できないものを既知の版へ寄せると、まさに #65 が防ごうとしている取り違えが起きる。**

### 9.3 Slice 2 の実装への影響（後方互換）

`src/pipeline/status.ts` の `PipelineStatus` にフィールドを 2 つ足す。

- **既存の読み取り側は無い**（G-2 のとおり status は未配線）。**破壊する対象が存在しない**
- 将来の読み取り側（`doctor`、Slice 7 の観測）は、**版フィールドの欠落を版 0 として扱う**（9.2）

**したがって後方互換の作業は発生しない。** これは M-1 が成り立っているうちだけの性質である。

### 9.4 Slice 7 の連続 7 日観測が移行点をまたぐ場合

**観測期間の途中で版が変わったら、その日で連続日数を 0 へ戻す。**

理由: 連続 7 日観測は「同じ条件で 7 日連続で正常だった」ことを確認するための仕組みである。
**途中で定義が変われば、同じ条件ではない。**

> **この判定は保守的すぎるように見えるが、代替案が無い。**
> 版の異なる日を同じ系列として扱えるのは「定義変更が観測項目に影響しない」と示せる場合だけであり、
> それを示すには結局、版ごとの定義を突き合わせる必要がある。
> **自動で判定するには、8 節の表に「この版変更は観測に影響するか」の列を足すことになる。**
> 本書はそこまでやらない。**影響しない版変更でも連続日数が 0 に戻るのは、
> 観測をやり直すコストであって、誤った合格を出すよりは安い。**

## 10. 合格条件

#63 の AC-53〜65、G-3 追補の AC-66〜69 に続けて **AC-70** から採番する。

- **AC-70**: `pipeline-status.json` のトップレベルに `definitionsVersion`（整数）と
  `definitionsLabel`（人が読む文字列）が含まれること。**機械判定は `definitionsVersion` だけで行うこと**
- **AC-71**: `definitionsVersion` が本書 8 節の表の行と対応すること。
  **表に無い版が status へ書かれないこと**
- **AC-72**: **件数の数え方・outcome の意味・period window・同一性の判定・
  連続 no-data の閾値のいずれかを変更する PR は、同じ PR で `definitionsVersion` を上げ、
  8 節の表に行を足すこと。** 定義変更と版更新を別 PR に分けないこと
- **AC-73**: 版が混在する記録を読む側（`doctor` と Slice 7 の観測）が、
  **版の変わり目を報告できること**
- **AC-74**: 版フィールドを持たない status を**版 0 として扱い、版 1 とみなさないこと**
- **AC-75（負のコントロール）**: **定義を変えたのに版を上げなかった変更が、試験で落ちること。**
  8 節の表の行数と、実装が書きうる版の最大値が一致することを試験で固定する
- **AC-76**: Slice 7 の連続観測が、版の変わった日で連続日数を 0 へ戻すこと

---

## 11. この定義では捕まらないもの（範囲外の明示）

1. **版を上げ忘れたまま定義を変えること。** AC-72 と AC-75 で塞ぐが、
   **試験は「表の行数と実装の版が一致するか」しか見ない。**
   表に行を足しつつ実装の定義を変えなければ、試験は通る
2. **定義文書の記述と実装の乖離。** 版は「どの定義で数えたと主張しているか」であって、
   実装が実際にその定義どおり動いている保証ではない。**これは版の限界である**
3. **status 以外の記録の版**（ログファイル、Slice 7 の観測記録そのもの）。本書は status に限る
4. **producer 側の定義変更**。先方が出力の意味を変えた場合、当方の版は変わらない。
   照会4 と再監査ゲート（2026-09-01）で扱う

## 12. 推奨のまとめ

| 論点 | 推奨 | 主たる根拠 |
| --- | --- | --- |
| 1. どこに | **V-1（status トップレベル）+ 人が読むラベル** | 別ファイル（V-3）は status が自己完結しなくなる。定義の埋め込み（V-4）は schema 変更が入れ子になる |
| 2. 表現 | **W-1（整数の連番）** | **文書 SHA（W-3）は 24 時間で 5 回変わり、定義は 0 回しか変わっていない**（M-2） |
| 3. 過去の記録 | **X-1（遡って再解釈しない）** | 観測記録の改変を避ける。AT-10・案件A と同じ扱い |
| 4. 範囲 | **Y-1（単一の版に束ねる）** | 値ごとの版は判断点を増やす。status に必要なのは「同じ定義か」の判定だけ |
| 現状維持 | **成立するが条件付き**（7 節） | #38 の報告と #54 の比較を「日をまたいで比較しない参考値」と位置づけるなら成立する |

**いま入れる理由**: 既存記録が 0 件（M-1）なので、**移行コストが 0 である。**
Slice 2 が本番へ載った瞬間にこの性質は失われる。

> **この理由は 2026-08-04 時点の実測に依存する。** 決定が遅れて Slice 2 が先に着地した場合、
> 「移行コスト 0」は成立しない。**そのときは移行対象の件数を数え直したうえで、
> 9.2（版フィールドを持たない status を版 0 として扱う）が実際に使われることになる。**
> 規則は既に決めてあるので、遅れても定義は成立する。**失われるのは安さだけである。**
