# インストーラとアンインストーラの目標定義

**起草**: `scale2sheet_innovator_claude`（innovator ロール）
**位置づけ**: 目標定義。設計書ではない。採用案の決定は**ユーザー**が行う。設計・実装は本書の決定後に architect / programmer が担当する。

## この依頼の本当の論点

依頼は「インストーラを作る」だが、実測の結果、その手前に**決めなければ設計が分岐する問い**があることが分かった。

> **インストール後の scale2sheet は、ソースコードのチェックアウトから独立するのか、しないのか。**

現状は独立していない。`scripts/run-pipeline.sh` と launchd plist が、開発チェックアウトの絶対パスを直接埋め込んでいる。

```sh
# scripts/run-pipeline.sh
exporter="/Users/kappa/Dropbox/data/dev/scale_exporter/.build/release/scale_exporter"
scale2sheet_dir="/Users/kappa/Dropbox/data/dev/scale2sheet"
scale2sheet_bin="$scale2sheet_dir/dist/scale2sheet"
```

```xml
<!-- scripts/launchd/jp.seijin.kappa.scale-pipeline.morning.plist -->
<string>/Users/kappa/Dropbox/data/dev/scale2sheet/scripts/run-pipeline.sh</string>
<string>/Users/kappa/Library/Logs/scale-pipeline/morning.log</string>
```

つまり今の「インストール」とは、**特定の絶対パスに開発チェックアウトを永久に置き続けること**であり、実行される本体は `dist/` の中、すなわちビルド生成物置き場にある。
これは PLAN.md Ph.12 が宣言した「正式な配布形態は `bun build --compile` による単体バイナリ」という方針と正面から矛盾している。単体バイナリの利点（1ファイルで完結し、どこに置いても動く）を、運用側がまだ一度も使っていない。

**ここを決めずにインストーラを作ると、README の手作業をシェルスクリプトに書き写すだけの成果物になり、この矛盾を自動化して固定してしまう。**
逆にここを決めれば、以降の論点（配置先・実装形態・冪等性）はほぼ自動的に定まる。だから本書は、この問いを論点 A として最初に置く。

## サクセスストーリー

決定の物差しとして、達成された状態を先に言葉にしておく。合格条件（後述）はすべてこの3話から導出している。

### S-1: 導入 —「新しい Mac に移した朝、何もしなくてもシートが埋まっている」

Mac を買い替えた。リポジトリを clone してコマンドを1つ実行し、鍵ファイルを1つ置いた。
翌朝 07:00、体重計に乗った値がスプレッドシートの当日行に入っている。
その間、README を読み返していない。plist をエディタで開いていない。パスを書き換えていない。**手順を覚えていなくても導入できた。**

### S-2: 撤収 —「やめると決めたら、迷いなく止められる」

しばらく使わないことにした。コマンドを1つ実行すると、朝夕の自動実行が止まり、バイナリが消えた。
**Google の鍵とスプレッドシートの設定は残っている**。消えたもの・残ったもの・残ったものを消すコマンドが、画面に列挙されている。
半年後に再開したとき、鍵を取り直す必要はなかった。

### S-3: 更新 —「新しいビルドを入れ直しても、何も壊れない」

コードを直して入れ直した。同じインストールコマンドを何度叩いても結果は同じで、エラーは出ない。
たまたま launchd の実行時刻と重なっていたが、走っていた処理は最後まで正常に完走した。
設定ファイルは上書きされず、編集した cron 時刻もシート ID もそのまま残っていた。

### 共通して満たすべき感覚

- **手順を暗記していなくても正しく導入・撤収できる**（README を「読み物」から「参照物」に降格させる）
- **取り返しのつかない操作が、確認なしに起きない**
- **失敗したとき、何が起きたか画面で分かる**（このプロダクトの既定の失敗は 07:00 に無人で起きる。沈黙は最悪の挙動）
  - **ただし例外が1つある。**実行体そのものが失われた場合だけは、沈黙を受け入れる決定が下っている（論点 H の「検出手段の限界」参照）。この感覚は**実行体が存在するかぎりにおいて**適用される

## 論点と選択肢

各論点に、選択肢・トレードオフ・推奨・根拠・決定欄を置く。推奨は innovator の意見であり、決定ではない。

### 論点 A: インストール後、チェックアウトから独立させるか（**最重要・他の論点の前提**）

| 案 | 内容 | 帰結 |
| --- | --- | --- |
| A-1 現状維持型 | チェックアウトを所定パスに置いたまま、`dist/scale2sheet` を直接指す | 実装が最小。ただしチェックアウトを移動・削除した瞬間に朝の自動実行が黙って壊れる。`node_modules/` を消しても壊れうる |
| **A-2 独立配置型** | ビルド成果物を `bin` ディレクトリへ**コピー**し、以後チェックアウトを参照しない | Ph.12 の方針を初めて実運用に反映する。チェックアウトを消してもシートは埋まり続ける。plist の生成が必要になる |
| A-3 二段階型 | 開発機は A-1、他機は A-2 を選べるフラグ（`--dev` / `--link`） | 柔軟だが、テストすべき経路が倍になり、壊れ方が2通りになる |

**推奨: A-2。**
根拠は3つ。第一に、Ph.12 で「単体バイナリが正式な配布形態」と決めた以上、運用がチェックアウトに縛られている状態は方針の未完了分である。第二に、S-1（新しい Mac への導入）は A-1 では成立しない。ユーザーが同じ絶対パスに clone することを強制されるからだ。第三に、A-1 のままインストーラを作ると、**壊れやすい構造を自動化して固定する**ことになる。

> **決定**: [ ] A-1 / [x] **A-2 独立配置**（A-1・A-3 は却下） — 決定者: ユーザー、決定日: 2026-07-29
>
> この決定により、**A-1 を前提とした要件は本書から失効する**。以降の論点・合格条件はすべて A-2 の上で読むこと。
> 具体的には、L1 の「配置先へのコピー」・AC-02（prefix 配置）・AC-17（atomic 置換）は A-2 の帰結であり、A-1 では成立しない要件である。

### 論点 B: インストール対象の範囲

段階的に大きくなる3層。**独立した3つの案ではなく、どこまで含めるかの線引き**である。

| 層 | 内容 | 含めるか |
| --- | --- | --- |
| L1 | バイナリの配置（ビルド → コピー → 実行権限） | 必須 |
| L2 | 設定の初期化（`~/.config/scale2sheet/` 生成、鍵の**存在確認**、ログディレクトリ作成） | 推奨: 含める |
| L3 | launchd 常駐の登録（plist 生成 → 配置 → `bootstrap`） | 推奨: 含める。ただし**既定では無効、`--launchd` で明示的に有効化** |

**推奨: L1+L2+L3、ただし L3 はオプトイン。**
根拠。L2 を外すと S-1 が成立しない（鍵の置き忘れは最も起きやすい失敗であり、しかも翌朝 07:00 まで発覚しない）。ただし**インストーラが鍵を生成することはできない**（F-5、GCP コンソールでしか作れない）ので、L2 の責務は「生成」ではなく「不足の明示」である。ここを取り違えないこと。
L3 をオプトインにするのは、常駐化が**ユーザーのマシンに対する継続的な副作用**であり、コマンド1つの副産物として無言で起きるべきではないからだ。加えて F-9（`serve` との二重書き込み）があり、L3 を既定 ON にすると事故が増える。

**追加の選択肢**: L2 に「鍵の存在確認」だけでなく **疎通確認**（Spreadsheet に実際に到達できるか、当日行が見つかるか）を含める案。
これは S-1 の「翌朝まで失敗が分からない」という本質的な弱点に効く唯一の手段であり、単なる利便性ではない。詳細は論点 F。

**用語の固定（重要）**: 本書では以下の2つを**別物として厳密に区別する**。名前が混ざると合格条件が矛盾するため、設計・実装でもこの区別を維持すること。

| 名称 | 目的 | 外部通信 | 副作用 |
| --- | --- | --- | --- |
| **操作プレビュー（`--dry-run`）** | これから何をするかを列挙するだけ | **一切行わない**（Google 認証もしない） | ゼロ。**ローカルの読み取りは可**（下記） |
| **疎通試験（`doctor`）** | 認証と Spreadsheet に実際に到達できるかを確かめる | **行う（読み取りのみ）** | 外部への書き込みゼロ・ローカル変更ゼロ |

**読み取りは副作用ではない（2026-07-29 追記）**。architect からの指摘により境界を明確にする。
`--dry-run` が「何をするか」を正確に述べるには、**現在の状態を知る必要がある**。plist が既にあるか、label が既に読み込まれているかが分からなければ、「登録する」と「既に登録済みなのでスキップする」を区別できない。
したがって禁止するのは**状態を変える操作**であり、状態を読む操作ではない。

| 操作 | `--dry-run` での可否 |
| --- | --- |
| ファイル・ディレクトリの `stat` / 読み取り | **可** |
| `launchctl print`（登録状態の照会） | **可** |
| `launchctl bootstrap` / `bootout` / `enable` / `kickstart` | **不可** |
| ファイルの作成・変更・削除 | **不可** |
| Google 認証・外部 API 通信（読み取りを含む） | **不可**（疎通試験の領分。`--dry-run` は外部へ一切出ない） |

外部通信だけは読み取りでも禁止する。ローカルの読み取りと違い、**認証情報を使い、相手側にアクセス記録を残し、ネットワーク断で失敗しうる**からである。`--dry-run` はネットワークを遮断した環境で成功しなければならない（AC-19）。

> **決定**: 含める層 [ ] L1のみ / [ ] L1+L2 / [x] **L1+L2+L3（L3 は `--launchd` オプトイン＝既定 OFF）** / [ ] L1+L2+L3（L3 既定 ON） — 決定者: ユーザー、決定日: 2026-07-29

### 論点 C: バイナリの配置先

| 案 | 内容 | 帰結 |
| --- | --- | --- |
| **C-1 `~/.local/bin`（推奨）** | ユーザー領域 | `sudo` 不要。単一ユーザーの launchd（`gui/$(id -u)`）と権限モデルが一致する。PATH に無い環境がある |
| C-2 `/usr/local/bin` | システム領域 | 最初から PATH にある。`sudo` が要る。ユーザー単位の launchd 常駐と権限の粒度が食い違う |
| C-3 `~/.config/scale2sheet/bin` | 設定と同居 | アンインストールが1ディレクトリの削除で済む。慣習から外れ、手で叩きにくい |
| C-4 選択可能 | `--prefix` で指定、既定は C-1 | 柔軟。アンインストーラが**配置先を記憶する必要**が生じる |

**推奨: C-1 を既定とし、C-4 の `--prefix` を用意する。**
根拠。このプロダクトは**単一ユーザーの個人データ**（体重・血圧）を扱い、launchd も `gui/$(id -u)` のユーザー単位で動く。ここだけシステム全体に置くのは権限モデルの不一致であり、`sudo` を要求する分だけ S-1 の摩擦が増える。

`--prefix` を許すなら、アンインストーラは配置先を推測してはならない。**インストール時に何をどこへ置いたかの記録（マニフェスト）を残す**設計が必要になる（合格条件 AC-10）。これは C-4 を選ぶ場合の必然的なコストなので、決定時に織り込むこと。

> **決定**: [ ] C-1固定 / [x] **C-1 既定 + `--prefix` + マニフェスト** / [ ] C-2 / [ ] C-3 — 決定者: ユーザー、決定日: 2026-07-29
>
> `--prefix` を許すため、**マニフェスト（何をどこへ置いたかの記録）が必須**になる（AC-10）。これは C-4 を選んだことの必然的なコストであり、設計で落とさないこと。

### 論点 D: 実装形態

| 案 | 内容 | 帰結 |
| --- | --- | --- |
| D-1 シェルスクリプト | `scripts/install.sh` / `uninstall.sh` | 素直。ビルド前でも動く。**vitest の対象外**になり、このリポジトリのテスト資産が効かない。既存 `run-pipeline.sh` と同じ流儀 |
| D-2 npm script | `npm run install:local` | 開発者には自然。`npm` 前提になり、単体バイナリを配った先では使えない |
| D-3 Makefile | `make install` | Unix の慣習に合う。このリポジトリに Make の文化がない |
| **D-4 バイナリ自身のサブコマンド（推奨・追加案）** | `scale2sheet install` / `scale2sheet uninstall` / `scale2sheet doctor` | 下記 |

**推奨: D-4 を主経路とし、ビルドと初回配置のみを担う極薄の `scripts/install.sh` を添える。**

D-4 は依頼書の選択肢リストに無かったので、innovator として追加する。利点が構造的だからである。

1. **パス問題が消える**。バイナリは自分の位置を知っている（`process.execPath`）。ハードコードもテンプレート置換も要らない。論点 A の根本原因が実装レベルで解消する
2. **テストできる**。TypeScript なので既存の vitest スイートに載る。シェルスクリプトのままでは、インストーラだけがテストされない部品として残る（`run-pipeline.sh` が現にそうなっている）
3. **配布物と一致する**。Ph.12 が「正式な配布形態は単体バイナリ」と決めた以上、インストール手段がその1ファイルの中にあるのが筋が通る。バイナリを1つ受け取った人が、リポジトリ無しで導入・撤収できる
4. **`doctor` が同居できる**。設定検証・鍵確認・疎通確認を、本体の設定読み込みコードを再利用して書ける。シェルで書くと JSON 解析と Google 認証を二重実装することになる

コスト（正直に記す）: バイナリが存在しない初回だけは D-4 を使えないので、**ブートストラップ（`git clone` → ビルド → 初回配置）には最小限のシェルが要る**。つまり D-4 は D-1 を完全には置き換えず、`install.sh` は「ビルドして `scale2sheet install` を呼ぶ」数行に痩せる。この二段構えを許容できるかが判断点である。

> **決定**: [ ] D-1 / [ ] D-2 / [ ] D-3 / [x] **D-4 + 極薄 D-1**（バイナリ自身の `install` / `uninstall` / `doctor`、初回ブートストラップのみシェル） — 決定者: ユーザー、決定日: 2026-07-29

### 論点 E: アンインストール時、設定・認証情報・ログをどうするか

**この論点だけは、他と性質が違う。取り返しがつかないからである。**

| 対象 | 消した場合の復旧コスト | 推奨既定 |
| --- | --- | --- |
| バイナリ | 再ビルドで即復旧 | **消す** |
| launchd plist + 登録 | 再インストールで即復旧 | **消す** |
| `~/Library/Logs/scale-pipeline/` | 復旧不能だが実害は小さい | **残す**（`--purge` で消す） |
| `~/.config/scale2sheet/settings.json` | 手で書き直せる（シート ID の調べ直しは面倒） | **残す**（`--purge` で消す） |
| `google-sheets-service-account.json` | **GCP コンソールでの再発行が必要。ローカルでは復旧不能** | **残す**（`--purge --yes` でのみ消す） |
| `google-fit-*.json` / トークン | 再認証が必要 | **残す**（同上） |

**推奨: 既定は「実行を止め、実行体を消す。データは残す」。破壊は `--purge` で明示的に、かつ対話確認つき。**

根拠。S-2 が語るのは「やめる」であって「無かったことにする」ではない。半年後に再開する可能性が普通にある個人ツールで、既定を破壊側に倒す理由がない。とりわけサービスアカウント鍵は、削除するとユーザーがこのマシンだけでは復旧できない（F-5）。**ローカルで復旧できないものを既定で消してはならない。**

**混同してはならない点を1つ明記する。**
鍵ファイルの削除は**アクセス権の失効ではない**。サービスアカウントは依然としてスプレッドシートの共有先に残り、鍵は GCP 側で有効なままである。完全に縁を切るには GCP コンソールでの鍵失効とシート共有解除が要る。
アンインストーラはこれを**実行できない**が、`--purge` 時に**残作業として画面に明示する責任がある**。ここを黙ると、ユーザーは「消えた」と誤解したまま権限を残すことになる。これはセキュリティ上の実害である。

**取り消し可能性についての追加案**: `--purge` は削除の代わりに `~/.config/scale2sheet.removed-<timestamp>/` へ**退避**する案。
不可逆操作を可逆にでき、実装は `rm -rf` と大差ない。ただし「消したつもりのシークレットがディスクに残る」ため、**セキュリティ目的の削除としては不適**である。既定を退避、`--purge --wipe` で真の削除、という二段が最も安全と考えるが、複雑さと引き換えになる。ここはユーザーの判断を仰ぐ。

> **決定**: 既定の破壊範囲 [x] **実行体のみ削除・設定と認証は残す** / [ ] ログも削除 / [ ] 全削除 — 決定者: ユーザー、決定日: 2026-07-29
> `--purge` の挙動 [ ] 即削除 / [ ] 退避（可逆） / [x] **退避を既定・`--wipe` で真削除**（設計書の採番では **P-3**） — 決定者: ユーザー、決定日: 2026-07-29
>
> `--purge` は設定・認証を**タイムスタンプ付きディレクトリへ退避**する。真の削除は `--wipe` を重ねたときだけ行う。
> **ユーザーの理由**: GCP 鍵はローカルで復旧不能であり、誤操作による損失を防ぐ。

> セキュリティ目的で確実に消したい場合は `--wipe` が必要であり、その区別を利用者に明示すること（AC-13・AC-12 と併せて設計へ落とす）。

### 論点 F: 冪等性と、実行中の launchd ジョブの扱い

再実行の安全性は「気をつけて書く」では担保されない。**壊れ方が具体的に分かっているものが5つある**ので、合格条件として名指しする。
（起草時は F-a〜F-d の4つだった。レビューで F-e が追加された経緯は「実行中 job の扱い」に記す。）

| # | 具体的な壊れ方 | 必要な対処 |
| --- | --- | --- |
| F-a | 既に読み込まれた label に `launchctl bootstrap` すると失敗する（`Load failed: 5: Input/output error` 等） | 登録前に `bootout` を試み、失敗を許容してから `bootstrap` する。**ただし実行中の job がある場合は F-e に従う** |
| F-b | 実行中バイナリを `cp` で直接上書きすると `ETXTBSY` や実行中プロセスの破壊を招きうる | **一時ファイルへ書いてから `mv`（rename は atomic）**。走行中プロセスは旧 inode を保持したまま完走する |
| F-c | 再インストールで `settings.json` を上書きすると、編集済みの cron 時刻・シート ID が消える | **既存の設定ファイルは絶対に上書きしない**。存在しない場合のみ生成（F-4 の本体機能に委ねる） |
| F-d | `serve` 稼働中に launchd を登録すると二重書き込みになる（F-9） | インストール時に `serve` プロセスを検出し、**警告して中断**（`--force` で続行可） |
| **F-e** | **`bootout` は実行中の job を停止させる。**F-a の対処をそのまま適用すると、走行中のパイプラインが途中で殺され、S-3 の「走っていた処理は最後まで完走した」が破れる | 下記「実行中 job の扱い」に従う |

F-b は S-3 の「走っていた処理は最後まで完走した」を成立させる技術的核心であり、`cp` と `mv` の差が結果を分ける。設計時に落とさないこと。

#### 実行中 job の扱い（F-e・2026-07-29 追記）

**この論点の表題は「冪等性と、実行中の launchd ジョブの扱い」でありながら、起草時の F-a〜F-d は後半をまったく扱っていなかった。**
reviewer_codex と reviewer_claude が独立に同じ穴を指摘した。構造的な見落としなので、ここで正面から埋める。

問題を正確に述べる。**F-b（atomic な `mv`）だけでは S-3 は守れない。**
`mv` はファイル差し替えの安全性を担保するが、走行中プロセスを殺すのは `mv` ではなく `bootout` である。プロセスが旧 inode を保持したまま完走できても、その前に launchd に停止させられれば意味がない。
**S-3 を破るのは、ファイル操作ではなく launchd 操作の方だった。**

| 案 | 内容 | 帰結 |
| --- | --- | --- |
| F-e-1 無条件 `bootout`（起草時の暗黙の前提） | 実行中かどうかを見ずに停止して再登録する | 実装が単純。**S-3 を破る。**朝 07:00 の転記中に再インストールすると、その日のデータが欠測しうる |
| **F-e-2 検出して中断（推奨）** | 実行中の job を検出したら **`bootout` せずに中断し、警告する**。`--force` で停止続行を許す | S-3 を守る。ユーザーは待つか `--force` を選べる。F-d（`serve` 検出）と挙動が揃い、覚えることが増えない |
| F-e-3 完了を待つ | 実行中なら終了までブロックしてから `bootout` | 親切に見えるが、待ち時間の上限が読めない（exporter のリトライだけで最大2分超）。無人実行と重なると長時間ハングしうる |
| F-e-4 停止せず plist だけ差し替える | 次回起動から新設定が反映される | 停止しないので S-3 を守るが、**「インストールしたのに反映されていない」という別の混乱**を生む。反映時点が暗黙になる |

**推奨: F-e-2。**
根拠。第一に、S-3 の要求は「処理が完走すること」であって「即座に更新が反映されること」ではない。中断して警告すれば、走行中の処理は完走する。
第二に、F-d が既に「稼働中プロセスを検出したら警告して中断、`--force` で続行」という型を持っている。同じ型を使えば、**ユーザーが覚える規則が1つで済む**。
第三に、F-e-3（待つ）は待ち時間の上限を保証できない。無人運用のツールで、インストールコマンドが数分ハングするのは受け入れがたい。

F-e-2 を採る場合の `--force` の扱いも述べておく。**`--force` は「S-3 を意図的に放棄する」宣言**であり、その旨を実行時に表示すべきである（走行中の処理を停止すること、当日のデータが欠測しうることを明示する）。黙って停止してはならない。

> **決定**: [ ] F-e-1 / [x] **F-e-2 検出して中断** / [ ] F-e-3 / [ ] F-e-4 — 決定者: ユーザー、決定日: 2026-07-29
>
> 実行中を検出したらインストールを**中断**し、「いま転記中なので後で再実行してほしい」と伝える。走っている処理は完走させる。
> **ユーザーの理由**: S-3 を放棄しない。人が再実行する手間より、転記が中途半端に切れるリスクを避ける方を採る。朝夕の短い実行窓を避ければ実際にはほとんど遭遇しない。
>
> これに伴い AC-37・AC-38 が有効な条件として確定する。

**推奨: 上記5つすべてを合格条件に含める。加えて操作プレビュー（`--dry-run`）と疎通試験（`doctor`）を、別の機能として両方必須とする。**

この2つを**必ず別コマンド／別フラグに分ける**。同じ `--dry-run` に両方を負わせると、「副作用ゼロ」と「外部 API に到達する」が同時に要求され、合格条件が自己矛盾する。目標側で要求する副作用契約は以下のとおり。

**操作プレビュー `--dry-run`（install / uninstall 共通）**

- 行うこと: 実行予定の操作（配置先パス・生成する plist・`launchctl` の呼び出し・削除対象）を列挙する。**現在状態の読み取りは行ってよい**（ファイルの `stat`、`launchctl print`）。「登録する」と「登録済みなのでスキップする」を区別するために必要だからである
- 行わないこと: ファイルの作成・変更・削除、**状態を変更する `launchctl` サブコマンド**（`bootstrap` / `bootout` / `enable` / `kickstart` 等）、**Google への認証、Spreadsheet を含むあらゆる外部 API への通信**（読み取りを含む）
- 認証ファイルの扱いは**存在確認（ローカルの stat）まで**。読み込んでトークンを取得しない

**疎通試験 `doctor`（独立した経路）**

- 行うこと: 認証情報の読み込み、Google への認証、対象 Spreadsheet の**読み取り**（アクセス可能か・対象シートが存在するか・当日行が特定できるか）
- 行わないこと: **Spreadsheet への一切の書き込み**（セル更新・行追加・シート作成）、ローカル設定の変更、launchd への操作
- 失敗時は、到達できなかった段階（鍵不足／認証失敗／シート未共有／当日行なし）を切り分けて報告する
- 実行は**ユーザーの明示的な起動時のみ**。インストールの副産物として自動実行しない（外部通信は無言で起きるべき副作用ではない。論点 B で L3 をオプトインにしたのと同じ理由）

疎通試験を必須と考える理由は、このプロダクトの失敗が**無人の朝に沈黙して起きる**からである（F-8 が macOS 通知という OS 完結の検知を用意しているのと同じ理由）。インストール直後にその場で疎通を確認できないなら、S-1 は「翌朝を待って祈る」体験になる。
一方、操作プレビューが必須なのは別の理由による。これは**破壊的操作（特にアンインストール）を実行前に点検する手段**であり、外部到達性とは無関係に要る。目的が違うので、片方が他方を代替しない。

なお `doctor` をどのコマンド名・どの実装形態に置くかは設計判断であり、本書では決めない（論点 D で D-4 を採れば本体サブコマンド、D-1 なら別スクリプトになる）。目標として要求するのは、**上記2つの副作用契約が守られた形で両機能が存在すること**である。

> **決定**: [x] **F-a〜F-e + `--dry-run`（副作用ゼロのプレビュー）+ `doctor`（読み取りのみの疎通試験）すべて必須** / [ ] `--dry-run` のみ / [ ] F-a〜F-d のみ / [ ] 個別に取捨 — 決定者: ユーザー、決定日: 2026-07-29
>
> 論点 D で D-4（`install` / `uninstall` / `doctor` をバイナリのサブコマンドとする）が決定したことにより、`doctor` の存在も併せて確定した。F-e の扱いは後述の決定欄を参照。

### 論点 G: そもそも作らないという案

依頼書が「除外してはならない」と指定した選択肢。真面目に評価する。

**「作らない」で足りるか — 結論: 足りない。ただし理由は利便性ではない。**

README には既にインストール・アンインストール手順が書かれている（バイナリのビルド、plist のコピー、`launchctl bootstrap`、削除手順）。手順は短く、実際に運用できている。手順書を厚くするだけで足りる、という主張には一定の説得力がある。

#### 自己参照の限界 — 「実行体の不在」は実行体自身では通知できない

architect（`scale2sheet_architect_codex`）から、AC-28 と H-2 が両立しないとの指摘を受けた（2026-07-29）。**指摘は正しい。**
H-2 では launchd がバイナリを直接起動するため、**そのバイナリが欠落・実行不能なら、通知するコードも起動できない**。

まず正確に言うと、これは H-2 が持ち込む新しい欠陥ではない。現行の H-1 構成でも、`run-pipeline.sh` 自体が消えれば同じく無言で失敗する。
**通知できる主体は、自分より下流の失敗だけを通知できる。**起動主体そのものの不在は、常に一段外側からしか観測できない。H-2 はその境界を「スクリプト」から「バイナリ」へ1つ動かすだけである。

したがって取りうるのは次の2つで、**本書は (1) を採る。**

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **(1) 目標例外として認める（採用・ユーザー決定）** | H-2 では「バイナリ不在・実行不可」の通知を構造的に持たないことを認める。**代替の自動検出手段は用意しない**（当初は stderr と `doctor` を代替に想定したが、後述のとおり両方とも機能しない） | 限界を正直に認めたうえで、単純さを優先できる |
| (2) 極薄ランチャー経由にする | `/bin/sh` などを launchd の起動主体にし、exit 126/127 を捕えて通知する | 却下。H-2 の「バイナリを直接呼ぶ」利点（パス独立性・単一配布物）を損ない、**そのランチャー自身の不在は依然検知できない**。限界が一段ずれるだけで消えない。加えて H-3（併存）と同じく実装が二重化する |

(2) を却下する決め手は、**問題が解決しないこと**である。検知できない対象がバイナリからランチャーへ移るだけで、代わりにチェックアウト非依存という A-2 の成果を一部手放す。交換として釣り合わない。

代わりに、以下を合格条件として要求する。**これらは「バイナリが存在するケース」に限って有効な条件であり、欠落時の代替検出経路ではない**（そのような経路は存在しない。下記「検出手段の限界」参照）。

#### 検出手段の限界 — できないことを明示する（2026-07-29 追記）

**当初、本書は「検出は launchd stderr と `doctor` に委ねる」と書いた。reviewer_codex の指摘により、それが誤りであることが判明した。**
以下は限界の記録であり、実装で解消すべき課題ではない。ユーザーはこの限界を理解したうえで、直接起動とバイナリ1つという単純さを選んでいる。

| 当初の想定 | 実際 |
| --- | --- |
| launchd の `StandardErrorPath` に起動失敗の痕跡が残る | **残る保証はない。**`StandardErrorPath` は job 自身の stderr であり、実行体を spawn できなかった場合のエラーはそこへは流れない。AC-34 が担保するのは**実行体が起動できた後**の失敗のみ |
| `doctor` で欠落に気づける | **気づけない。**`doctor` は欠落したのと**同一バイナリのサブコマンド**である。バイナリが無ければ `doctor` も起動しない |
| `doctor` が「動いていないこと」を教えてくれる | **教えない。**AC-36 は最後に成功した実行を報告するだけで、**期待時刻の超過を判定しない**。「今朝も動いていない」という能動的な判断は行わない |

Issue #49のbounded stable snapshotにも、解消できない限界がある。

| 暫定防御で確認すること | 確認できないこと |
| --- | --- |
| 5秒間と読取前後でfile集合、device、inode、size、mtimeが一致する | producerが完全なJSONL行の境界で5秒を超えて停止し、その後同じfileへ追記すること |
| その時点で列挙できた全fileをstrict parseできる | 複数file batchの後続fileがsnapshot後に公開されること |
| 対象日fileが存在する | producerが完了したこと、または正当なno-data日であること |

このためAC-26はatomic publicationまたはbatch完了を保証しない。
対象日file不在を失敗にする決定は、「正当なno-data日にもfileを公開する」という合意済みproducer契約がない状態で、偽陽性を許容する暫定判断である。
Issue #37が求めたproducer失敗と正当な0件の完全な識別は達成しない。
ユーザーが決定したのは「入力fileが存在しなければその日は失敗でよい」という範囲だけである。
fileが存在して0件だった場合の区別要否は、B-1 + B-3（N=4）で暫定的に扱う。本書は終了コードでproducer失敗と正当な未測定を区別せず、三つの件数の重複単位は Issue #63 の決定後に確定する。
完全な識別は先方の公開完了契約に依存する。

最初のproduction `failed:input-missing`、`failed:input-unstable`、`failed:input-invalid-or-partial`のいずれか、第二writer、新source、schema version追加前、または2026-09-01 23:59 JST到来のうち最初の時点で、pmはmanager間の契約監査を起票する。
期限後も現行pipelineは自動停止しないが、scope拡張を止め、暫定契約を恒久契約へ読み替えず、ユーザーへ継続リスク受容か契約実装かを再提示する。
immutable batch、atomic completion manifest、producer共通排他は当方の将来要求案であり、先方との合意済み契約ではない。

**したがって、バイナリ欠落時の検出手段は次の1つだけである。**

> **スプレッドシートに行が増えていないことに、人が気づく。**

これが唯一の検出手段であることを、設計・実装・README のいずれでも**言い換えたり補強したように書いたりしてはならない**。
「検出できる」と書いて実際は検出できない状態が、最も危険である。気づくのが遅れることそのものより、気づけると誤認させることの方が害が大きい。

**AC-33・AC-34・AC-36 は削除せず残す。**これらは**バイナリが存在する**ケース——実行体はあるが設定が壊れている、認証が切れている、シート ID が誤っている、権限が落ちている——では有効に機能するからである。
無効なのは「バイナリそのものが無い」場合に限られる。適用範囲を各条件に明記したのはそのためである。

> **決定**: [x] **(1) 目標例外として認める** / [ ] (2) 極薄ランチャー経由 — 決定者: ユーザー、決定日: 2026-07-29
>
> **決定の内容**: launchd はバイナリを直接起動する。シェルラッパは持たず、配布物はバイナリ1つを維持する。監視用の別ジョブも増やさない。
> **バイナリ自体が欠落・実行不能な場合の失敗通知は AC-28 の例外とし、通知を要求しない。**
>
> **この決定は「検出手段なしを受け入れる」ことを含む。**当初は launchd の stderr と `doctor` を代替の検出手段として想定していたが、上表のとおり**どちらも欠落時には機能しない**ことが判明した。
> それを踏まえて再度ユーザーへ諮り、**そのままでよい**との再決定を得た（同日）。**代替の自動検出手段は用意しない。**
>
> **例外の範囲は欠落時のみ**である。バイナリが存在する状態での失敗（API エラー、認証切れ、シート転記失敗など）は**従来どおり通知する**。ここを広げて解釈しないこと。
>
> **ユーザーが了解済みのトレードオフ**: バイナリが消えると朝の転記が黙って止まり、気づく手段は人がシートを見ることだけになる。
> ユーザーは検出可能性より**直接起動・バイナリ1つの単純さ**を優先した。この決定を「気づく仕組みが別にある」と読み替えてはならない。

| --- | --- |
| AC-06（`launchctl print` で登録済みを確認） | launchd は `HOME` の差し替えでは隔離されず、**実ユーザーの本番 label を自動テストで登録・解除してはならない**。したがって (a) 本番と衝突しない**一時 label**（例: `...scale-pipeline.test.<pid>`）を用いた自動テスト、または (b) **生成された plist の内容と、`launchctl` を呼ぶ層（adapter）が正しい引数を組み立てたことの検証**を代理指標として認める。本番 label での確認は**手動試験**とし、その旨を受け入れテスト記録に残す |
| AC-03（チェックアウト移動後も launchd 経路が成功） | 同上。plist に**チェックアウト由来のパスが含まれないこと**の検査を自動化し、実 launchd での通し実行は手動試験とする。A-2 の本質は「参照が無い」ことなので、代理指標で本質を捉えられる |
| AC-24（疎通試験の実到達） | 実際の外部到達を伴うため自動テストの対象外。手動確認、またはモックによる副作用契約（書き込みを行わないこと）の検証とする |
| AC-35（登録直後の実行可能性確認） | 確認自体は**インストーラのプロセス内で完結**するため、実 launchd を要さず隔離環境で自動検証できる。実 launchd での登録を伴う部分は AC-06 と同じ扱い（一時 label または代理指標） |
| AC-37・AC-38（実行中 job の扱い） | 実 launchd で job を走らせた状態を自動テストで作るのは危険かつ不安定。**「実行中である」という判定を返す層（adapter）を差し替えた検証**を代理指標として認める。実 job での確認は一時 label による手動試験とする |
| AC-27・AC-28（macOS 通知の発火） | 実際の通知表示は自動検証しない。AC-31 のとおり「通知が要求されたこと」を検証できる形にする |
| AC-33（`doctor` の異常検出） | **バイナリが存在するケースのみ**が検証対象である（設定破損・認証切れ・権限不足などを仕込んだ隔離環境で自動検証できる）。バイナリ欠落時は適用範囲外であり、**検証しない**（`doctor` 自体が起動しないため、テストすべき挙動が存在しない） |
| AC-34（launchd 経路の stderr 記録） | 検証対象は **plist に出力先が正しく設定されていること**（自動検証可）。実際に launchd がその先へ書くこと、および spawn 失敗時の挙動は**検証しない**（後者は担保していない。「検出手段の限界」参照） |
| AC-36（直近の転記の報告） | バイナリが存在する状態での報告内容を隔離環境で自動検証する。**期待時刻の超過判定は要件に含まないため、検証もしない** |

**代理指標を認めるにあたっての条件**: 代理指標で置き換えた条件は、`docs/ACCEPTANCE_TEST_REPORT.md` に**「自動」「代理指標」「手動」のいずれで確認したかを明記**すること。ここを曖昧にすると、手動試験が実施されないまま合格と記録される。

## 非目標（今回やらないと明示するもの）

境界を引かないと、インストーラは際限なく育つ。

- **Homebrew tap / パッケージマネージャ対応**。利用者が実質1名の段階では配布インフラの維持コストが見合わない。ただし論点 A で A-2 を選べば、将来の tap 化の前提条件は満たされる
- **scale_exporter のインストール**。別プロジェクトであり、チーム境界を越える（下記エスカレーション参照）
- **GCP プロジェクト・サービスアカウント・OAuth クライアントの自動作成**。ブラウザ操作と課金アカウントの選択を伴い、自動化の適地ではない
- **macOS 以外への対応**。launchd 前提であり、現時点で需要がない
- **自動アップデート機能**。インストーラの再実行で足りる（AC-15）

## pm へのエスカレーション事項

innovator の判断だけでは閉じない点。**決定前に確認が要る。**

### E-1: scale_exporter への依存をどう扱うか（要・他チーム確認）

`run-pipeline.sh` は scale_exporter の Swift バイナリを絶対パスで呼ぶ（F-7）。
scale2sheet だけをインストールしても、**scale_exporter が所定パスに無ければ朝の自動実行は毎回失敗する**。S-1（新しい Mac に導入して翌朝動く）は、scale2sheet 単体のインストーラでは成立しない。

取りうる立場は3つ。

1. インストーラは scale_exporter の**存在確認のみ**行い、無ければ警告する（推奨。境界を越えず、S-1 の失敗を沈黙させない）
2. exporter のパスを `settings.json` の設定項目に昇格させ、ハードコードをやめる（設計変更を伴う。architect 案件）
3. 何もしない（S-1 が成立しないことを受け入れる）

**確認したいこと**: scale_exporter 側にもインストーラ整備の計画があるか。あるなら「両者が同じ配置規約（`~/.local/bin`）に従う」ことを先に合意したい。**pm 経由で scale_exporter チームの pm へ照会をお願いしたい。**

### E-2: `build` → `build:node` 改名との依存（architect と直接調整する）

pm から共有のあった改名案件は、本件と**同じ場所を触る**。インストーラがビルドを呼ぶ以上、スクリプト名の変更は直撃する。
本書の論点 D で D-4（サブコマンド）を採る場合、インストーラ側が `npm run` に依存するのは初回ブートストラップの数行だけになり、結合は最小化される。

architect（`scale2sheet_architect_codex`）と直接すり合わせ、次の境界で合意した（2026-07-29）。

- **インストーラの正式ビルド経路は `npm run build:bun`**（単体バイナリ生成）。改名対象の `build` → `build:node` は Node.js 開発用 `tsc` emit であり、インストーラの正式経路とは交差しない
- したがって**本書の合格条件はビルドスクリプト名に依存しない**。インストーラが `npm run` を呼ぶのは初回ブートストラップの1箇所のみで、そこが参照するのは `build:bun` である
- 改名検討書はユーザー決定前のため未確定。本書側で確定させることはしない

### E-3: 決定の順序についてのお願い（**解消済み・2026-07-29**）

起草時のお願いは「論点 A を最初に決めていただきたい」だった。A が決まらないと B・C・D・G の選択肢の意味が変わり、規模が一桁違ったためである。

**このお願いは満たされた。**論点 A は A-2（独立配置）に決定し、それに伴って論点 E・AC-28 の例外も決定した。
以降、本件の規模は「配置規約とマニフェストを持つサブコマンド群」で確定であり、A-1 を前提とした縮小案（plist のパス置換のみ、20 行程度）は失効している。

**その後、論点 B・C・D・F・G・H および `--purge` の挙動もすべて決定した（いずれも 2026-07-29、決定者ユーザー）。本書に未決定の論点は残っていない。**

## 推奨案のまとめ（1行ずつ）

ユーザーが最短で判断できるよう、推奨をまとめる。

| 論点 | 推奨 | 一言の理由 |
| --- | --- | --- |
| A 独立性 | **A-2 独立配置** | Ph.12 の「単体バイナリが正式形態」を運用に反映する未完了分 |
| B 範囲 | **L1+L2+L3（L3 は `--launchd` オプトイン）** | 常駐化は無言で起きるべき副作用ではない |
