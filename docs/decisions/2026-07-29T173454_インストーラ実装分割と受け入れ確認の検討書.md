入力の正本は次のとおりである。

## 分割時に守る条件

実装の分け方にかかわらず、次の条件を固定する。

1. 各 PR は、直前の PR が main へマージされた後の main から作る。
2. 複数 PR を同時に積む stacked PR は使わない。
3. 各 PR は、単独でテストが通り、既存の本番 launchd を変更しない状態でマージできるようにする。
4. `install` と既定 `uninstall` は同じ PR に置く。
5. 内蔵 pipeline が手動実行で検証できるまでは、既存 `run-pipeline.sh` を本番経路から外さない。
6. `scripts/run-pipeline.sh` と旧静的 plist の削除は、production 切替後の連続7日観測を終えた別 PR で行う。
7. 各 PR は `docs/ACCEPTANCE_TEST_REPORT.md` の installer AC 節を更新する。
8. manual または代理指標が必要な AC を、自動テストだけで `PASS` にしない。
9. 実装 branch の開始条件は、clean な作業ツリーで基準 main SHA を取得できることである。
10. 利用者の既存 `package-lock.json` 変更、stash、認証情報、launchd 登録を実装準備のために変更しない。

### scale_exporterとの責任境界

`scale_exporter` は測定データ取得、JSONL出力、自身の設定、認証、バイナリ、LaunchAgentを所有する。
`scale2sheet` は自身のlaunchd、朝夕スケジュール、JSONL読取、Spreadsheet転記、pipelineを所有する。

連携は公開JSONL出力契約に限定する。
各Sliceは `jp.seijin.kappa.scale-exporter` と先方の設定、認証、バイナリを作成、変更、診断、登録解除、削除しない。
`scale-exporter-output-dir` は当方の消費側設定であり、その参照先へinstall、uninstall、purge、wipe、archiveを適用しない。

ユーザーは2026-08-03に案Aと案Zを採用した。
先方scheduleとiPhoneショートカットがJSONLを公開し、当方pipelineはproducerを起動せず、公開入力の安定性を暫定確認して消費する。
Slice 1のrun leaseは当方processだけを排他し、producerとの共通排他を提供しない。
現行producerにatomic publication、batch完了manifest、複数fileの一括完了がない限界を受け入れ、後述のbounded stable snapshotをSlice 2の最小防御とする。

`install` と既定 `uninstall` を分けない理由は、両者が manifest の `installing | installed | uninstalling` 状態、`created-paths`、operation algebra、executor の再実行契約を共有するためである。
片方だけを先に実装すると、後続 PR が manifest schema と失敗復旧順序を変更し、先行 PR の受け入れ結果を無効にする。

## 実装分割の選択肢

### 案 I：単一 PR

一つの PR に foundation、pipeline、install、uninstall、doctor、purge、distribution を入れる。

| 評価軸 | 評価 |
| --- | --- |
| 利点 | 中間状態を公開せず、一度で機能を揃えられる |
| 欠点 | run lease、Google API 読取、不可逆操作、launchd 移行を同時にレビューするため、差分が大きくなる |
| 失敗時 | 原因箇所の切り分けと revert の範囲が広い |
| 判定 | 非推奨 |

### 案 II：コマンド別 PR

`pipeline`、`install`、`uninstall`、`doctor` の順にコマンド単位で分ける。

| 評価軸 | 評価 |
| --- | --- |
| 利点 | CLI の見た目と PR の名前が一致する |
| 欠点 | `install` と `uninstall` の共有状態機械を途中で分断する |
| 欠点 | `pipeline` と入力snapshot、PATH、plist の契約が別 PR に散りやすい |
| 判定 | 却下を推奨 |

### 案 III：依存順の capability slice

共有する不変条件を先に置き、独立に却下できる機能を後続 PR へ分ける。

| 評価軸 | 評価 |
| --- | --- |
| 利点 | kernel 排他、pipeline 保存機能、不可逆 purge を別々にレビューできる |
| 利点 | production launchd を変えずに内蔵 pipeline と lifecycle を先に検証できる |
| 欠点 | 実装 PR が6本、観測後 cleanup PR が1本になる |
| 欠点 | 各 PR を直列に進めるため、単一 PR より calendar time が延びる |
| 判定 | **採用** |

### Slice 2：内蔵 pipeline の shadow path

この PR は、production launchd を切り替えずに内蔵 pipeline を手動実行可能にする。

本Sliceは、当方pipelineがproducerを起動せず、公開JSONLだけを消費する案Aを前提とする。
Issue #38の三つの件数とIssue #49の入力安定確認をSlice 2のstatusとlogのschemaへ反映してから実装を始める。

主な成果物は次のとおりである。

- `scale2sheet pipeline --period <morning|evening>`
- bounded stable snapshotの最大3attempt、5秒間隔
- input failure と transfer failure の2段階通知
- timestamp log と `pipeline-status.json`
- 対象日に一致したfile数、読取対象行数、period window適用後のreading数
- pipeline の共通 run lease 取得と同時実行拒否
- `scale-exporter-output-dir` のread-only解決
- file集合とdevice/inode/size/mtimeを返すinput snapshot port
- clock、stat、delay fake
- PATH と ProgramArguments を組み立てる pure plist generator
- `StandardOutPath` と `StandardErrorPath`

pipeline移植、入力snapshot、PATH、plistの値生成は同じPRに置く。
ただし、plist の書込み、`launchctl bootstrap`、本番 label の変更は行わない。

三つの件数は当方単独で記録でき、「対象fileが無いため失敗した」と「fileはあるが使えるreadingが無く正常終了した」を分離する。ただし、同一物理測定が複数経路で公開された場合に何を1件と数えるかは **Issue #63 の決定後に確定**し、それまでは件数を暫定的な実測値として扱う。
未到達またはparse中断後の件数は0にせず、未計測として記録する。
producerが実行した結果として0件だった状態の完全な識別は、先方の公開完了契約に依存する。

pipeline は Slice 1 の read-only settings loader を使う。
`SCALE_EXPORTER_OUTPUT_DIR`など既存設定の「環境変数、settings、組み込み既定値」という優先順位は変えない。

launchd は対話 shell の環境変数を継承しない。
plistへproducer commandまたはその絶対パスを保存しない。
pipelineは実行時にread-only settings loaderから出力ディレクトリを解決する。

bounded stable snapshotは`INPUT_READ_ATTEMPTS = 3`、`INPUT_STABILITY_INTERVAL_MS = 5_000`とする。
各attemptで完全な対象日file集合とpath、device、inode、size、mtimeを取得し、5秒後に同じsnapshotであることを確認してから全fileをmemoryへstrict parseし、読取後の再statでも同じ集合と属性である場合だけ採用する。
入力不在、不安定、parse不能は最大3attempt後に終了コード1と入力段階通知で失敗し、転記しない。
fileが存在し、安定し、parse可能だがperiod適用後0件なら`completed:no-data`、終了コード0で転記しない。
period不正は終了コード2とし、終了コード3はSlice 2では使わない。

5秒は実測保証ではなく暫定値である。
producerが完全なJSONL行の境界で5秒を超えて停止して再開する場合と、複数fileが後から追加される場合は検出できない。
入力不在を失敗にするが、producerには正当なno-data日にもfileを公開する合意済み契約がないため、偽陽性を許容する暫定判断である。
producer失敗と利用者が測定しなかった状態を区別したとは記録しない。
producerがno-data日にfileを公開する契約はなく、入力不在の偽陽性頻度は現時点で未知である。
一方、設定済み出力ディレクトリでは2026-06-29から2026-08-03 JSTの36日間に対象日file不在は観測されず、平常運用で日常的に発火する兆候は無い。ただし一度も発火していないため、発火時にそれがproducer停止を示すかどうかは実測されていない。
file存在は正当な測定を含むことを証明しないが、入力不在を非通知にするとproducer停止が無人運用で沈黙するため、入力段階通知を要求する。長期停止時はschedule上最大4回/日の通知が起こりうる。

現行`reader.ts`が出力ディレクトリの`ENOENT`を空配列へ畳む挙動はpipelineの成功判定に使わない。
pipeline用readerは`missing | unstable | invalid | ready`を返し、`ready`のreading集合だけを転記専用APIへ渡す。
pipelineはusable row 0件を`completed:no-data`として記録し、serviceまたは転記専用APIへ委譲しない。
既存`run` / `serve` 経路では`syncMeasurements`の`Nothing was written.`経路が、present、stable、parse可能、usable row 0件の場合に引き続き到達する。
Issue #37は完全識別まで閉じず、file不在をfail-closedにする範囲をAC-30で検証する。

#### D-2：snapshotと転記の責務分離

bounded stable snapshotで検証したreadingをpipelineがperiod window、dedup、no-data判定へ通した後、既存`syncMeasurements`へ渡すだけでは、同関数がJSONLを再読して同じ判定を行う。
これではsnapshotの検証結果と転記対象が一致する保証がなく、reference timeがずれた場合にはpipelineの記録件数と実際の転記件数も一致しない。

Slice 2では、Sheets adapter呼出専用の転記APIをservice層から抽出する案を採用する。
pipelineは確定済みのreading集合をそのAPIへ渡し、転記APIは入力を再読せず、period window、dedup、no-data判定を再適用せず、渡されたreadingをSpreadsheet rowへ変換してSheets adapterを呼び出す。
したがって、snapshotから転記までのreading集合と、Issue #38で記録するwindow適用後件数・転記件数の意味を一意に保つ。

no-data判定はpipelineだけが行う。
入力失敗またはno-dataの場合は転記専用APIを呼び出さず、Sheets adapterの呼出回数も0とする。
転記専用APIの名称、引数の具体的な型、内部の分割は実装側の裁量とするが、上記の責務契約と recording fake で差し替え可能な独立境界は変更しない。

既存の`run` / `serve`経路は外形挙動を維持する。
既存`syncMeasurements`はwrapperとして残し、従来どおり自身がcollect、no-data判定、転記を行うため、AT-07 / AT-09を含む既存service・CLIテストを変更せず通過させる。
この判断は外部契約やCLIインタフェースの変更ではなく、Slice 2内部の責務分離である。

最初のproduction `failed:input-missing`、`failed:input-unstable`、`failed:input-invalid-or-partial`のいずれか、第二writer、新source、schema version追加前、または2026-09-01 23:59 JST到来のうち最初の時点で、pmはmanager間の公開契約監査を起票する。
期限後も現行pipelineは自動停止しないが、scope拡張を止め、暫定契約を恒久契約と扱わず、ユーザーへ継続リスク受容か契約実装かを再提示する。
提案するimmutable batch、atomic completion manifest、producer共通排他は当方の要求案であり、先方との合意事項ではない。

この境界により、reviewerは入力安定確認、入力/転記の2段階通知、転記抑止をproduction scheduleを変えずに判定できる。

### Slice 3：install と既定 uninstall

この PR は、manifest、planner、executor を一つの lifecycle として実装する。

主な成果物は次のとおりである。

- `model.ts`、`paths.ts`、`manifest.ts`
- `planner.ts` と `executor.ts`
- `process.ts` の launchctl adapter
- `install`
- 設定と認証を残す既定 `uninstall`
- install と uninstall の `--dry-run`
- atomic binary replacement
- Bun compiled 実行体であることの判定
- production とテストを分離する `BinaryCopySource`
- launchd の opt-in 登録と再登録
- active serve または pipeline の検出
- F-e-2 の既定中断と `install --force`

binary copy source は production では Bun compiled binary の `process.execPath` に限定する。
テストでは任意ファイルを source として直接渡さず、production 実装と明示的に分離した `BinaryCopySource` port を注入する。
production adapter は、実行体が Bun compiled binary であることを検査してから source を返す。

```typescript
interface BinaryCopySource {
  resolve(): Promise<string>;
}
```

production の `BinaryCopySource` だけが `process.execPath` を返す。
テスト用 adapter は fixture の絶対パスを返してよいが、CLI オプション、環境変数、設定ファイルから copy source を上書きできる経路は作らない。

Slice 3 では paths と manifest を含む実値で plist を再生成するため、Slice 2 で閉じた AC-07 と AC-34 を再実行する。

この PR は `doctor`、`--purge`、`--wipe` を公開しない。

## Slice ごとの完了ゲート

Slice 1〜6 のコード変更は、`npm run typecheck`、`npm test`、`npm run build:bun` の成功を共通ゲートとする。
Node.js 上の Vitest は module と adapter の契約を検査し、Bun compiled acceptance は配布実行体と macOS の kernel 境界を検査する。
一方だけで他方を代用しない。

fixtureまたはstubを使う試験は、`scale_exporter` の実設定、認証、バイナリ、LaunchAgentを作成または変更しない。
手動試験で実 `scale_exporter` を使う場合も、利用者または先方installerが導入済みであることを外部前提として記録する。

| --- | --- | --- | --- |
| Slice 1 | `APP_VERSION`、read-only settings、run lease の状態遷移、owner token、異常系 errno | macOS と APFS 上の compiled binary を別2 process で実行し、競合時の `EAGAIN \| EWOULDBLOCK` と holder の SIGKILL 後の再取得を確認 | 不要 |
| Slice 2 | input snapshot port、3attempt、5秒fake、通知要求、status、period、処理段階別件数、missingとpresent-but-zeroの区別、pure plist | 一時HOMEとJSONL fixtureを使い、compiled `pipeline`がproducer processと実networkを使わず成功または期待した入力段階で失敗し、SIGKILL後にrun leaseを再取得することを確認 | 実通知はSlice 6まで`PARTIAL` |
| Slice 3 | planner、manifest、executor、`BinaryCopySource`、dry-run、active run adapter、各中断点 | macOS と APFS 上で compiled 実行体から `process.execPath` を atomic copy し、install、既定 uninstall、再install、dry-run、別 process の active `serve` と `pipeline` を確認 | 不要 |

## ACCEPTANCE_TEST_REPORT の記録形式

既存 AT-01〜AT-18 は削除しない。
新しい `Installer AC（AC-01〜AC-38）` 節を追加する。

各行は次の列を持つ。

| 列 | 内容 |
| --- | --- |
| AC | `AC-01` から `AC-38` |
| owner Slice | 最終判定を閉じる Slice |
| 必須方式 | 自動、代理指標、手動の一つまたは複数 |
| 実施方式 | 実際に使った方式 |
| 対象 commit | 検証した full SHA |
| 実施日時 | JST の ISO 8601 |
| 証跡 | test 名、command、fixture、一時 label、ログのうち秘密情報を含まないもの |
| 判定 | `PASS \| PARTIAL \| BLOCKED \| PENDING` |
| 備考 | 適用範囲外、未実施理由、既知の限界 |

判定は次の意味で使う。

- `PASS`：必須方式をすべて満たした
- `PARTIAL`：自動または代理指標は通ったが、必須の手動確認が残る
- `BLOCKED`：必要な実機、認証、検証用 Spreadsheet を用意できず実施不能
- `PENDING`：owner Slice が未マージ、または観測期間が未完了

各 PR は、自分が追加または変更した AC 行と、既存37件のテストを含む全体サマリーを更新する。
後続 PR は以前の `PASS` を無条件に写さず、共有 module を変更した場合は関連 AC を再実行する。
secret、token、Spreadsheet ID、測定値、認証 JSON の内容を証跡へ書かない。

## run-pipeline.sh からの切替

### rollback snapshot

Slice 6 の production 操作前に、次を `~/.config/scale2sheet/rollback/<timestamp>/` へ mode `0700` で保存する。

- 切替前の repository revision
- `scripts/run-pipeline.sh`
- morning と evening の legacy plist
- 現在の installed binary の絶対パスと SHA-256
- `launchctl print` が両 label に対して成功したか
- rollback command

認証情報、settings の内容、Spreadsheet ID は snapshot に複製しない。

### 一時環境での受け入れ

production label を触る前に、次を満たす。

1. 一時 HOME、一時 prefix、一時 label、一時ログディレクトリを使う。
2. 検証用 Spreadsheet または read-only mock を使い、production Spreadsheet を変更しない。
3. morning と evening の ProgramArguments が installed binary の `pipeline` を指すことを確認する。
4. input failure と transfer failure の通知を fault injection で確認する。
5. active job 中の通常 install が中断し、`--force` だけが警告後に停止することを確認する。
6. checkout を rename した後も一時 label が起動することを確認する。

一時 label は試験後に必ず `bootout` し、一時 plist とログを削除する。

### production 切替

production 切替は repository の merge では自動実行しない。
利用者が runbook を明示的に実行する。

1. legacy process と新 run lease を検査する。
2. 実行中なら変更せず、完走後の再実行を案内する。
3. rollback snapshot の hash を再確認する。
4. legacy morning と evening label を `bootout` する。
5. installed binary と新 plist を配置する。
6. 新 morning と evening label を `bootstrap` する。
7. `launchctl print` の終了コードで両 label の登録を確認する。
8. plist が指す binary の存在、実行権限、`--version` を installer process 内で確認する。
9. いずれかが失敗した場合は新 label を両方 `bootout` し、legacy plist を戻して両 label を `bootstrap` する。

legacy と新 label を同時に登録しない。
同じ対象日へ二重転記する経路を作るためである。
production 切替では `kickstart` を使わない。

### 連続7日観測

観測初日は、production 切替後に最初の morning schedule が動く JST の暦日とする。
切替時の手動実行は観測日数へ含めない。
各暦日に、morning と evening でそれぞれ1回以上、launchd から開始した成功または正常な no-op の実行証跡が揃った場合だけ、その日を1日と数える。

毎日、次を記録する。

- launchd 起動の実行証跡
- `pipeline-status.json` の開始、完了、outcome
- Slice 2で定義した対象file数、読取行数、period window適用後件数
- 実行証跡がある run の Spreadsheet 結果
- stderr log
- OS 通知の有無

記録先は Slice 6 で作成した `docs/observations/<cutover-JST>_installer-cutover.md` とする。
観測記録には日付、period、開始元、開始時刻、終了時刻、outcome、確認者、関連する秘密情報を含まないログ参照だけを書く。
Spreadsheet ID、認証情報、測定値は記録しない。

対象日file不在は`failed:input-missing`であり、観測失敗日として連続日数を0へ戻す。
fileが存在し、安定snapshotを全行parseでき、period適用後0件ならruntimeは`completed:no-data`、終了コード0とする。
この区別はproducer失敗と利用者の未測定を識別するものではなく、正当なno-data日にもfileを公開する契約が無い間は、入力不在の偽陽性を許容する。
三つの件数とoutcomeを記録し、`matched-file-count: 0`を成功runとして扱わない。

いずれかの period に実行証跡が無い日、起動後に失敗した日、production の binary、plist、settings を変更した日、rollback した日は、連続日数を0へ戻す。
実行証跡、Slice 2の三つの件数、安定入力から実測readingを確認できたrunだけが連続日数を維持する。
present-but-zeroはruntime上code 0でも、公開完了契約が無い間は`unverified`として連続日数を0へ戻す。
公開完了契約が得られない間、連続7日を成立させるには7日間毎日、morningとevening双方でproducer供給を示す実測readingが必要になる。
暫定防御で検出不能なline境界停止または複数fileの後発公開を疑う場合は、その日を`unverified`と記録して連続日数を0へ戻し、自動検出できたとは記録しない。

rollback 条件は次の三つである。

- 実行体が起動した後の pipeline failure
- fault injection で通知要求が失われる
- 実行証跡がある転記結果に後退がある

rollback では新 production label を両方 `bootout` し、snapshot の hash を検証して legacy script と plist を戻し、両 label を `bootstrap` する。
status、ログ、settings、認証情報は削除しない。

7日連続で各日の morning と evening が上記条件を満たし、観測記録を reviewer が確認した場合だけ Slice 7 を作る。
