## 位置づけ

本書は、承認済みの目標定義と設計を、reviewer が独立に判定できる実装単位へ分ける。

入力の正本は次のとおりである。

- 最終 PR base：`21e74d2c64688ef4e3ace1f2019964f50a82fb52`
- ユーザー決定時の main：`d829630bb2bef5abbe76f793dc83949b1fa2eaca`

- 設計：`docs/INSTALLATION_DESIGN.md`
- 設計方式：`docs/decisions/2026-07-29T091044_インストーラとアンインストーラの設計方式.md`

## 分割時に守る条件

実装の分け方にかかわらず、次の条件を固定する。

1. 各 PR は、直前の PR が main へマージされた後の main から作る。
2. 複数 PR を同時に積む stacked PR は使わない。
3. 各 PR は、単独でテストが通り、既存の本番 launchd を変更しない状態でマージできるようにする。
4. `install` と既定 `uninstall` は同じ PR に置く。
5. 内蔵 pipeline が手動実行で検証できるまでは、既存 `run-pipeline.sh` を本番経路から外さない。
6. `scripts/run-pipeline.sh` と旧静的 plist の削除は、production 切替後の連続7日観測を終えた別 PR で行う。
7. 各 PR は `docs/ACCEPTANCE_TEST_REPORT.md` の installer AC 節を更新する。
8. manual または代理指標が必要な AC を、自動テストだけで `PASS` にしない。
9. 実装 branch の開始条件は、clean な作業ツリーで基準 main SHA を取得できることである。
10. 利用者の既存 `package-lock.json` 変更、stash、認証情報、launchd 登録を実装準備のために変更しない。

### scale_exporterとの責任境界

`scale_exporter` は測定データ取得、JSONL出力、自身の設定、認証、バイナリ、LaunchAgentを所有する。
`scale2sheet` は自身のlaunchd、朝夕スケジュール、JSONL読取、Spreadsheet転記、pipelineを所有する。

連携は公開CLIとJSONL出力契約に限定する。
各Sliceは `jp.seijin.kappa.scale-exporter` と先方の設定、認証、バイナリを作成、変更、診断、登録解除、削除しない。
`scale-exporter-command` と `scale-exporter-output-dir` は当方の消費側設定であり、その参照先へinstall、uninstall、purge、wipe、archiveを適用しない。

先方LaunchAgentの既定時刻07:00、21:00と現行pipelineの同期起動を同時に有効化すると、同じ取得が二つのschedulerから起動されうる。
Slice 1のrun leaseは当方processだけを排他するため、この競合を防がない。
取得を先方scheduleに委ねて当方はJSONLだけを読む案、当方が公開CLIを同期起動する案、`invoke`と`consume`を切り替える案のユーザー決定、および選択した案に必要な公開契約が確定するまで、Slice 2以降を開始しない。

`install` と既定 `uninstall` を分けない理由は、両者が manifest の `installing | installed | uninstalling` 状態、`created-paths`、operation algebra、executor の再実行契約を共有するためである。
片方だけを先に実装すると、後続 PR が manifest schema と失敗復旧順序を変更し、先行 PR の受け入れ結果を無効にする。

## 実装分割の選択肢

### 案 I：単一 PR

一つの PR に foundation、pipeline、install、uninstall、doctor、purge、distribution を入れる。

| 評価軸 | 評価 |
| --- | --- |
| 利点 | 中間状態を公開せず、一度で機能を揃えられる |
| 欠点 | run lease、Google API 読取、不可逆操作、launchd 移行を同時にレビューするため、差分が大きくなる |
| 失敗時 | 原因箇所の切り分けと revert の範囲が広い |
| 判定 | 非推奨 |

### 案 II：コマンド別 PR

`pipeline`、`install`、`uninstall`、`doctor` の順にコマンド単位で分ける。

| 評価軸 | 評価 |
| --- | --- |
| 利点 | CLI の見た目と PR の名前が一致する |
| 欠点 | `install` と `uninstall` の共有状態機械を途中で分断する |
| 欠点 | `pipeline` と exporter command、PATH、plist の契約が別 PR に散りやすい |
| 判定 | 却下を推奨 |

### 案 III：依存順の capability slice

共有する不変条件を先に置き、独立に却下できる機能を後続 PR へ分ける。

| 評価軸 | 評価 |
| --- | --- |
| 利点 | kernel 排他、pipeline 保存機能、不可逆 purge を別々にレビューできる |
| 利点 | production launchd を変えずに内蔵 pipeline と lifecycle を先に検証できる |
| 欠点 | 実装 PR が6本、観測後 cleanup PR が1本になる |
| 欠点 | 各 PR を直列に進めるため、単一 PR より calendar time が延びる |
| 判定 | **採用** |

### Slice 2：内蔵 pipeline の shadow path

この PR は、production launchd を切り替えずに内蔵 pipeline を手動実行可能にする。

本Sliceの現行記述は、当方pipelineが `scale_exporter` の公開CLIを同期起動する案を前提とする。

pipeline 移植、exporter command、PATH、plist の値生成は同じ PR に置く。
ただし、plist の書込み、`launchctl bootstrap`、本番 label の変更は行わない。

pipeline は Slice 1 の read-only settings loader を使う。
exporter command の解決順序は、`.env` を含む環境変数 `SCALE_EXPORTER_COMMAND`、`settings.json` の `scale-exporter-command`、組み込み既定値 `scale_exporter` の順とする。
値に `/` が含まれる場合は `~` を展開した絶対パスだけを許可し、相対パスを拒否してから存在と実行権限を検査する。
それ以外は command 名として生成対象 plist と実行時の `PATH` で解決する。
`SCALE_EXPORTER_OUTPUT_DIR` など既存設定の「環境変数、settings、組み込み既定値」という優先順位は変えない。
exporter へ渡す source は現行と同じ `google-fit` に固定し、配置先を選ぶ `scale-exporter-command` と取得元を混同しない。

launchd は対話 shell の環境変数を継承しない。
`install --launchd` の実行時に `SCALE_EXPORTER_COMMAND` が明示されていた場合だけ、その値を plist の `EnvironmentVariables` へ保存する。
パス形式の値は展開済み絶対パスとして保存し、XML escape する。
明示されていない場合は plist へ同変数を書かず、pipeline が実行時に settings または組み込み既定値を読む。
plist の PATH は install 時の実効 command の親ディレクトリを含むため、後から settings の command を別ディレクトリへ変えた場合は `install --launchd` の再実行を必要とする。

この境界により、reviewer は `run-pipeline.sh` の H-a〜H-f が、H-c の確定済み2段階通知という境界を含めて保存されたことを、production schedule を変えずに判定できる。

## Slice ごとの完了ゲート

Slice 1〜6 のコード変更は、`npm run typecheck`、`npm test`、`npm run build:bun` の成功を共通ゲートとする。
Node.js 上の Vitest は module と adapter の契約を検査し、Bun compiled acceptance は配布実行体と macOS の kernel 境界を検査する。
一方だけで他方を代用しない。

fixtureまたはstubを使う試験は、`scale_exporter` の実設定、認証、バイナリ、LaunchAgentを作成または変更しない。
手動試験で実 `scale_exporter` を使う場合も、利用者または先方installerが導入済みであることを外部前提として記録する。

## AC-01〜AC-38 の割当

### 記録規則

検証方式は、目標定義の例外表から変更しない。

- **自動**：Vitest、隔離 filesystem、fake adapter、compiled Bun acceptance のいずれかで機械判定する
- **代理指標**：実 launchd または実通知の代わりに、plist、adapter 引数、通知要求を検査する
- **手動**：一時 label、実 macOS 通知、read-only の実 Spreadsheet 到達を人が確認する

一つの AC が複数方式を要求する場合、すべて完了するまでは `PARTIAL` とする。

| AC | 最終 owner | 必須方式 | Slice 内の証跡 |
| --- | --- | --- | --- |
| AC-01 | Slice 3 | 自動 | 一時 HOME と prefix で compiled binary の install が成功する |
| AC-02 | Slice 3 | 自動 | `<prefix>/bin/scale2sheet --version` が成功する |
| AC-03 | Slice 6 | 代理指標、手動 | 固定 checkout path 不在を自動検査し、一時 label で checkout rename 後の起動を確認する |

## ACCEPTANCE_TEST_REPORT の記録形式

既存 AT-01〜AT-18 は削除しない。
新しい `Installer AC（AC-01〜AC-38）` 節を追加する。

各行は次の列を持つ。

| 列 | 内容 |
| --- | --- |
| AC | `AC-01` から `AC-38` |
| owner Slice | 最終判定を閉じる Slice |
| 必須方式 | 自動、代理指標、手動の一つまたは複数 |
| 実施方式 | 実際に使った方式 |
| 対象 commit | 検証した full SHA |
| 実施日時 | JST の ISO 8601 |
| 証跡 | test 名、command、fixture、一時 label、ログのうち秘密情報を含まないもの |
| 判定 | `PASS \| PARTIAL \| BLOCKED \| PENDING` |
| 備考 | 適用範囲外、未実施理由、既知の限界 |

判定は次の意味で使う。

- `PASS`：必須方式をすべて満たした
- `PARTIAL`：自動または代理指標は通ったが、必須の手動確認が残る
- `BLOCKED`：必要な実機、認証、検証用 Spreadsheet を用意できず実施不能
- `PENDING`：owner Slice が未マージ、または観測期間が未完了

各 PR は、自分が追加または変更した AC 行と、既存37件のテストを含む全体サマリーを更新する。
後続 PR は以前の `PASS` を無条件に写さず、共有 module を変更した場合は関連 AC を再実行する。
secret、token、Spreadsheet ID、測定値、認証 JSON の内容を証跡へ書かない。

## run-pipeline.sh からの切替

### rollback snapshot

Slice 6 の production 操作前に、次を `~/.config/scale2sheet/rollback/<timestamp>/` へ mode `0700` で保存する。

- 切替前の repository revision
- `scripts/run-pipeline.sh`
- morning と evening の legacy plist
- 現在の installed binary の絶対パスと SHA-256
- `launchctl print` が両 label に対して成功したか
- rollback command

認証情報、settings の内容、Spreadsheet ID は snapshot に複製しない。

### 一時環境での受け入れ

production label を触る前に、次を満たす。

1. 一時 HOME、一時 prefix、一時 label、一時ログディレクトリを使う。
2. 検証用 Spreadsheet または read-only mock を使い、production Spreadsheet を変更しない。
3. morning と evening の ProgramArguments が installed binary の `pipeline` を指すことを確認する。
4. exporter failure と transfer failure の通知を fault injection で確認する。
5. active job 中の通常 install が中断し、`--force` だけが警告後に停止することを確認する。
6. checkout を rename した後も一時 label が起動することを確認する。

一時 label は試験後に必ず `bootout` し、一時 plist とログを削除する。

### production 切替

production 切替は repository の merge では自動実行しない。
利用者が runbook を明示的に実行する。

1. legacy process と新 run lease を検査する。
2. 実行中なら変更せず、完走後の再実行を案内する。
3. rollback snapshot の hash を再確認する。
4. legacy morning と evening label を `bootout` する。
5. installed binary と新 plist を配置する。
6. 新 morning と evening label を `bootstrap` する。
7. `launchctl print` の終了コードで両 label の登録を確認する。
8. plist が指す binary の存在、実行権限、`--version` を installer process 内で確認する。
9. いずれかが失敗した場合は新 label を両方 `bootout` し、legacy plist を戻して両 label を `bootstrap` する。

legacy と新 label を同時に登録しない。
同じ対象日へ二重転記する経路を作るためである。
production 切替では `kickstart` を使わない。

### 連続7日観測

観測初日は、production 切替後に最初の morning schedule が動く JST の暦日とする。
切替時の手動実行は観測日数へ含めない。
各暦日に、morning と evening でそれぞれ1回以上、launchd から開始した成功または正常な no-op の実行証跡が揃った場合だけ、その日を1日と数える。

毎日、次を記録する。

- launchd 起動の実行証跡
- `pipeline-status.json` の開始、完了、outcome
- 実行証跡がある run の Spreadsheet 結果
- stderr log
- OS 通知の有無

記録先は Slice 6 で作成した `docs/observations/<cutover-JST>_installer-cutover.md` とする。
観測記録には日付、period、開始元、開始時刻、終了時刻、outcome、確認者、関連する秘密情報を含まないログ参照だけを書く。
Spreadsheet ID、認証情報、測定値は記録しない。

体重計に乗らなかった no-op と pipeline 未実行は Spreadsheet 上で区別できない。
したがって「行が増えないこと」を自動的な失敗判定にしない。
利用者が Spreadsheet を目視し、未実行の疑いを判断した場合は調査または rollback を選ぶ。

いずれかの period に実行証跡が無い日、起動後に失敗した日、production の binary、plist、settings を変更した日、rollback した日は、連続日数を0へ戻す。
実行証跡がある正常な no-op は連続日数を維持する。
未実行と no-op を自動判定できない場合は、その日を `unverified` と記録して連続日数を0へ戻し、自動検出できたとは記録しない。

rollback 条件は次の三つである。

- 実行体が起動した後の pipeline failure
- fault injection で通知要求が失われる
- 実行証跡がある転記結果に後退がある

rollback では新 production label を両方 `bootout` し、snapshot の hash を検証して legacy script と plist を戻し、両 label を `bootstrap` する。
status、ログ、settings、認証情報は削除しない。

7日連続で各日の morning と evening が上記条件を満たし、観測記録を reviewer が確認した場合だけ Slice 7 を作る。
