# herdr pane 配置についての検討書

## 背景

Ph.8 で確立した 3 層体制（claude_product_manager / codex_senior_architect / codex_senior_programmer）を herdr の 1 workspace 内でどう pane 配置するか、また再現可能な構築手順をどう記録するかを決める必要があった。

## 採用した案

**manager 左・全高、architect 右上、programmer 右下の 2 カラム構成**を採用し、構築コマンド一式を PLAN.md に追記する。

- manager は kappa との対話・PR フロー操作が最も長文になるため全高を割り当てる
- architect / programmer は codex ペアとして右カラムに縦積みし、レビュー↔実装の往復を視線移動だけで追える
- workspace はラベル `scale2sheet` で識別する（workspace ID / pane ID は再作成で変わるため、ID は文書に固定値として書かず `herdr agent list` で都度取得する運用とする）
- `--split` がフォーカス中 pane 基準で動く点が再現時の主な落とし穴のため、focus を明示するコマンド手順として残す

## 却下した案

### 案A: 3 カラム横並び（manager / architect / programmer を等幅で横に並べる）

却下した理由: 各 pane の横幅が狭くなり、コード diff やログの折り返しが増えて可読性が落ちる。3 者の重要度・出力量は等価ではなく、等幅にする利点がない。

### 案B: エージェントごとに別 workspace（または別 tmux セッション）に分離する

却下した理由: 3 エージェントの同時監視が一画面でできず、切り替え操作が常時発生する。チームとしての作業状況を俯瞰するという配置目的に反する。

### 案C: 構築手順を PLAN.md に書かず、シェルスクリプト化のみで済ませる

却下した理由: workspace ID / pane ID が動的で完全自動化には ID 取得・分岐処理が必要になり、現時点では過剰。まず計画書に手順と落とし穴（focus 依存の split、root pane の後始末）を記録し、再構築頻度が上がったらスクリプト化を検討する。
