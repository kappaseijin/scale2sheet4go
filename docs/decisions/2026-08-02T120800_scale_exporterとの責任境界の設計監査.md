# scale_exporterとの責任境界の設計監査

## 位置づけ

本書は、`scale2sheet` のインストーラ設計と実装分割が `scale_exporter` の責任を所有していないかを監査する。

監査対象は `main` の `6dbdd4505e4cf2d8799ae3e98cb8c55d89083c0b` にある次の正本である。

- `docs/INSTALLATION_DESIGN.md`
- `docs/decisions/2026-07-29T173454_インストーラ実装分割と受け入れ確認の検討書.md`
- AC-01からAC-38を定義する `docs/decisions/2026-07-29T084808_インストーラとアンインストーラの目標定義.md`

監査開始後に `24ef0b8569c3edc2df8532ac1f958db4413df378` から進んだ差分は `docs/PLAN.md` だけである。
同差分が記録した責任分界、二重取得の未解決状態、Slice 2の監査待ちは本書と一致することを確認した。

他チームのリポジトリと文書には直接アクセスしていない。
他チームの事実は、`scale2sheet_pm_claude` が2026-08-02に中継した次の責任分界だけを入力とする。

- `scale_exporter` は測定データ取得、JSONL出力、自身の設定、認証、バイナリの install と uninstall を所有する。
- `scale2sheet` は自身の launchd、朝夕スケジュール、Spreadsheet転記、pipeline実行を所有する。
- 連携は公開CLIとJSONL出力契約に限定する。
- `scale_exporter` は専用LaunchAgent `jp.seijin.kappa.scale-exporter` と既定時刻07:00、21:00を持つ予定である。
- `scale2sheet` は `jp.seijin.kappa.scale-pipeline.morning` と `jp.seijin.kappa.scale-pipeline.evening` だけを管理する。

## 結論

監査項目1から5には、`scale_exporter` の設定、認証、バイナリ、LaunchAgentを作成、変更、退避、削除する処理はない。
したがって、現行文面から確定できる実処理には責任境界の越境がない。

ただし、`scale2sheet` の設定や認証を単に「設定」「認証情報」と呼ぶ箇所があり、将来の実装で `scale_exporter` の資産まで対象に含められる余地が残る。
実装前に、所有物と読み取り可能範囲を両正本へ明記する必要がある。

追加された監査項目6には未解決の設計衝突がある。
現行設計は `scale2sheet pipeline` が `scale_exporter --source google-fit` を同期起動してからJSONLを読むため、明確に案Bを前提としている。
同じホストで `scale_exporter` 自身のLaunchAgentも07:00、21:00に有効化すると、二つのプロセスが同じ取得処理を開始しうる。
`scale2sheet` のrun leaseは `scale2sheet` プロセスだけの排他なので、この競合を防がない。

この衝突は実装詳細では閉じない。
案A、案B、案Cのいずれかをユーザーが決定し、その決定に合わせて目標定義、インストール設計、実装分割、AC対応を更新する必要がある。
Slice 1は exporter に触れないため継続できるが、Slice 2は決定、公開契約、Issue #38のproducer供給観測設計が完了するまで開始できない。

## 既存5項目の監査

### exporter commandの解決

`SCALE_EXPORTER_COMMAND` と `~/.config/scale2sheet/settings.json` の `scale-exporter-command` は、`scale2sheet` が公開CLIをどう起動するかを指定する消費側の設定である。
解決処理は値の優先順位、絶対パス、実行権限、`PATH`だけを扱い、`scale_exporter` の設定ファイルを読まず、書かず、生成しない。

したがって現行案は責任境界内にある。
ただし設定キーの説明には、これが `scale2sheet` 所有の呼び出し参照であり、`scale_exporter` の導入先または内部設定を管理するものではないことを追記する。

### plistのEnvironmentVariables

`scale2sheet` が自身のplistへ展開済み絶対パスまたはcommand名を保存することは、自身の子プロセス起動条件を固定する操作である。
`jp.seijin.kappa.scale-exporter` の作成、変更、登録解除を行わない限り、先方のLaunchAgentを所有することにはならない。

したがって現行案は責任境界内にある。
ただしパスは導入形態の保証ではなく、`scale2sheet install --launchd` 時点の呼び出し先snapshotである。
先方の再インストールで実体が移動した場合は、公開CLIの新しい場所を利用者が指定し、当方のinstallを再実行する。

### doctorの診断範囲

現行doctorは、`scale_exporter` についてcommandの解決とJSONL出力ディレクトリの読取可否だけを検査する。
この二つは公開CLIと出力契約を利用できるかを判定する消費側診断であり、先方の設定または認証の健全性診断ではない。

`source に必要な追加認証ファイル` は `scale2sheet` が直接扱う `google-fit` の認証を指す。
文面だけでは `scale_exporter` の認証も含むように読めるため、次を明記する。

- doctorは `scale_exporter` の設定ファイルと認証ファイルを探索または検証しない。
- doctorは `scale_exporter` のinstall、修復、再認証を実行しない。
- exporter側の失敗は公開CLIの終了結果またはJSONLの読取結果までを報告し、内部原因は先方の診断手順へ委ねる。

### purgeとwipeの対象

現行設計の既知対象は `~/.config/scale2sheet/`、`~/Library/Logs/scale-pipeline/`、当方のplist、manifest、statusである。
`scale_exporter` のバイナリ、設定、認証、LaunchAgent、JSONL出力は対象に含まれていない。

したがって現行案は責任境界内にある。
ただし `設定から解決した認証 file` を `scale2sheet` 自身の設定schemaで列挙した認証fileに限定する。
`scale-exporter-command` と `scale-exporter-output-dir` が指す実体は参照先であり、purge、wipe、archiveの対象にしないことも明記する。

### AC-01からAC-38

exporterの実行を扱うAC-26からAC-31は、process fake、fixture実行体、delay、notifier、status、run leaseの差し替えで判定する。
この自動判定は `scale_exporter` の実インストール、設定、認証を前提にしない。

AC-27とAC-28の実通知もfault injectionで発火条件を作れるため、先方の実認証を前提にしない。
production切替では外部依存として公開CLIまたはJSONL出力が必要になるが、依存物が用意済みであることと、当方がその導入を所有することは別である。

AC対応へ次の共通条件を追記する。

- 自動試験はfixtureまたはstubだけを使い、`scale_exporter` の実設定、認証、バイナリ、LaunchAgentを作成または変更しない。
- 手動試験で実 `scale_exporter` を使う場合も、利用者または先方installerが導入済みであることを外部前提として記録する。
- `scale_exporter` が未導入であることを、当方のAC失敗として解消するために先方資産を変更しない。

## 定期実行の重複

### 現行設計が前提とする案

現行設計は案Bである。
その根拠は次の記述にある。

- pipeline処理の手順5から8が exporter を起動し、失敗時に計3回再試行する。
- `scale-exporter-command` と `SCALE_EXPORTER_COMMAND` が起動対象を指定する。
- plistの `PATH` が exporter の親ディレクトリを含む。
- AC-26からAC-31が exporter process の失敗、再試行、通知、転記中断を検査する。

一方、既存のJSONL readerと `scale2sheet run --source scale-exporter` は、既に案Aの「出力だけを消費する」経路を持つ。
案Aは新しいreaderを必要とせず、pipelineからproducer起動責務を外す変更になる。

### 案A

案Aでは `scale_exporter` が自身のスケジュールで測定データを取得してJSONLを公開し、`scale2sheet pipeline` は公開済みJSONLの読取とSpreadsheet転記だけを行う。

この案は責任分界と一致する。
取得の実行、失敗時の再試行、取得失敗の通知はproducerが所有し、consumerは入力の読取失敗と転記失敗を所有する。
両チームが互いのLaunchAgentまたは設定を操作する必要がなく、二重取得とcross-process leaseも不要になる。

ただし07:00と21:00にproducerとconsumerを同時起動すると、consumerがJSONL公開前に読む競合が残る。
現行readerは対象日のファイル名だけで入力を選び、出力ディレクトリまたは対象ファイルが無い場合は空配列で正常終了する。
一方、対象ファイルが存在して行が契約を外れる場合は例外で読取全体が中断し、先行する正常行を含む部分結果を返さない。
producerの今回の実行が完了したか、当日分が古い実行の出力か、no-dataかは判定しない。
したがって、時間差だけでは通常時の重なりを減らせても、producer失敗後に古い出力を読むことまたは未実行をno-dataとして扱うことを検出できない。
案Aを採るには、公開出力契約として次を合意する必要がある。

- JSONLをatomicに公開すること。atomic公開が無い場合、切れた最終行のJSON parse失敗は静かな欠測ではなくhard errorとして読取全体を中断する。
- consumerが対象日とsourceの公開完了、成功、no-dataを識別できる完了記録を持つこと。
- 完了記録を持たない場合はproducer完了後にconsumerを起動する時間差を設け、producer失敗の通知を先方が所有し、no-data、古い出力、未実行を当方が区別しない限界をユーザーが受け入れること。
- 拾い直し時刻と、どの時点までに公開された出力を対象にするかを明記すること。
- JSONL行schemaの正本、変更通知、互換期間、`source` が取りうる値の集合を合意すること。
- producerがconsumerの知らない値を出した場合に、読取全体の失敗、該当行の隔離、既定値への写像のどれを行うかを合意すること。
- 同じ出力ディレクトリへ書き込む主体と、複数主体が存在する場合のnamespaceまたは衝突回避を合意すること。
- 対象日とperiodについて、producerが実行した結果として0件だった状態をconsumerが識別できること、または識別できない限界をユーザーが受け入れること。

案Aを採った場合の変更範囲は次のとおりである。

| 対象 | 変更 |
| --- | --- |
| 目標定義 | H-a、H-b、H-c、H-fとAC-26からAC-31の責任を再定義する。producer側の取得再試行とconsumer側の読取、転記を分ける |
| Slice 2 | exporter起動、`SCALE_EXPORTER_COMMAND`、`scale-exporter-command`、exporter親ディレクトリのPATH追加を削除する。JSONL読取、period検証、status、log、transfer通知、run leaseは残す。Issue #38の処理段階別件数をstatusとlogへ記録する |
| Slice 3 | `install --launchd` のexporter実行体検査を削除する。先方LaunchAgentは作成、検査、登録解除しない |
| Slice 4 | exporter command診断を削除し、設定済みJSONL出力ディレクトリの存在、読取可否、入力形式だけを診断する |
| Slice 5 | 実装変更は不要である。先方資産をpurge対象外とする境界だけを明記する |
| Slice 6 | producer完了後にconsumerが読む時刻または完了契約を手動受け入れへ追加する。取得失敗通知は当方の手動試験から外す |
| Slice 7 | 旧script削除は維持する。Slice 2で確定したproducer供給とconsumer転記の証跡を使って観測する。Slice 7で観測項目を後付けしない |

### 案B

案Bでは `scale2sheet pipeline` が従来どおり公開CLIを同期起動し、成功後にJSONLを読んで転記する。

この案は、公開CLIだけを使う限り責任境界には違反しない。
しかし、同じホストで先方LaunchAgentも有効にするなら、二重取得を避ける追加契約が必要になる。

取りうる運用は二つである。

1. `scale2sheet` と連携するホストでは先方LaunchAgentを有効にせず、取得の起動主体を当方pipelineだけにする。
2. 両LaunchAgentを有効にし、先方の公開CLIが全起動元に共通する排他、busy結果、完了済み出力の再利用を契約する。

前者は単純だが、「scale_exporter 自身にも定期実行が必要」という今回の指示と同一ホストで両立しない。
後者は、07:00と21:00の衝突が通常経路になるため、当方の3回再試行だけでは十分であると判断できない。
先方の排他中に当方CLIがどの終了コードを返すか、待機後にどの出力を読めばよいか、SIGKILL後に誰が回復するかを公開契約として固定する必要がある。

案Bを採った場合、Slice 2の現行範囲は残る。
その上でbusy結果の分類、待機、出力再利用、二つの起動元を同時に動かす受け入れ試験を追加する。
先方のLaunchAgent自体は当方のplanner、doctor、uninstall、purgeの対象にしない。

### 案C

案Cでは `invoke` と `consume` を `scale2sheet` の設定で切り替え、案Aと案Bの両方を製品機能として維持する。

この案は単体利用と連携利用を一つのバイナリで選べるが、pipeline、doctor、plist、通知、ACを二経路に分ける。
利用者が両側のLaunchAgentを有効にしたまま `invoke` を選ぶ誤設定も防げない。
現在の単一利用環境に対して検証面が増えすぎるため、推奨しない。

## 推奨

案Aを条件付きで推奨する。

理由は、producerが取得と自身の定期実行を所有し、consumerが公開済み出力の読取と転記を所有する分界が、設定、認証、install、uninstall、LaunchAgentの所有関係と一致するためである。
同じ取得を二つのschedulerから起動する仕組みを残すより、公開出力を唯一の結合点にする方が失敗の所有者を一意にできる。

この推奨は、同時刻の読取競合またはproducerの現行稼働状態を無視して案Aを採るという意味ではない。
先方の定期取得が当該ホストで成功し、JSONLのatomic公開、行schema、出力主体、完了と0件の識別に関する公開契約を得ることを成立条件とする。
完了記録を持たない場合は、producer完了後にconsumerを起動する時間差と、no-data、古い出力、未実行、producerの空出力を区別できない限界をユーザーが受け入れる必要がある。

案Bを選ぶ場合は、先方のLaunchAgentを同じホストで無効にするか、公開CLIの共通排他とbusy時の契約を先に確定する必要がある。
当方のrun leaseを先方へ共有したり、先方のlock fileを直接読んだりする設計は採らない。

## 正本へ反映する差分

案A、案B、案Cの決定に依存しない差分は次のとおりである。

1. `INSTALLATION_DESIGN.md` の非目標を、`scale_exporter` の設定、認証、バイナリ、LaunchAgentのinstall、uninstall、修復へ拡張する。
2. 同書へ責任境界節を追加し、公開CLIとJSONL出力以外の先方資産を読取、変更、削除しないと定義する。
3. doctorが先方の設定と認証を診断しないことを明記する。
4. purge、wipe、archiveが `scale-exporter-command` と `scale-exporter-output-dir` の参照先へ追従しないことを明記する。
5. 実装分割の共通ゲートへ、fixtureまたはstubを使い先方資産を変更しない条件を追加する。

案固有の差分は、ユーザー決定後に前節の表に従って適用する。
それまでは `INSTALLATION_DESIGN.md` と実装分割検討書に、Slice 2の開始条件として本件の決定、公開契約、Issue #38のproducer供給観測設計の確定を追加する。

## 公開契約と稼働前提の現況

次の現況は、先方managerの2026-08-03の回答を `scale2sheet_pm_claude` が同日に中継した内容である。
本監査では先方環境または先方文書へ直接アクセスしていないため、独立実測ではなく伝聞として扱う。

- 先方LaunchAgentのplistは引数を持たず、既定sourceは`apple-health`のままだった。
  macOSでは`isHealthDataAvailable()`がfalseとなるため、定期実行はexit 2で失敗し続けていた。
- iPhoneショートカット経由のPh.11形式JSONLも同じ出力ディレクトリへ書き込まれていた。
  同形式では`source`にデバイス名が入り、当方readerが期待する`apple_health | google_fit`と衝突する。
- 先方は、定期実行のsource選択とJSONLの値域逸脱を先方側の問題とし、当方readerの現行契約は妥当で変更を求めない方針を示した。
- 先方は、公開契約が確定するまでSlice 2を開始しない当方のゲートを妥当とした。

この現況により、案Aが前提とする「producerが自身のscheduleで取得して公開する」は、当該ホストで現在成立していない。
案Aの条件付き推奨は責任分界の評価として維持するが、先方が定期取得経路を修復し、公開契約を確定する前に採用可能とは判定しない。

また、現行の連続7日観測はconsumerの実行証跡だけを基準とし、producerが動作したが空出力だった日を正常なno-opから区別できない。
この欠落はSlice 7で判定するときではなく、観測記録のschemaを作るSlice 2で閉じる必要がある。
Slice 2で記録しなければ、その後の7日分へ必要な情報を遡って追加できないためである。

当方単独で、対象日に一致したfile数、読取対象行数、period window適用後のreading数をstatusとlogへ記録できる。
この三つにより、「対象fileが無い」と「fileはあるが使えるreadingが無い」を分離する。
一方、producerが実行した結果として0件だった状態と、producerが未実行または未公開だった状態の完全な識別は、先方の公開完了契約に依存する。
Issue #38の当方側schemaと公開契約が確定するまで、Slice 2を開始しない。

## 決定待ち

次の判断はユーザーが行う。

- [ ] 案A：`scale_exporter` が定期取得し、`scale2sheet` は公開済みJSONLだけを読む。
- [ ] 案B：`scale2sheet` が公開CLIを同期起動する。先方LaunchAgentとの共存条件を別途固定する。
- [ ] 案C：`invoke` と `consume` の両モードを持つ。

決定前に、pm経由で次の公開契約を確認する。

- 先方LaunchAgentと手動CLIの同時起動に共通排他があるか。
- 競合時の終了結果と再試行契約は何か。
- JSONLはatomicに公開されるか。
- 対象日、period、no-dataを含む出力完了をconsumerが識別できるか。
- 07:00と21:00にconsumerが読む場合の推奨順序または時間差は何か。
- JSONL行schemaの正本はどちらが持ち、`source`の値域を含む変更をどのように通知し、どの互換期間を設けるか。
- producerがconsumerの知らない値を出した場合、読取全体を失敗させるか、該当行を隔離するか、既定値へ写像するか。
- 出力ディレクトリへ書き込む主体は誰か。複数主体が書く場合、ファイル名、schema、公開完了をどのように分離するか。
- 対象日とperiodについて、producerが実行した結果として0件だったことをconsumerが識別できるか。
- exit 5とexit 6はGoogle Fit経路でも返るか。
- exit 5とexit 6は同じ入力で再実行しても回復しないterminal codeか。
- transient failureを表す終了コードのallowlistは何か。HTTP 503はどのcodeになるか。
