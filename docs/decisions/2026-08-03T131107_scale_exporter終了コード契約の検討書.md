# scale_exporter終了コード契約の検討書

## 位置づけ

本書は、`scale_exporter` が検討しているexit 5とexit 6を、`scale2sheet pipeline` がどのように扱うかを比較する。
契約の決定者はユーザーであり、本書は選択肢、帰結、推奨を提示する。

入力は当方Issue #40と、2026-08-03に`scale2sheet_pm_claude`が中継した先方managerの回答である。
他チームのリポジトリ、文書、実行環境には直接アクセスしていない。
先方の終了コードは案であり、先方ユーザーの決定前である。

## 対象範囲

本契約は、`scale2sheet pipeline` が`scale_exporter`の公開CLIを起動し、その終了結果を直接受け取る経路だけを対象とする。
現行の対象は`--source google-fit`である。

Apple Health形式のJSONLはiPhoneショートカットが出力ディレクトリへ直接書いており、当方pipelineはその生成processの終了コードを受け取らない。
したがって、exit 5とexit 6がApple Health経路だけへ導入される場合、本契約による分岐は実行されない。
先方には両コードをGoogle Fit経路にも導入するかを照会中である。

## 確認できている事実

現行`run-pipeline.sh`は、exporterの終了コードを分類しない。
終了コード0以外を一律に失敗とみなし、初回を含む計3回、試行間を60秒空けて再試行する。
3回とも非ゼロの場合は通知を要求し、`scale2sheet run`を起動せずに終了コード1で終わる。

この再試行は、2026-07-02に発生したGoogle APIのHTTP 503から回復するために導入された。
現行CLIが503と恒久失敗を異なる終了コードで返す契約は確認できていない。
したがって、未知の非ゼロコードを直ちに再試行対象から外すと、既存の503回復経路も同時に失う可能性がある。

現行readerは、対象ファイルが存在しない場合は空配列を返す。
一方、対象ファイルの1行でもschemaを外れると読取全体を例外で中断し、正常行を含む部分結果を返さない。
このため、exit 5とともに出力ファイルが存在しても、隔離後の正常部分だけを安全に転記できる契約は現在ない。

先方からは次の公開契約上の制約も中継されている。

- launchd実行と手動実行の共通排他はない。
- JSONL公開はatomicではなく、consumerが書込み途中を読む可能性がある。
- 複数ファイルを一括でatomicに公開する仕組みはない。
- exit 0でも出力ファイルが存在しない場合がある。

先方はraw stagingから検証、正規化、atomic公開を行う案を検討しているが、先方ユーザーは未決定である。

## 契約と実装の区別

当方が先方へ回答するのは、公開された終了コードをどう解釈するかという契約である。
現行shellがその契約を実装できることを意味しない。

| 項目 | 現行実装 | 契約として約束できる状態 |
| --- | --- | --- |
| exit 6 | 他の非ゼロと同じく3回再試行し、最後はexit 1へ畳む | 再試行せず、転記未実施の専用outcomeと生のexit 6を記録できる |
| exit 5 | 他の非ゼロと同じく3回再試行し、出力を読まない | 再試行せず、契約違反としてfail-closedにし、生のexit 5を記録できる |
| 未知の非ゼロ | 3回再試行し、最後はexit 1へ畳む | 異常として扱い、互換期間中は上限付き再試行後に失敗できる |
| statusとlog | exporterの生の終了コード、試行回数、reader件数を保持しない | Slice 2で分類結果と件数を追加できる |

契約を採用する場合は、Slice 2の内蔵pipelineが終了コードを取得し、statusとlogへ保存する必要がある。
既存shellをそのまま契約適合と記録することはできない。

## exit 6の選択肢

先方案では、exit 6は入力自体が更新されておらず、出力が0件だった状態を表す。
これは転記成功でも、利用者が測定しなかった正常なno-opでもない。

### 案6-A：従来どおり3回再試行する

60秒以内に入力が更新される場合は回復できる。
ただし先方がexit 6をterminalな状態として定義するなら、同じ入力を3回読み直して合計120秒待つだけになる。
一時的な入力待ちをexit 6へ含めるかが先方契約で決まらない限り、再試行の効果を保証できない。

### 案6-B：再試行せず、転記未実施として終了する（推奨）

exporterは1回だけ起動する。
exit 6を受けたpipelineはreaderとSpreadsheet転記を起動せず、`degraded:producer-no-fresh-input`、生のexit 6、試行回数1、転記未開始をstatusとlogへ記録する。
通知はexporter段階で1回だけ要求する。

`scale2sheet pipeline`自身は非ゼロで終了するが、exit 6を透過しない。
生の値はstatusとlogへ保持し、当方CLIの終了コード空間とは分離する。
案6-Bを採用する場合、当方pipelineは終了コード3を返す。
この扱いにより、launchd上の成功と転記未実施を同一にしない。

### 案6-C：正常なno-dataとして終了する

再試行せず、当方pipelineを終了コード0にする。
運用上の警報を減らせるが、producerの入力が更新されていない状態を利用者の正常なno-opと誤認しやすい。
Issue #37とIssue #38で問題になった静かな欠測を残すため、推奨しない。

## exit 5の選択肢

先方案では、exit 5は入力を取得したものの、出力契約に違反するデータを検出して隔離した部分的失敗を表す。
非ゼロ終了と出力ファイルの存在が同時に起きる。

### 案5-A：従来どおり3回再試行する

同じ契約違反データを再処理する場合、再試行では回復しない。
再試行ごとに隔離物または出力が増える契約であれば、後続の読取対象も不明確になる。
exit 5がterminalと定義される限り、推奨しない。

### 案5-B：再試行せず、出力を読まない（推奨）

exit 5を受けたpipelineはreaderとSpreadsheet転記を起動しない。
`failed:exporter-contract`、生のexit 5、試行回数1、出力未消費をstatusとlogへ記録し、exporter段階の通知を1回要求して非ゼロ終了する。
案5-Bを採用する場合、当方pipelineは異常を表す終了コード1を返す。

出力が存在しても、どのfileまたはrowが検証済みかを当方だけでは判断しない。
これにより、不完全なbatchの一部だけを転記して処理済みに見せる経路を閉じる。

### 案5-C：隔離されなかった出力だけを転記する

有効な測定値を失わない利点がある。
ただし採用には、検証済み出力と隔離出力のnamespace分離、batch identity、公開完了、atomic公開、正常部分のschema保証が必要になる。
現行のall-or-nothing readerと非atomic公開では成立しないため、将来の公開契約が揃った場合だけ再検討できる。

## 未知の終了コードの選択肢

未知の非ゼロコードは成功またはno-dataへ写像しない。
どの案でも異常として扱い、readerと転記を成功扱いで続行しない。

### 案U-A：直ちに失敗する

未知コードを1回受けた時点で失敗する。
fail-fastになる一方、現在code別に表現されていない503まで再試行しなくなる可能性がある。

### 案U-B：互換期間中は上限付き再試行する（推奨）

exit 5とexit 6だけをterminal codeとして再試行対象から外す。
それ以外の非ゼロコードは異常として記録しつつ、既存どおり最大3回、60秒間隔で再試行する。
最終失敗時は最後の生code、全試行のcode列、試行回数をstatusとlogへ残す。

先方がtransient codeのallowlistを公開した後は、そのcodeだけを再試行する。
allowlist確定後の未知codeは直ちに失敗させる。
この二段階移行により、既存503保護を維持しながら将来のfail-fastへ移れる。

### 案U-C：未知コードを恒久的に再試行する

既存動作との互換性は高い。
ただし恒久失敗のcodeが追加されるたびに120秒の待機が発生し、契約追加を当方が認識できない状態を固定するため、推奨しない。

## 推奨する組み合わせ

案6-B、案5-B、案U-Bの組み合わせを推奨する。

| exporter結果 | 再試行 | readerと転記 | 当方outcome | 当方process |
| --- | --- | --- | --- | --- |
| 0 | しない | 実行する | readerと転記結果に従う | 成功時0、readerまたは転記失敗時1 |
| 5 | しない | 実行しない | `failed:exporter-contract` | 1 |
| 6 | しない | 実行しない | `degraded:producer-no-fresh-input` | 3 |
| その他の非ゼロ | 最大3回、60秒間隔 | 成功するまで実行しない | 上限到達時`failed:exporter-unknown` | 1 |

この組み合わせは、先方が「5と6は同じ入力で再実行しても回復しないterminal code」と契約することを前提とする。
先方が6を時間経過で回復しうるtransient codeとして定義する場合は、案6-Aを再評価する。

## 当方pipelineの終了コード空間

推奨する組み合わせを採用する場合、当方が制御して終了する`scale2sheet pipeline`のcodeを次に固定する。
先方の生codeは透過せず、statusとlogだけへ記録する。

| code | 当方での意味 | 主な経路 |
| --- | --- | --- |
| 0 | pipeline成功 | exporter成功後のreaderと転記が完了した |
| 1 | 異常終了 | exporter契約違反、未知codeの上限到達、readerまたは転記失敗 |
| 2 | 引数不正 | AC-30で予約済みの不正period |
| 3 | producer未更新によるdegraded | 案6-Bの`degraded:producer-no-fresh-input` |

code 3は成功ではないため、launchdからは転記未実施として観測できる。
一方、code 1との違いは当方の終了codeでも残り、詳細な原因と先方の生codeはstatusとlogで判定する。
signal終了やruntime自身の異常終了は、この表の当方制御codeには含めない。

## statusとlogの最小拡張

Slice 2では、periodごとのstatusとtimestamp logへ次を追加する。

- `exporter-exit-code`：最後に観測した生の終了コード
- `exporter-attempt-count`：実行した回数
- `exporter-attempt-codes`：各試行の終了コード列
- `transfer-started`：readerとSpreadsheet転記を開始したか
- `matched-file-count`：対象日に一致したJSONL file数
- `read-line-count`：空行を除き、readerが読取対象にした行数
- `windowed-reading-count`：period window適用後に残ったreading数

件数は、その段階まで処理が到達した場合だけ数値を記録する。
未到達またはparse中断を0として記録せず、未計測として区別する。

exit 5とexit 6ではreaderを起動しないため、三つのreader件数は未計測になる。
代わりに生の終了コードと`transfer-started: false`が、producer段階で転記を止めた理由を示す。

exit 0の経路では三つの件数を記録する。
これにより、当方単独で「対象fileが無い」「fileはあるが読取行が無い」「readingはあるがperiod windowに残らない」を分離できる。
producerが実行した結果として0件だったことと、producerが実行されなかったことの完全な識別は、先方の公開完了契約に依存する。

この切り分けはIssue #38のうち当方単独で閉じられる範囲である。

## 受け入れ確認

Slice 2のprocess fakeとfixture exporterを使い、少なくとも次を自動検査する。

1. exit 6は1回だけ実行し、delay、reader、転記を呼ばず、専用outcomeと生codeを記録して当方code 3で終了する。
2. exit 5は出力fileが存在しても1回だけ実行し、readerと転記を呼ばず、当方code 1で終了する。
3. 未知codeが2回続いた後に0となる場合、60秒delayを2回挟み、readerと転記を1回だけ実行する。
4. 未知codeが3回続く場合、全code列を記録し、readerと転記を呼ばずに当方code 1で失敗する。
5. exit 0で対象fileが無い場合、`matched-file-count: 0`と後続件数を区別して記録する。
6. 対象fileに行があるがperiod windowに残らない場合、三つの件数が処理段階に対応する。
7. parse失敗では未到達の件数を0にせず、reader失敗として記録する。
8. 503相当の一時失敗を表す既存codeは、先方のtransient code契約が確定するまで上限付き再試行される。

実`scale_exporter`の設定、認証、バイナリ、LaunchAgentは自動試験で作成または変更しない。

## 先方へ確認する公開契約

公開契約の確認項目と回答の正本は、`docs/decisions/2026-08-02T120800_scale_exporterとの責任境界の設計監査.md`とする。
本書では、終了コードに固有の次の三項目を同監査書へ追加してmanager間で確認する。

- exit 5とexit 6はGoogle Fit経路でも返るか。
- exit 5とexit 6は同じ入力で再実行しても回復しないterminal codeか。
- transient failureを表す終了コードのallowlistは何か。HTTP 503はどのcodeになるか。

exit 0と出力0件の識別、atomic公開、隔離物と公開物のnamespace分離は、同監査書に既にあるため本書で重複管理しない。

## ユーザー決定

次の三つを独立に決定する。

- [ ] exit 6：案6-A（3回再試行）
- [ ] exit 6：案6-B（再試行せず、転記未実施として記録。推奨）
- [ ] exit 6：案6-C（正常なno-dataとして終了）

- [ ] exit 5：案5-A（3回再試行）
- [ ] exit 5：案5-B（再試行せず、出力を読まない。推奨）
- [ ] exit 5：案5-C（契約済みの正常部分を転記）

- [ ] 未知code：案U-A（直ちに失敗）
- [ ] 未知code：案U-B（互換期間中は上限付き再試行。推奨）
- [ ] 未知code：案U-C（恒久的に上限付き再試行）

どの案でも、未知の非ゼロcodeを成功または正常なno-dataとして扱わない。
